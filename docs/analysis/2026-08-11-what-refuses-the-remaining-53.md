# 剩下 53 条被谁拒的：三个总体，外加一个新发现的静默洞

> 日期：2026-08-11
> 阶段：Phase 40 S3（归因，不改解码器）
> 产物：`examples/probe_phase40_text_and_polyline_refusals`
> 上游：S1 `2026-08-10-the-silent-bucket-is-refusals-not-unknowns.md`、
> S5 `2026-08-11-remaining-header-is-the-psm-aux-field.md`

## TL;DR

S5 之后静默桶从 141 降到 53。这 53 条**不是一个病因**，是三个，且都**不是**
S5 那个病因——`igTextBox` 与 `igLineString2d` 压根不校验 `aux_hi`。

| 总体 | 报告数 | 第一道拒收规则 | 性质 |
|---|---:|---|---|
| A | 33 | `igTextBox`：`+30` 的内联长度 ≠ 从 `btf` 推出的长度 | **三个子总体**，见下 |
| B | 12 | `igTextBox`：`btf < 68`（假定的固定开销） | 与 A 同根：68 不是下界 |
| C | 8 | `igLineString2d`：两个顶点完全重合 | **大概率是正确的拒收** |

**外加一个 S3 才看见的洞：还有 32 条被拒记录连 S2 的警告都发不出来**，
因为它们的起始字节落在别的家族已认领的字节区间里。

## 一、先把分母对齐

per-family 的「解码器说不」与发行版普查的「没人认领」**不是一回事**。
普查判定 `Rejected` 的条件是记录起点不落在任何家族的 `decoded_ranges` 内。
两个口径差 32 条：

| 家族 / 规则 | 解码器拒收 | 普查报告 |
|---|---:|---:|
| `igTextBox` / `inline-len-mismatch` | 52 | 33 |
| `igTextBox` / `btf-below-overhead` | 17 | 12 |
| `igLineString2d` / `degenerate` | 16 | 8 |

对齐后的 `reported` 与棘轮逐 fixture 完全吻合（4 / 5 / 18 / 5 / 13+8=21），
说明这次归因和发行版走的是同一个分母。

作为规模参照：今天被接受的 `igTextBox` 191 条、`igLineString2d` 153 条。

## 二、总体 A：`+30` 与 `btf` 对不上（33 条报告 / 52 条拒收）

解码器的做法是**假定固定 68 字节开销**，从 `bytes_to_follow` 反推文本长度，
再要求 `+30` 的 u16 与之相等：

```rust
let derived = (btf - IGTEXTBOX_PAYLOAD_OVERHEAD) / 2;   // 68 写死
if inline_text_length != derived { return None; }
```

判据：**反过来相信 `+30`**。若 `+30` 是真长度，那么 `btf - 2*inline` 就是这条
记录的真实开销；再看 `+32` 起的 UTF-16 读不读得成文本。结果分成三堆：

| `btf - 2*inline` | 条数 | 文本可读 | 样例 |
|---:|---:|:---:|---|
| **108** | 9 | **9/9** | `"MPag"` |
| **100** | 15 | **11/15** | `" "` |
| 40 / 72 / 76 / 78 / 84 / 86 | 13 | 0/13 | — |
| **负数**（−40658 … −71422） | 15 | 0/15 | — |

- **24 条落在恰好两个值（100、108）上，其中 20 条读出可读文本。** 开销不是常数
  而是**两三个变体**，`+30` 在这批里就是长度——和 S5 同款：把首批记录的规律
  硬化成了规则。
- **15 条 `inline` 大到荒谬**（`btf=68` 而 `inline=21495`）。这批的 `+30`
  **确定不是长度**，是另一回事。
- 中间 13 条散在六个开销值上、零条可读，**暂时判不了**。

## 三、总体 B：`btf < 68`（12 条报告 / 17 条拒收）

`btf` 读出 60、62——**比假定的固定开销还小**。与 A 同一个根：68 是从首批记录
量出来的一个数，既不是下界也不是常量。

## 四、总体 C：两点重合的折线（8 条报告 / 16 条拒收）

```
/Sheet6 @ 0x000A09 btf=56 — 2 vertices, all (0.1709, 0.2202)
/Sheet6 @ 0x000C21 btf=56 — 2 vertices, all (0.1565, 0.2202)
```

`btf=56 → vc=2`，且 `+18` 的内联顶点数**与之相符**（否则会先栽在上一道规则）。
也就是说**文件自己声明它是一条两顶点、两点重合的折线**。解码器按
「退化 → 不收」拒掉。

这大概率是**正确的拒收**：零长折线画不出东西。S2 之后它已经不是静默的了。
**建议就停在这里**——除非有人能说出这些点在图上该长什么样。

## 五、S3 的意外收获：第二个静默洞

32 条被拒记录连警告都发不出来，因为起点被别人的认领区间盖住了：

| 盖住它们的家族 | 条数 |
|---|---:|
| `SubRecord0x0010` | 15 |
| `JStyleOverride` | 12 |
| `AttributeFragment` | 5 |

记录链上的记录**互不重叠**（一条的结束就是下一条的开始）。所以一个家族的
`decoded_ranges` 盖住了链上另一条记录的起点，只能是这些家族**按扫描而非按链**
认领字节的结果——与 S5 里 `decode_iglines` 那个滑窗是同一个物种。

后果是：普查的 `claimed` 判据会被扫描型家族的越界认领污染，制造出
**S2 没堵住的第二个静默桶**。它不影响画面（这些记录本来也没画），只影响
「有没有人说出来」。

## 六、结论与建议排序

1. **A 的两个好子总体（24 条，20 条文本可读）** —— 值得做。手法明确：先证
   开销为什么是 100/108 两种（原生 `igTextBox` 的 Save，或语料对账），
   再让解码器认识变体，而不是放宽 `+30 == derived`。
2. **第二个静默洞（32 条）** —— 便宜且结构性。让普查的 `claimed` 只认**链上
   记录**的认领，扫描型家族的越界认领不参与判定。与 S5 同一把尺子。
3. **B（12 条）** —— 与 A 同根，A 解开后大概率一并解释。
4. **A 的负数子总体（15 条）与中间 13 条** —— 现在下不了结论，需要各自的字节取证。
5. **C（8 条）** —— 建议明确判为「正确拒收」，写进文档收口，不做。

## 六之二、追加取证：A 的好子总体是什么（`probe_phase40_igtextbox_tail_variants`）

顺着 §6 第 1 项往下量了一步。开销 100/108 比假定的 68 多出的正好是 **32 与 40 字节**，
而 68 = 头 32 + 尾 36。所以问题是：多出来的挂在哪。

**答案：头没变，尾变长了。** 被接受的 191 条尾巴**无一例外正好 36 字节**；这 24 条的
尾巴是 68 或 76，且多出来的部分结构一致：

```
tail 68  = 36 + 32   多出：u32 + f64 + f64 + u32 + u32 + u32
tail 76  = 36 + 40   多出：同上 + 再一个 f64
```

而且**解码器要的那三个 double 就在它该在的位置上**（紧跟文本，第三个恒为 `1.0`），
读出来有限、在域内。真正拦住这批的只有「`+30` 与 `btf` 推出的长度不等」这一条。

文本本身是决定性的：`"MPag"`、`"℃"`、`"m"` —— **P&ID 上的单位符号**。乱字节凑不出
这三个。

### 候选规则的实测

把「按固定 68 开销从 `btf` 反推长度」换成「相信 `+30`，但要求 payload 装得下文本
与其后的三个 double」：

| 规则 | 接受 | 其中新增 |
|---|---:|---:|
| 今天发行的 | 191 | — |
| 相信 `+30` + 留 24 字节 | **224** | 33 |
| 相信 `+30` + 留 36 字节 | **224** | 33 |

两种余量给出同一个数，而且**一条不丢**（224 − 33 = 191）。结构性检查自己把
`inline` 荒谬的那 15 条挡在外面，不需要再发明一条规则。

### 但 33 条里只有 20 条文本干净

另外 13 条读出来是 `"0-LNG-57602- - \u{3}\u{1}B\0\u{1}\u{1}F\0…"` ——
**文本后面跟着格式游程**。它们的尾长是 40/44/46/52/54，尾部还能看出
`u16 u16 u32` 的重复结构（如 `01 00 01 00 42 00 00 00` / `01 00 02 00 24 00 00 00`），
像是游程描述符。也就是说 `+30` 在这批里数的是**文本 + 游程**的总长，直接当文本
画上去会把二进制糊在图上。

**所以这一刀有个岔路要先定**：只收干净的 24 条需要一条能说清楚的判据（不能是
「看着像文本」——那正是 Phase 39 三次判错的理由）；收全部 33 条会往图上放 13 条
带控制字符的串；或者先去原生 `igTextBox` 的 Save 把游程结构定下来。

## 七、本次没做

- **一行解码器没改。** S3 的定义就是「先归因，再决定做不做」。
- 没有为了让数字好看去放宽 `+30 == derived` 或 `btf >= 68`——那正是 S5 刚
  证过代价的那类动作，且这次**还没有**原生序列化器的证据。
