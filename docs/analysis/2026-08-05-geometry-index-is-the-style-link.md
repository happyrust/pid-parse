# 几何 → 样式链路打通：`index` 就是样式引用，基类块的账也平了

> 日期：2026-08-05
> 范围：`pid-parse`
> 结论类型：**阻塞解除**。样式记录侧升到 native-reader，几何侧为 corpus + fixture ratchet。
> 前置：`2026-08-04-geometry-to-style-link-negative.md`、`2026-08-04-jstyleoverride-points-at-geometry.md`
> 落地：`src/style_link.rs`、`tests/style_link_ratchet.rs`
> 复现脚本（仓外）：`../_ida-probe-plant10-2026-08-05/`

## 0. 一句话

`igLine2d` / `igPoint2d` / `igLineString2d` 的 `index`（payload `+14`）**就是样式引用**。
它命名的是**同一个文档**的 `StyleCluster` 里的一个样式 id；那条记录要么直接是
`0x002E JStyleSimpleLine`，要么是 `0x0030 JStyleOverride`，后者的 `+22` 再指向
`JStyleSimpleLine`。四张图 558 条可绘制记录**全部**据此拿到线宽与颜色，零未解析。

`index` 曾经是 §8.1 排除表里的第 3 号候选。**排除它的测试有两个 bug。**

## 1. 旧测试错在哪

`examples/probe_geometry_style_link.rs` 判负的依据是「`index` 的取值在不在
`0x002E` 样式 id 集合里」，DWG-0201 得 0/24、工艺管道得 212/218，于是记为巧合。

**（一）作用域。** 一个 `.pid` 不是一个文档。根存储有自己的 `Sheet*` 与
`StyleCluster`，每个 `JSite<n>/` 是**自带 `StyleCluster` 的嵌套子文档**，而**样式 id
每个文档从 1 重数**。那个探针把所有名字含 `style` 的流汇成一个 id 集合、所有
`Sheet` 汇成一堆几何，于是拿根文档的线去对 JSite 的 id 表。混域既凭空造出命中，也
掩盖真命中。

**（二）判据。** 它只问「是不是一条 `SimpleLine` 的 id」。但线**大多数时候指向的是
一条 `JStyleOverride`** —— 正确答案在这个判据下算 miss。DWG-0201 的 0/24 就是这么来
的：那 4 个 index 全部指向 Override。

顺带说明为什么「命中率」这个判据本身就弱：样式 id 在每个文档内是 1..N 的**稠密**区
间（实测密度 79%–97%），所以任何范围内的小整数都能命中。同一份输出里
`sub_type_word` 在 DWG-0201 拿到 24/24、在工艺管道拿到 0/218，而它是个**恒为 16 的
常量** —— 这就是命中率判据的噪声水平。

## 2. 换一个判据：看它落到哪一**类**样式

按文档分域之后，问的不是「命中没有」，而是「落到的样式类别对不对」。

| 几何族 | `index` 指向 | 四图共计不同取值 | 零假设概率（最强一张） |
|---|---|---:|---|
| `igTextBox` | **`JStyleTextPara`** | 58/58 | `5.2e-12` |
| `igLineString2d` | **`JStyleSimpleLine`** | 15/15 | `1.0e-04` |
| `igPoint2d` | **`JStyleSimpleLine`** | 12/12 | `4.1e-03` |
| `igLine2d` | **`SimpleLine` 或 `Override`** | 13/13 | `2.3e-08` |

零假设是「`index` 是个无关的小整数，恰好落进 id 空间」，此时它命中类别 K 的概率就是
K 在该文档样式记录里的占比；按不同取值连乘（同一取值的多条记录不是独立抽样）。

**98 个不同取值，没有一个落错类**——没有文字指向填充样式，没有线指向文字样式。

### 自带的阴性对照组

`igSymbol2d` 的 `+14` 在四张图里**恒为 16**，而且每张图落到不同类别
（`SimpleFill` / `TextChar` / `SimpleLine` / `TextChar`），p 在 0.05..0.39 之间，不显著。

原因查清了：`sheet_records.rs` 自己的注释写明 `igSymbol2d` 的 `14..T-5` 是
「variable sub-fields」——**它根本没有 `index` 字段**。探针在那里读的是没定义的字节，
结果就是噪声。同一个探针、同一批数据、同一个偏移，**它能跑出阴性**，所以另外四个族
的一致性不是探针写死的。

## 3. 第二跳：`+22`

线大多指向 Override，所以还差一跳。用同样的列扫描法（就是当初找到「Override 的 `+50`
指向几何」的那个手法）扫 `StyleCluster` 里 Override 的每个 u32 列：

| 持有者 | 记录数 | `+22` 的内容 |
|---|---:|---|
| **`JStyleOverride`** | 48 | **`SimpleLine` 44、`SimpleFill` 4** |
| `TextChar` / `TextPara` / `SimpleLine` / 其余五族 | 670 | **全为 0** |

670 条非-Override 记录全是 0，48 条 Override 全是非零**且全部解成合法的本地样式 id**。
巧合不会在别处恰好全部归零。

## 4. 全链与产出

```text
几何记录 payload +14 (u32)
   └─ 在它自己那个文档的 StyleCluster 里查这个样式 id
        ├─ 落在 0x002E SimpleLine → 线宽 +34 (f64·米)、颜色 +50 (COLORREF)
        └─ 落在 0x0030 Override   → 它的 +22 命名一条 SimpleLine → 同上
```

四张图 **558/558**（`decode_iglines` / `decode_igpoints` / `decode_iglinestrings`
接受的全部记录）走通，零未解析。全语料只解出 **9 种**线宽×颜色组合：

| 线宽·颜色 | 条数 | |
|---|---:|---|
| 0.350mm `#000000` | 179 | ISO 128 |
| 0.130mm `#000000` | 182 | ISO 128 |
| 0.100mm `#000000` | 107 | 非档位——**全是点**，0.1mm 是绘图最细线惯例 |
| 0.700mm `#808000` | 39 | ISO 128，主工艺管线 |
| 0.100mm 蓝 / 绿 | 28 | 点 |
| 0.350mm `#808000` / 0.180mm `#008000` / 0.350mm `#FE0060` | 23 | ISO 128 |

调色板跨图**语义稳定而数字不同**：0.350mm 黑在四张图都是 `id=1`；0.700mm 橄榄色的主
管线在四张图分别是 id 28 / 76 / 18 / 34。这正是真链路该有的样子——若是巧合，数字变了
语义不会跟着对齐。

## 4b. 文字：同样两跳，换一个字段

`igTextBox` 的 `index` 指向 `0x002D JStyleTextPara`，但字高在
`0x002C JStyleTextChar` 的 `+42`（native-reader），所以中间还差一跳。

它不可能是基类的 `+22`——那个字段在 237 条 `TextPara` 上全为 0。所以引用在类字段里，
用同一套列扫描找：

| 偏移 | 命中 | 指向 |
|---|---|---|
| **`+38`** | **237/237，每个文档都是** | **`JStyleTextChar`** |
| `+73` | 94/237 | 混合 |
| `+1`（未对齐） | 83/237 | 混合 |

全链跑完，116 条文字（`decode_igtextboxes` 接受的那批）拿到真字高，取值全落在制图
档位上：

| 字高 | 条数 | |
|---|---:|---|
| 3.175mm | 64 | 1/8 英寸，最常见 |
| 2.500mm | 26 | ISO 3098 |
| 1.500mm | 10 | ISO 3098 |
| 2.464 / 3.500 / 2.032 / 2.540mm | 16 | 磅值与英制档 |

**渲染器此前把每一条文字都写成固定的 ISO 2.5mm**，也就是说整张图大部分字号偏小 27%。

### 顺带推翻 Phase 35-D 的一个读法

`2026-07-26-phase35d-igtextbox-style-id.md` 认为 `igTextBox` 12 字节 trailer 的末 4
字节是跨图稳定的样式 id。当时没有解出来的样式表可以对照，现在有了：同一个值在四张图
里分别落到 `LineTerminator` / `SimpleLine` / `TextChar` / `Override` / `PointSymbol`，
还夹着 `218103808`、`3002759231` 这类大数。

它观察到的**分组**是真的（21 ≈ 常规标注、56 ≈ 中文、64 ≈ 管道号，跨三张图稳定），
但那个值**不是这个 id 空间里的样式 id**。这和 §2 的 `igSymbol2d` 是同一种形状：值稳定
不等于值有这个语义。字高不需要它。

## 5. 基类块的字节账（本轮同时结掉的悬案）

`docs/pid-format-guide.md` §6 标着一个三方矛盾：本表说 `B = 26`、数原生 `DoIO` 得 14、
真 fixture 字节得 12。**三个数都是对的，只是在量不同的东西。**

### 5.1 原生侧读完了

`JStyleBase__ReadCommonFields`（`sub_10079CE0`）的 load 路径就是四个连续读：

```text
DoIO(2, scratch+18)   DoIO(4, scratch+20)   DoIO(4, scratch+24)   DoIO(4, scratch+28)
```

合计 **14 字节**，scratch 落点连续无填充，所以流里也连续。两个字段的语义由周围代码
直接给出：

- **第一个（u16）是 dash 索引**。`JStyleBase__LoadV3Block` 按
  `(w & 7) != 0 ? (w & 7) + 10 : 0` 映射到成员字节 60。这与
  `2026-08-04-jstylesimpleline-native-reader-confirmed.md` 独立得到的「成员字节 60 =
  dash 索引，按线宽默认 11 或 13」互相印证。
- **第四个（u32）是一个惰性解析的对象引用**。加载器拿它和 `this+18` 存的 id 比，一旦
  不同就释放 `this+16` 缓着的对象指针、存下新 id。**这就是 resolver，而且它在基类里**，
  所以每个样式族都有一个。

顺带封掉一条错误指引：`LoadV3Block` 里那个 `(*this + 184)` 虚调（slot 46）**不读流**。
它只拿到对象和一个 scratch 槽位、**拿不到 IOContext**，且只在存盘位（`a2+24 & 1`）时
执行——它是存盘路径上把成员值取出来填进 scratch 的 getter。

### 5.2 把这个四字段块在 payload 里滑一遍，位置唯一

判据用第四个字段的语义：**引用字段的非零值必须命名另一条记录**。

| 候选起点 | 引用字段落在 | 非零数 | 命名另一条记录 |
|---|---|---:|---|
| +2 / +4 | +12 / +14 | 718 | 0% |
| +6 / +8 | +16 / +18 | 0 | — |
| +10 | +20 | 48 | 0% |
| **+12** | **+22** | **48** | **100%** |
| +16 / +18 / +20 | +26 / +28 / +30 | 600+ | 0% |

只有一个候选能过，且 48/48 全中。于是：

```text
+0..11   12 字节 prologue（在类的 Load 之前）
+12  u16   dash 索引
+14  u32   记录自己的身份          ← 因为是基类字段，才会跨全部样式族唯一
+18  u32   718 条全为 0
+22  u32   JStyleBase 的对象引用    ← 只有 Override 填它
+26        类专属字段开始           ← 即 guide 的 B = 26
```

**26 = 12 + 14。** guide 的 26 是「类字段的起点」，原生数出的 14 是「基类块本身」，
实测的 12 是「基类块之前的 prologue」，也正是 `JStyleOverrideDecoder` 那个 18 字节
扩展头减去 6 字节信封的部分。

### 5.3 于是两个偏移升级

- **`+14` = 记录自己的身份，等级 native-reader**。它跨全部样式族唯一，是因为它是基类
  字段而不是每族各自的字段。
- **`+22` = `JStyleBase` 唯一的对象引用，等级 native-reader**。它**不是** Override 的
  专属槽位——每个样式族都有，只是这四张图里只有 Override 填了。

第 3 节那个「Override 是一排样式槽位」的说法应当作废，换成这一条：**样式体系内置了一层
引用，解析逻辑写在基类里**，`+22` 就是那一层。

## 6. 落地

`src/style_link.rs`：`DocumentStyleTable::from_stylecluster_bytes()` 走一条
`StyleCluster` 链，`resolve_line_style(id)` 走完两跳。三个防坑设计：

- `stylecluster_path_for_sheet()` 把作用域写成结构约束，第 1 节那个 bug 写不出来了；
- 样式表只收录文档化的 10 个样式族，特别是**排除 `0x005A JStyleLibrarian`**——它是链首
  第一条，宽容收录会让它的 `+14` 遮掉一个真样式 id；
- 分帧错位的宽度直接拒掉（非 normal 浮点或超 100mm），不往上报。

`tests/style_link_ratchet.rs` 钉三层：每图每族记录数、direct/override 分流、零未解析；
以及整个 9 项调色板作为一个值断言——分帧一动，调色板会变长变怪，而光看计数看不出来。

## 7. 已知缺口

**version 2 那条路的账还没平。** `JStyleSimpleLine` 是 v2，上一轮数它的基类 helper 只
得 8 字节，但 `12 + 8 = 20`，而它的类字段实测从 `+30` 开始（`+34` 的线宽在 558 条记录
上给出干净的 ISO 调色板）。要么 v2 基类块当时漏数，要么 v2 的 prologue 不同。不影响
现有结论，但是根线头。

**几何侧仍是 corpus。** 没有反编译代码显示原生渲染器读几何的 `+14` 去查样式表。样式
记录侧已经是 native-reader，几何侧靠的是第 2 节的类别一致性 + fixture ratchet。

**`igSymbol2d` 与文字的字高不在本轮范围内。** 符号没有 `index` 字段；文字的 `index`
指向 `TextPara`，要拿字高还得再走一跳到 `TextChar`。

## 8. 一条方法论备注

本轮第一版定位脚本有个自引用缺陷：它用 payload `+14` 建 id 集合，又拿候选起点 `+4` 的
引用字段（恰好也是 `+14`）去查该集合，于是 718/718 命中——**那是恒真式，不是证据**。
改成「必须命名另一条记录」重跑才得到 §5.2 那张表。

这和 §7.1 那个被推翻的锚点、以及 `index+14` 的 212/218 是同一类陷阱：**一个数字很漂亮
的时候，先问它有没有可能不漂亮。**
