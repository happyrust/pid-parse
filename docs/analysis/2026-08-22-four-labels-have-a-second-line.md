# 四条标签有第二行：`+66` 行距该接，但接之前先量出来的那组数才是本轮的产物

> 日期：2026-08-22
> 阶段：文字保真收口 —— **行距 `+66` 已接线**（见 §5）
> 证据等级：字段读序 **native-reader**（`style.dll!sub_100337A0`）；本轮新增的
> 是**语料计数**，产物 `examples/probe_text_multiline_census`
> 前置：`docs/analysis/2026-08-13-text-para-layout-and-justification.md` §三

## TL;DR

`JStyleTextPara +66` 的读序早就有了，取值 `{0.0: 8, 1.0: 332, 1.5: 36}`，形状就是
行距倍数。上一轮的结论是「单行标签用不上，多行才显现，**暂不接线**」——那句话里
藏着一个从没有人量过的前提：**这套语料里到底有没有多行标签。**

量完了，有，但只有一点点：

- 全语料 **235 条 `igTextBox`**，其中 **4 条（1.70%）文本里带换行**；
- 换行符是 **`U+000D` 单独一个 CR**，没有 LF，也没有任何别的控制字符；
- 这 4 条其实是 **2 条不同的标签**（一个 4 行图签、一个 2 行注释），都在
  `DWG-0202GP06-01` 上，因为该图在语料里发布了两份而各数了两遍。

**真正让这个字段值得接的不是那个 4，是它和 `+66` 的对齐关系：**

| | `+66 = 1.0` | `+66 = 1.5` |
|---|---|---|
| 单行 | **228** | 3 |
| 多行 | **0** | **4** |

**每一条多行标签都声明 1.5；声明 1.0 的 228 条里一条多行都没有。** 一个字段只在
它声称管的那件事也变化的地方变化，这不是巧合——这比「取值像行距」强得多，也是
本轮唯一新增的证据。

顺带查出来一件更要紧的事：**这 4 条标签今天在 `OpenCADStudio` 里是画错的**，而且
错法跟行距无关（见 §4）。

## 〇、本文每一个数都是按**两跳口径**量的

`style_link` 走的是 `igTextBox +14` → `JStyleTextPara +38` → `JStyleTextChar`。
本文的行距取自那条链上的**段落**记录，字高取自它指到的**字符样式**。

**这个口径本身正在被质疑。** 同期 t-42（opus-5-23）查出：形状 2 的 `igTextBox`
记录自己还带一条 run，直指另一条 `JStyleTextChar`——215 条里 153 条两者不是同一条
样式，122 条不一致里 116 条字高或字体真的不同（run 侧是非整数实测值如 2.2931mm，
para 侧是标称值如 3.1750mm），而原生把 run 交给 `AddCharStyleRun`，那才是真正上
格式的调用。**尚未定论**，读序只证明 run 被逐区间应用，没读到渲染端的取舍规则。

对本文结论的影响，分两层，得分开说：

- **行距本身不受影响。** 行距是**段落**属性，run 是**字符样式**区间；`AddCharStyleRun`
  换掉的是字形，不是行与行之间的距离。`+66` 无论如何都只能从段落上读。
- **但拿它算出来的行距 pitch 会受影响。** 消费侧的行间距是 `字高 × 行距`，而那个
  字高是两跳口径的。若将来改成 run 优先，这 4 条标签的字高会变，pitch 跟着变，
  **OCS 的 `字高 × 1.5` 断言要重量**。ratchet 里的 151/3/2 也是两跳口径下的计数。

本轮按边界不动两跳逻辑，也不回头改口径——先把这句话写在这里，接手的人一眼能看出
哪些数要重量。

## 一、口径，以及它可能怎么被推翻

「多行」在本轮的定义是：**解码出的文本里含有一个断行码点** —— `U+000A`、
`U+000D`、`U+000B`、`U+000C`、`U+0085`、`U+2028`、`U+2029`。除此之外的全部 C0
控制字符单独计数，这样一个本表没收录的断行写法不会被悄悄归进「单行」——实测
其他控制字符 **0 条**，所以这条兜底没有被触发。

这个口径有一条已知的可能被推翻的路。`igTextBox` 形状 3 在文本之后挂 `A + B` 个
格式化 run（见 `2026-08-13-igtextbox-has-three-shapes.md` §五），而一个把富文本
建模成 run 的厂商，**同样可以把段落断行建模成一个 run 而不是字符串里的一个字符**。
真是那样的话，一条标签可以视觉上是多行、而文本里一个断行码点都没有，本轮就会把
它记成单行。

所以形状交叉表是要一起看的：

```
 shape    records   multi-line
     1         14            0
     2        208            4      ← 全部 4 条都在这里
     3         13            0      ← 存疑的那 13 条
```

**存疑面是 13 条（5.5%）**，全部 4 条已知多行都落在形状 2——也就是不带 run 的那
一档。所以「多行是用字符表达的」这个读法在它自己的地盘上是成立的；形状 3 会不会
另有一套，要等富文本 run 那条线（**另有其人在做，本轮不碰**）给答案。

## 二、不依赖解码器的证伪线

如果解码器拒收了某些文本记录，「解码出来的文本里没有换行」就可能只是拒收造成的
假象。所以 probe 另跑一条不走解码器的扫描：对链上**每一条** `0x004D` 记录的
payload，按偶数对齐扫全部 u16，看有没有断行码点。

实测：**链上 235 条，解码器接收 235 条——没有缺口**，这条证伪线因此没有派上用场
（它报 210/235 命中，是预期中的大幅过计：一个 double 的字节完全可能拼出 `0x000A`，
所以它只有报 0 的时候才有意义）。denominator 没有洞，是本轮结论能站住的前提。

## 三、语料计数

```
=== igTextBox labels: how many have more than one line? ===
chain 0x004D records:  235
decoder-accepted:      235
multi-line records:    4 / 235  (1.70%)
break code points seen: {"U+000D": 8}
other control chars:    {}
lines per record:       {1: 231, 2: 2, 4: 2}
```

四条多行标签的原文：

```
1、污油池上放空管线高度应大于5m。\r2、阻火器电伴热带从根部缠至地面以上2m。
安3集气站\r排污单元\r污油池\r管道及仪表流程图
（以上两条各出现两次：DWG-0202GP06-01 在语料里发布了两份）
```

按图分：

| fixture | 标签 | 多行 | `+66 ≠ 1` |
|---|---|---|---|
| DWG-0201GP06-01 | 59 | 0 | 3 |
| DWG-0202GP06-01 | 56 | **2** | 2 |
| 工艺管道及仪表流程-1 | 58 | 0 | 0 |
| D06 | 4 | 0 | 0 |
| A01（publish） | 2 | 0 | 0 |
| DWG-0202GP06-01（publish） | 56 | **2** | 2 |

**声明 1.5 却只有一行的 3 条**全在 `DWG-0201`：一条 `人孔`，两条纯空白。行距落在
单行标签上是**空转，不是错**——所以按实测原样钉住，不去替它编一个解释。

**没有任何标签引用 `+66 = 0.0` 的段落。** 那 8 条 `0.0` 记录躺在样式表里没人引用，
所以「0.0 读作未声明」这个取舍对本语料零成本。

## 四、接之前先发现的一件事：这 4 条今天就是画错的

`OpenCADStudio` 把每条标签导入成**一个 DXF `TEXT` 实体**，而 `TEXT` 按定义是单行
的；`entities/text_support.rs` 的 `text_local_bounds` 用**一个水平游标**遍历
`text.chars()`，没有任何换行处理。`U+000D` 在描边字体里没有字形，于是走
`None => cursor_x += 6.0` 那条分支。

**所以那 4 条标签今天渲染成一整行**：图签的四行「安3集气站 排污单元 污油池
管道及仪表流程图」首尾相接横着铺出去，每处断行只留一个空档。这跟行距对不对无关
——它在读到 `+66` 之前就已经错了。

这件事反过来定了本轮接线的形状：**只把 `+66` 读进来是没有消费者的**。行距要有意义，
标签得先真的排成多行。两件事分不开，所以一起做了（§5 OCS 侧）。

## 五、接线结果

**`pid-parse`**：新增 `TEXT_PARA_LINE_SPACING_OFFSET = 66`，`StyleRecord` 与
`ResolvedTextHeight` 各多带一个 `line_spacing: Option<f64>`，走**已有的**两跳链，
不新建索引表——与字高、颜色、对齐、字体同一条 join。两处取舍：

- 它取自**段落**记录，和对齐同理（行与行之间的距离属于 run 不属于字形），所以
  一跳形状下为 `None`。
- **合理区间取 `0.25..=4.0`**，这不是我们定的：那是 DXF 给 MTEXT 行距因子
  （group 44）的取值范围，也正是消费侧会把它填进去的那个字段。语料的 `1.0 / 1.5`
  稳稳在里面；语料的第三个值 `0.0` 按构造落在外面——零倍行距会把每一行摞在第一行
  上——读作「未声明」，调用方保留自己的默认。

**`OpenCADStudio`**：新增 `stack_text_lines`，在样式应用**之前**把带断行的标签拆成
每行一个 `TEXT`，沿基线法向按 `字高 × 行距` 逐行下移。三个细节：

- 作用域与 `apply_text_height` / `apply_text_colour` / `apply_text_alignment`
  一致，**只管图纸自己在 `PID-TEXT` 上的文字**；符号内部文字来自 `.sym` 库，既无
  段落样式也无断行。**既有 apply_* 的图层门禁一个都没有放宽。**
- 拆在样式应用之前，所以每一行都照常各自领到字高、颜色、对齐、字体，不需要为
  多行另开一条样式路径。
- 位移走**基线法向**而不是垂直向下：语料的标签在 0°/90°/180° 都有，竖排标签要是
  往下摞就自己压自己。
- 段落没声明可用行距时按单倍摞。没有声明的消费者本来也只能假定单倍，而**不摞**
  才是唯一确定错的选项。

**回归测试**两侧各钉一头。`pid-parse` 的 `style_link_ratchet` 钉的不是分布而是
**对应关系**——`{(单行,1.0): 151, (单行,1.5): 3, (多行,1.5): 2}`，一旦出现
`(多行, 1.0)` 就是偏移读错了；偏移错**也**能产出某个分布，但产不出一个和「哪些
标签真的有第二行」对得上的分布。OCS 侧钉四行图签确实落成四个实体、行间距恰为
`字高 × 1.5`，另加一条全语料断言：**没有任何标签带着画不出来的控制字符进图**。

## 六、顺带查实的一处 join 碰撞

写 ratchet 时对不上一个数：本测试数到 156 条标签，而同文件其它几条钉的是 155。
差的那一条是真的，不是取整——`工艺管道及仪表流程-1.pid` 的 `/Sheet6` 上有**两条
`igTextBox` 记录共用 oid 6345**。`TextHeightIndex` 以 `(stream, oid)` 为键，于是
两条塌成一条，第二条静默继承第一条的样式。

两条都声明 1.0、都不是多行，所以对本轮测量零影响，已在 ratchet 注释里钉住。但
**这个键在本语料里不是唯一的**，这一点此前没有任何地方写过，谁下次拿它做 join
都会踩到。

## 七、本轮登记不做

- **形状 3 的格式化 run**（13 条）——§一那条口径风险的出处，**是别人的活**，本轮
  按边界不碰。
- **垂直对齐 `+36`**（恒为基线）、**kind 2 的额外 32/40 字节**——与行距无关，状态
  同 08-13。
- `+42 / +50 / +58 / +74 / +82` 那五个度量——除 `+82` 有 6 条 `0.000508`（0.02″）
  外恒为 0，没有消费者，不接。
