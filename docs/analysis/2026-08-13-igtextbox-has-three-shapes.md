# igTextBox 有三种形状，我们只实现了其中一种：45 条记录、43 条真标签回到图上

> 日期：2026-08-13
> 阶段：Phase 40 收尾（改解码器，有行为变化）
> 证据等级：**native-reader**（`radsrvitem.dll` 的 `igTextBox` Load）
> 产物：`examples/probe_phase40_igtextbox_subtypes`（前次会话遗留在工作树、未提交）
> **撤回**：`2026-08-12-a01-refused-text-has-no-lettering-behind-it.md` 结论作废，见 §4

## TL;DR

`igTextBox`（PSM `0x004D`）不是一种记录，是**三种**。payload `+18` 的 `u16` 是形状
判别位，**每种形状把文本长度放在不同偏移**：

| 形状 | 判别位 | 长度 @ | 文本 @ | body 长度 |
|---:|---:|---|---|---|
| 1 | `1` | `+22` | `+24` | `2 + 2*count` |
| 2 | `2` | `+30` | `+32` | `10 + 2*count` |
| 3 | `3` | `+26` | `+28` | `6 + 2*count + 8*(A+B)` |

我们的解码器**只实现了形状 2**——它是常见的那个（260 条里占 215），于是另外
45 条被整族拒收，不是因为它们畸形，而是因为解码器去形状 2 的偏移找它们的长度。

实现三种形状之后：

| | 之前 | 之后 |
|---|---:|---:|
| 被接受的 `igTextBox` | 215 | **260**（全族，零拒收） |
| graphic refused（ratchet 五图） | 53 | **13**（只剩折线与一条 `0x00FA`） |
| 解出真字高的文字 | 134 | **155** |

45 条新记录里 **43 条带可读标签**——形状 1 有 30/32，形状 3 有 13/13。

## 一、原生证据

`radsrvitem.dll` 的 `igTextBox` Load 是 `sub_56498C00`，尺寸辅助是 `sub_5646D450`。
本轮用 idalib 从另一条路独立复现了判别位：发布例程 `sub_564468B0`（唯一引用字符串
`"igTextBox"` 的函数之一）在 `*a2 != 77` 校验之后，按 `a2[12]`（`_WORD*` 索引 12 =
字节 24）三路分派：

```c
if ( a2[12] != 1 ) {
    if ( a2[12] != 2 ) {
        if ( a2[12] != 3 ) return -2147418113;
        v5 = sub_56447730(a2);  v6 = *(WORD*)(v5 + 4);  v7 = v5 + 6;
    }
    v8 = sub_56447710(a2);      v6 = *(WORD*)(v8 + 8);  v7 = v8 + 10;
}
v9 = sub_56449240(a2);          v6 = *v9;               v7 = v9 + 1;
v10 = 2 * v6;   // UTF-16
```

三个辅助函数各自校验判别位后都返回 `this + 14`（字节 28），调用方再按形状在
不同偏移读长度。字节 24 = payload+18（记录头 6 字节），与 Load 侧一致；形状 2 的
字节 36/38 = payload+30/+32，正是我们一直在用的那套——**这解释了为什么只有形状 2
能解开**。

## 二、语料验证

`probe_phase40_igtextbox_subtypes` 对链上全部 260 条 `0x004D` 记录套用原生公式：

- **套不上的：0 条**；
- **形状 2 的冗余计数（`+22` 处 `count | 0x10000`）与 `+30` 不符的：0 条**；
- 三种形状的 body 之后，**尾块一律 36 字节**（插入点 2 个 double + 方向 2 个 double
  + 4 字节尾），与 `2026-08-13-igtextbox-rotation-is-a-direction-pair.md` 的发现一致。

## 三、这同时解释了前两轮的现象

- **「尾巴变长 32/40 字节」**（`2026-08-12-igtextbox-overhead-is-a-floor-not-a-constant.md`）：
  那不是尾巴变长，是**形状 3 的 body 里含 `8*(A+B)` 字节的 double**，`A+B` 为 4 或 5。
- **方向校验拒掉的 9 条**：它们是形状 3，方向对被那些 double 挡在后面，读到的自然
  不是单位向量。校验本身没错，病因诊断错了——不是长度超读，是形状没实现。
- **`btf = 60 / 62` 的记录**：形状 1 空文本的最小 payload 是 `22 + 2 + 36 = 60`，
  它们被 68 这个**形状 2 的**地板挡在外面。地板已改为 60。

## 四、撤回：A01 那 18 条背后**有**字

`2026-08-12-a01-refused-text-has-no-lettering-behind-it.md` 判定 A01 的 18 条被拒
记录「0/18 有可读文本」，据此登记为阴性结论、建议不要再挖。**那是错的。**

错在测量方法：那次去 `+32` 读文本——**形状 2 的偏移**——而这 18 条是形状 1 和 3，
它们的文本在 `+24` 或 `+28`。用错的偏移当然读不出字。实现形状之后，A01 的
`PID-TEXT` 从 9 条涨到 **27 条**（含 6 条竖排）。

教训与前一天判错旋转角是同一个：**在证明「这里没有东西」之前，先确认自己是在正确
的位置上看。** 阴性结论比阳性结论更需要交叉验证，因为它会让人停止寻找。

## 五、改了什么

- 新增 `igtextbox_body_shape(payload, sub_type) -> (count, text_start, body_len)`，
  一处集中三种形状的布局；
- `decode_igtextbox_payload` 改为按形状取文本、并从 `22 + body_len` 起算尾块
  （形状 2 恰好仍等于 `text_end`，所以它的行为逐字节不变）；
- 形状 2 额外校验 `+22` 的 `count | 0x10000` 与 `+30` 一致（格式自带的冗余，白拿）；
- 新增 `SheetIgTextBoxDecoded::text_sub_type`；
- 地板常量 `IGTEXTBOX_MIN_PAYLOAD_LEN = 60` 取代 `IGTEXTBOX_PAYLOAD_OVERHEAD` 作为
  尺寸门；后者保留原名，注释改为「形状 2 的固定开销」。

## 六、下游

`OpenCADStudio` 零改动：多出的 45 条 `Text` 实体自动落到 `PID-TEXT`，各按自己的
字高与旋转排版。DWG-0201 的字高表里第一次出现 **6.350mm（1/4 英寸，标题字号）**
和 1.524mm——这两个尺寸此前从未在任何图上出现过，因为携带它们的记录一条都没解开。
