# `0x00FA` 尾部的自描述块

> ## ⚠ 2026-08-04 晚间重大修正 —— 先读这一段
>
> PSM `type_code → CLSID` 表已被正确定位（见
> `2026-08-04-psm-type-code-registry.md`），结果推翻了本文标题原本的判断：
>
> - **`0x00FA` 不是 "GraphicGroup"，它是 `imagdex.dex` 的 "Dependency Object"。**
>   pid-parse 现有的 `GraphicGroup / GraphicPersist` 命名是未经证实的假设，应改。
> - 这解释了第 3 节里那两个 OID 引用（`+22` 与 `+34`）：**它们是一条依赖关系的两端**，
>   不是「对象 + 它的图元」。
> - 因此第 3–5 节把尾部四个小整数词读作「每对象显示属性」的假设**大概率是错的**，
>   更可能是依赖关系的元数据。第 9 节担心的方向被证实：`0x0077` 在 PSM 表里是
>   **"Fix Constraint"**，与 `ig*` 类表的 `igFixRelation2d` 互相印证。

> **仍然成立的**：第 7 节那个自描述长度前缀 trailer 是纯字节结构证据，两图逐桶一致，
> 与记录叫什么名字无关。第 6 节「符号学不在几何图元里」也仍然成立。
>
> **不再成立的**：把 `+50/+54/+58/+62` 当作线型/线宽候选。线宽/颜色的候选现在只剩
> `0x005A`（= **"JSL Style Librarian"**，style.dll），与字高同一个阻塞点。
>

## 1. 为什么看这里

`docs/analysis/2026-08-04-annotation-families-risk.md` §6 已经用字节账排除了几何图元：
`igLine2d`（50 字节）与 `igPoint2d`（34 字节）都是定长且字节全额入账，**没有任何空位
放线宽/颜色/线型**。排除法之后只剩两个地方，`0x00FA GraphicGroup` 是其中之一，而且
它是全语料出现次数最多的族（458 次），payload 过了 offset 18 就一直保持 raw。

## 2. 方法

按 `(bytes_to_follow, group_kind_word)` 分桶，只比较同形状的记录，然后**逐列**读：
一个在几十条记录里从不变化的列是格式写死的常量，变化的才是数据。再把每个 4 字节窗口
拿去和「本 Sheet 实际定义的 OID 集合」比对，把引用和取值分开。

## 3. 主桶 `btf=66 group_kind=2` 的结构

这是最大的一桶：DWG-0201 有 64 条（占该图 GraphicGroup 的一半），工艺管道有 34 条。
两张图**互相独立**——不同项目、不同幅面（A2 / A1）、不同语言。

尾部 48 字节（payload `+18..+66`）逐窗口对照：

| payload 偏移 | DWG-0201（n=64） | 工艺管道（n=34） | 判读 |
|---|---|---|---|
| `+18` | `{0, 0x10000}` | 常量 `0x00010000` | |
| **`+22`** | **REFERENCE 60/64** | **REFERENCE 28/34** | 几何引用 |
| `+26` | `{0xFFFB0000, 0xFFFB0001, 0xFFFF0001}` | `{0x10001, 0xFFFB0000, 0xFFFB0001}` | |
| `+30` | `{0x1FFFB, 0x1FFFF}` | `{0x10001, 0x1FFFB, 0x1FFFF}` | |
| **`+34`** | **REFERENCE 64/64** | **REFERENCE 34/34** | 几何引用 |
| `+38` | 常量 `0x00040000` | 常量 `0x00030000` | 每图常量 |
| `+42` | 常量 `0x00770000` | 常量 `0x00770000` | **跨图同一常量** |
| `+46` | 常量 `0x00100001` | 常量 `0x00100001` | **跨图同一常量** |
| **`+50`** | `{0, 1, 2, 4, −1}` | `{0, 1, 2, −1}` | **属性候选** |
| **`+54`** | `{0, 1, 3, −3, −1}` | `{0, 1, −3, −1}` | **属性候选** |

两个 `0x00770000` / `0x00100001` 常量在两张无关图纸上逐比特相同，说明分桶分对了，
列是对齐的。

## 4. 决定性测试：属性还是类型标签

一个显示属性会在**同族对象之间**变化；一个类型标签不会。把四个候选词对
`+34` 指向对象的族做交叉表：

```
DWG-0201  +50 PROPERTY  igPoint2d={-1,0,1,2,4}
          +54 PROPERTY  igPoint2d={-3,-1,0,1,3}
          +58 PROPERTY  igPoint2d={0,1,5,7}
          +62 PROPERTY  igPoint2d={0,2}
工艺管道   +50 PROPERTY  igPoint2d={-1,0,1,2}
          +54 PROPERTY  igPoint2d={-3,-1,0,1}
          +58 PROPERTY  igPoint2d={0,1,5,7}
          +62 PROPERTY  igPoint2d={0,1,2}
```

`+34` 在这一桶里**100% 指向 `igPoint2d`**（64/64 与 34/34），而四个词在这个单一族内
仍然各自取多个值 → **它们是每对象属性，不是类型标签。**

## 5. 支持「显示属性」的旁证

- **`+58` 的值域 `{0,1,5,7}` 在两张无关图纸上完全相同**，且落在 IGDS / MicroStation
  线型编码的 `0..7` 区间内。
- `+50` 与 `+54` 都带 `−1`（`0xFFFFFFFF`），`+54` 还带 `−3`。`−1` 在 IGDS 里是
  「ByLevel / 继承」的惯用哨兵值。
- `radsrvitem.dll!sub_564BB990`（igDimension 的第一级 reader）读取符号学的形状是
  `&0x0F` 取一个 4 位字段、`(>>4)&3 + 1` 取一个 2 位字段、再展开约 16 个位标志。
  说明 IGDS 符号学确实是「小整数枚举 + 哨兵」这种形态。

## 6. 尚未证明的部分（不要跳过）

1. **这一桶只包住 `igPoint2d`。** 线和文字的符号学在别的桶里（`btf=104`/`98`/`154`/
   `170`/`200` 等），列布局不同，本文没有对齐它们。**「线宽在哪」严格说还没定位**，
   本文定位的是「每对象属性块存在，且在 GraphicGroup 尾部」。
2. **四个词各自是什么，没有证据。** 「`+58` 是线型」目前只是值域吻合，属于
   corpus-statistical，达不到 native-reader 等级。要提升需要：
   （a）在 IDA 里找到写出 `0x00770000` / `0x00100001` 之后那四个字的 writer/reader；
   或（b）拿一张已知线型/线宽的 controlled fixture 做对照。
3. **不要**在这两条之一落实之前就把任何一个词命名为 `line_style` 写进 DTO——那正是
   Stop-And-Challenge 第 6 条禁止的无据 promotion。

## 7. 定位锚：不是固定偏移，是自描述长度前缀

第 6 节列的第 1 项已经做了，结果比预期好：**`0x00770000` 不是通用锚点**（它在
`btf=44 / 52 / 68 / 98 / 104 / 122 / 164 / 200` 等桶里根本不出现）。但对齐这些桶时
发现了真正的结构——**每条记录都以一个自描述的长度前缀块收尾**：

```text
<block_type: u16>  <selector: u16>  <len: u16>  <len 字节的块>
                                                └── 一直到记录末尾
```

判据：在 tail 里正向找第一个满足 `descriptor_offset + 6 + len == tail_end` 且
`len >= 4` 的位置。（必须正向找并要求 `len >= 4`：记录尾部是零，从后往前找会被
一个 `len=0` 的退化描述符命中。）

两张无关图纸在**每一个共有桶形上给出完全相同的描述符**：

| btf | kind | block_type | selector | len | 描述符 @payload | DWG-0201 | 工艺管道 |
|---:|---:|---|---:|---:|---|:-:|:-:|
| 44 | 1 | `0x0007` | 1 | 8 | +30 | ✓ n=10 | ✓ n=9 |
| 52 | 2 | `0x0007` | 1 | 8 | +38 | ✓ n=3 | — |
| 54 | 1 | `0x0077` | 2 | 12 | +36 | ✓ n=8 | ✓ n=10 |
| **66** | **2** | **`0x0077`** | **1** | **16** | **+44** | **✓ n=64** | **✓ n=34** |
| 68 | 4 | `0x0007` | 1 | 8 | +54 | ✓ n=2 | — |
| 76 | 5 | `0x0007` | 1 | 8 | +62 | — | ✓ n=1 |
| 98 | 2 | `0x0007` | 1 | 48 | +44 | ✓ n=3 | ✓ n=12 |
| 104 | 2 | `0x0007` | 1 | 48 | +50 | ✓ n=12 | ✓ n=19 |
| 110 / 116 | 2 | `0x0007` | 1 | 48 | +56 / +62 | ✓ | ✓ |
| 120 | 1 | `0x0007` | 1 | 48 | +66 | — | ✓ |

**两种块类型分工清楚：**

- **`0x0077`**（len 12 / 16）：小整数词，就是第 3–5 节那个每对象属性块。
  `btf=66` 那桶的 16 字节 = 4 个词，即 `+50 / +54 / +58 / +62`。
- **`0x0007`**（len 8 / 48）：48 字节 = 6 个 `f64`，且列分析里 `+71 / +79 / +87 / +95`
  恒为 `3F`（`0.x` 量级双精度的高字节）。**更像 range / 变换矩阵，不是符号学。**

所以属性块**有了与记录长度无关的定位方式**：读最后 `len` 字节，再按 `block_type`
分派。这一条已经可以支撑解码器的定位逻辑，不需要按 btf 写死偏移表。

**一个已知瑕疵**：正向首匹配在工艺管道的 `btf=66` 桶里命中过一次伪描述符
（`type=0x01FF selector=45568 len=29 @+31`）。把 `block_type` 限定在实测集合
`{0x0007, 0x0077}` 内即可排除，但这属于需要写进解码器的约束，不是可以默认的。

## 8. 一次失败的取证尝试（记下来免得再走）

想从二进制侧给 `0x0077` / `0x0007` 定名，走了一条**错路**，记在这里免得后人重复。

**假设**：`radsrvitem.dll` 里那张 CLSID 数组是 PSM `type_code → CLSID` 表，
16 字节槽、按 type code 索引；于是 trailer 的 `block_type` 可以直接查表定名。

**做法**：找到 Phase 16 已知的控制 GUID `47FCC338`（= `JStyleOverride`，PSM `0x0030`），
用 `base = offset(control) − 0x30 × 16` 反推基址，再按 index 查。

**为什么错**：控制项通过是**循环论证**——基址就是从控制项反推的，任何 GUID 放在
那个位置都会「验证通过」。真正的检验是查一个独立的已知项，而它没通过：

> `0x004D` 必定是 `igTextBox`（pid-parse 全语料解出 260 条，带内联 UTF-16 文本），
> 但这条链查出来是 `stylecnv.dex` 的 **"JSL Convert Hole Processor Solid Fill Style"**。
> 显然不是。

**结论**：`radsrvitem.dll` 那张数组确实是 CLSID 数组，但**不是按 PSM type code 索引
的**（或者基址不对、或者根本是另一张表，`dword_5667B068` 需要重新定位）。本节
先前基于它得出的一切 type-code → CLSID 对应**全部作废**，工具也已删除。

**教训**：从控制项反推基址、再用同一个控制项验证，是无效验证。必须用**第二个
独立已知项**（这里就是 `0x004D = igTextBox`）做检验。

## 8b. 一个真实且可复用的收获：CLSID → 类名注册表

同一轮里找到了 `JUTIL.dll`（本机在 `D:\pid\RADInstallA~\jutil.dll`，`dlls/` 里没有），
它就是 Phase 16 用过的 RAD CLSID 注册表。结构是 96 字节条目的平铺数组：

```text
  +0   GUID   16 字节
  +16  char[] 实现模块，NUL 补齐到 16 字节
  +32  char[] 友好名，NUL 结尾
```

**独立验证**：`47FCC338-2D0F-11D0-A1FF-080036A1CF02` → `style.dll` /
**"JSL Override Style"**，与 Phase 16 发表的结果逐字一致。

已封装成 `tools/clsid_registry.py`，支持按 GUID 查、按名字 `--grep`、以及
`--self-test` 跑控制项。**这一条与第 8 节的失败无关，可以放心用**——它是
「GUID → 名字」，不依赖任何 type-code 索引假设。

拿两个 block type 的 CLSID 去查（**注意：这两个 GUID 本身来自第 8 节那条作废的链，
所以下面这两行只是记录，不构成 block type 的定名**）：

## 9. 一个必须正视的反面可能

`ig*` 类表 `sub_56448F70` 里 **`0x0077` = `igFixRelation2d`**（一个参数化约束）。
如果 trailer 的 block type 与 `ig*` 类号是同一套编号，那么 `0x0077` 块就是**约束
数据而不是显示属性**，第 3–5 节的解读就要推翻。

支持「不是同一套编号」的旁证：三个 CLSID 的版本位不同代（igPoint2d 是 `11CD`、
igLine2d 是 `11D3`、`0x0077` 是 `11CE`），且 `ig*` 类表与 PSM CLSID 表是两张独立的
表、两种索引用途。

支持「就是显示属性」的旁证仍然成立：值在**同一族对象之间**变化（64/64 与 34/34 全
指向 `igPoint2d`）、`+58` 值域 `{0,1,5,7}` 两图完全一致且落在 IGDS 线型区间、
`+50`/`+54` 带 `−1`/`−3` 哨兵。

**这条歧义只能靠拿到类名来消。** 在那之前，第 3–5 节的读法是**最佳假说而不是结论**，
不得据此命名字段。

## 10. 建议的下一步

1. **重新定位真正的 PSM `type_code → CLSID` 表。** 判据已经有了：查 `0x004D` 必须
   得到 `igTextBox`、查 `0x0030` 必须得到 `JStyleOverride`——**两个都对**才算找对表。
   Phase 16 的笔记指向 `radsrvitem.dll!dword_5667B068`，需要在 IDA 里重新确认这个
   符号的实际地址与元素宽度，而不是像第 8 节那样从控制项反推。
2. 表定位对了之后，用 `tools/clsid_registry.py` 把 block type 的 CLSID 转成类名，
   消除第 9 节的歧义。这是唯一能把证据等级提到 native-reader 的路。
3. 独立于以上：确认 `0x0007` 的 48 字节块是不是 6 个 `f64` 的 range——如果是，
   那是一个不受定名歧义影响的收获（每对象包围盒）。
4. 以上任一坐实之后再考虑 promotion，配 fixture ratchet 与 byte-audit movement。
