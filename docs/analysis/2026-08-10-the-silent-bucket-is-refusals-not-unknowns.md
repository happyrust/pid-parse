# 静默桶是「被拒收」，不是「未知类型」

> 日期：2026-08-10
> 范围：`pid-parse`（普查 + 诊断）+ `OpenCADStudio`（报告）
> 结论类型：**四分账普查**——每条链上记录归入唯一一个桶，先证伪再下结论
> 前置：`2026-08-04-annotation-families-risk.md`（原生图形谓词）、
> Phase 38 S2（未解码族从静默丢弃改为具名警告）、
> Phase 39 S4/S5（严格记录链，撤回 `0x3FE6` 幽灵家族）
> 工具：`examples/probe_phase40_render_gap_census`

## 0. 一句话

图纸内容丢失有两条路，这个仓库两个 phase 只堵住了其中一条。**被报告的那条只占
丢失量的 3.4%**：全语料 5 条「无解码器」被具名警告，而 **141 条「有解码器、被该
解码器拒收」一个字都没有**。

## 1. 为什么会漏掉一整类

`undecoded_type_code_census` 的判据是：

```rust
if !claimed_here && !DECODED_TYPE_CODES.contains(&type_code) { count }
```

一条**「类型码有解码器、但这些字节被该解码器拒了」**的记录，两个条件都不满足：
它不在任何 claimed 区间里（所以不算已解码），它的类型码又在 `DECODED_TYPE_CODES`
里（所以不算未解码）。它同时掉出解码输出和普查，无人计数、无人警告。

函数自己的注释把这称作「另一种诊断」（*a different diagnostic*）——**而 crate 里
没有任何地方发出那种诊断。**这正是 Phase 38 S2 立意要终结的失败模式，当时只堵了
一半。

## 2. 四分账：每条记录的去向

`probe_phase40_render_gap_census` 走同一条链走查，把每条记录归入唯一一个桶：

| 桶 | 含义 | 全语料 | 今天谁在说话 |
|---|---|---:|---|
| claimed | 解码器收了字节 | 1511 | 正常上屏 |
| **REJECTED** | **解码器存在，拒了这些字节** | **141** | **无人。完全静默** |
| warned | 无解码器，原生谓词说它该画 | 5 | 具名警告（S2） |
| quiet | 无解码器，谓词说它不画 | 2 | 按设计静默 |

静默桶按族分：

| 类型码 | 类 | claimed | **REJECTED** | 占该族比例 |
|---|---|---:|---:|---:|
| `0x0018` | Line Object | 326 | **88** | **21%** |
| `0x004D` | Text Object | 215 | **45** | **17%** |
| `0x0084` | LineString Object | 161 | **8** | 5% |
| 其余各族 | — | 809 | 0 | 0 |

对照报警桶的全部内容：`0x0020 Rectangle` 4 条、`0x007B Group` 1 条。

## 3. 先证伪：它们真的是记录吗

Phase 39 的 F 项就栽在扫描伪命中上——候选集由校验规则自己定义，再回头观察类型码
一致，是恒真式。所以这里先用**同一把尺子**反过来验：把 141 个被拒偏移去对
`sheet_record_starts` 的严格记录链（走不通整条流就返回空，不退化成扫描）。那正是
当初判定 `0x3FE6` 三条「记录」不在链上、从而撤回整个家族所用的判据。

**141/141 全在链上，零条脱链。** 逐流看：

| 流 | 链长 | 被拒在链上 | 脱链 |
|---|---:|---:|---:|
| DWG-0201 `/Sheet6` | 359 | 4 | 0 |
| DWG-0202 `/Sheet6` | 274 | 5 | 0 |
| DWG-0202 `/Sheet6615` | 5 | 4 | 0 |
| 工艺管道-1 `/Sheet6` | 563 | 21 | 0 |
| A01 `/JSite204/Sheet6` | 111 | 98 | 0 |
| publish 副本 ×2 | — | 9 | 0 |

另外，探针对每个被拒偏移直接调发行版的 `decode_igline_at`：**0 次分歧**。普查说被拒
的，解码器确实拒。

## 4. 为什么被拒：不是未知形状，是第二种帧装

被拒与被收的 `0x0018` **声明长度完全一致，都是 50 字节**。逐条复算 `igLine2d` 的
四道校验，**88/88 只栽在第一道：`remaining_header != 12`**。与坐标、退化、非有限值
全无关系。

两个总体：

| 总体 | 数量 | `type_flags` | `remaining_header` | 标准偏移上读出的坐标 |
|---|---:|---|---:|---|
| A01 `/JSite204/Sheet6` | 80 | 0 | **8** | (19.9, 394.8) → (19.9, 369.9) mm，一条 24.9mm 竖线 |
| DWG-0202 `/Sheet6615` | 8 | 2 | **6996** | (126.3, 92.4) → (253.8, 92.4) mm，一条 127.5mm 横线 |

两者在标准偏移上都读出合理的页面坐标（米制）。**但这一条只记为弱判据**：「看着像
真的」正是 Phase 39 三次判错的那种理由。坐标是否真在那个偏移上，要由
`radsrvitem` 的 `igLine2d` 序列化器来定，本轮没做。

## 5. 集中度：两个流几乎全黑

- **A01 `/JSite204/Sheet6`：111 条记录被拒 98 条（88%）。** 这张图在 OCS 里一共只画
  27 个实体，此前读作「这张图本来就空」。
- **DWG-0202 `/Sheet6615`：5 条记录，拒 4 警 1，整个流一个像素不画。**

## 6. 本轮做了什么

**只把静默变成警告，不动任何解码规则。** 拒收本身是对的——解码器去猜一个未知帧装
会画出虚构的线；静默才是错的。

| 仓 | 改动 |
|---|---|
| `pid-parse` | `undecoded_census` 新增 `refused_record_census` + `RefusedRecordCount`；两个普查抽出共用的 `unclaimed_counts` 走查，从结构上保证它们**划分**未认领记录而不是各测各的 |
| `pid-parse` | `SheetGeometry.refused_records`、`NormalizedPidGeometry.refused_graphic_records`，措辞与「无解码器」明确分开 |
| `pid-parse` | 新增 `tests/render_gap_census.rs`：语料计数棘轮（4/9/21/0/98）+ 具名不变式 + 两种措辞不得混同 |
| `OpenCADStudio` | `report_import` 把被拒收的图形记录按名报出 |

## 7. 那 80 条线属于图纸吗：属于，而且它们是 A01 的图框

A01 的 80 条在 `/JSite204/Sheet6`——一个 `JSite`（`SmartPlant` 的符号实例容器）内的
sheet。合理的担心是：那是**符号局部几何**，已经由某个 `igSymbol2d` 摆到页面上了，
再解码一遍就是重复绘制或画错坐标系。按 Phase 39 S3 的规矩，**先证消费者，再谈解码**。

`examples/probe_phase40_jsite_sheet_is_page_content` 取四条互相独立、任何一条都能
单独否掉结论的读数：

| # | 读数 | 结果 |
|---|---|---|
| 1 | 这条流已经是页面内容来源吗 | **是。** `/JSite204/Sheet6` 今天已经有 7 条记录被接受并画在 A01 的页面上；这不是假设 |
| 2 | 一个坐标系还是两个 | **一个，就是页面的。** 被拒的线张成 `x 0.0000..594.0000 mm`、`y 0.0000..420.0000 mm`；同流被接受的记录（20.0..548.2、89.2..380.3）落在这个框里 |
| 3 | JSite204 是符号定义吗 | **不是。** 它 `symbol_name` / `symbol_path` 皆为 `None`；同文件的 JSite1229（`Flanged Nozzle.sym`）、JSite206（`Horizontal Drum.sym`）才是真符号，且都不含 Sheet 流 |
| 4 | 会不会重复绘制 | **不会。** 顶层 sheet 上仅有的两条 `igSymbol2d` 分别指向 JSite1229 与 JSite206，**没有一条指向 JSite204** |

第 2 条还给出一个意料之外的强信号：**80/80 全部轴对齐**，最长一条恰为 594.0mm（页宽），
四角精确落在 `(0.0000, 0.0000)`–`(594.0000, 420.0000)`——与边框声明的页幅逐位相符。
**错帧的字节凑不出一个精确的页面矩形。** 这 80 条是图纸的**边框与图框网格**。

由此顺带解释了症状：A01 在 OCS 里只画 27 个实体、看着像一张空图，**是因为它的边框
就在这 80 条被拒记录里**。

这条同时把 S5 的风险降了一档：坐标确实在标准偏移上（否则不会落成页面矩形）。但
`remaining_header` 到底是什么、两个总体是不是两个版本，仍需原生序列化器来定——
本文不据此放宽任何校验。

## 8. 明确没做、也不该顺手做的

- **没有解第二种 `igLine2d` 帧装。** `remaining_header == 8` / `== 6996` 各自是什么，
  要 `radsrvitem` 原生序列化器定字段语义。那是独立一刀。
- **没有查 45 条 text 与 8 条 linestring 的拒收原因。** 只对 88 条线做了规则归因。
  文字占静默桶三分之一，病因未知就无法排序。
- **没有查 DWG-0202 `/Sheet6615` 那 8 条的归属。** 它在顶层流、不在 JSite 里，
  `type_flags` 也与 A01 那批不同，是另一个总体，需要自己的取证。
- **没有把 `0x3FE6` 从 `DECODED_TYPE_CODES` 里摘掉。** S5 撤回了那个家族，但解码器
  仍在（只是从不接受任何东西），留在表里不影响分账；全语料 0 条命中。

## 9. 复现

```powershell
cargo run --example probe_phase40_render_gap_census            # 四分账、证伪、规则归因
cargo run --example probe_phase40_jsite_sheet_is_page_content  # §7 四条读数
cargo test --locked --test render_gap_census                   # 语料棘轮与具名不变式
```
