# 文字颜色在 `JStyleTextChar +34`：已由原生读序坐实

> 日期：2026-08-13
> 阶段：文字样式补完（改解析 + 改渲染，有行为变化）
> 证据等级：**native-reader**（`style.dll!sub_10030A20`，见 §4）
> 产物：`examples/probe_text_colour_candidate`、`examples/probe_text_char_layout`
>
> **§4 已更新（同日稍后）**：本文最初以 corpus 级发布，明说没拿到原生读序。
> 后来拿到了——序列化器是 `sub_10030A20`，读序把 `+34` 夹在两个已知的
> native-reader 锚点之间且字节账精确闭合。等级随之升到 native-reader，
> 顺带解释了「`-1` 哨兵」为何在盘上一个都见不到，并定位了字体名。

## TL;DR

`.pid` 导入的每一条标签此前都渲染成 `PID-TEXT` 图层的绿色——那是本导入器自己发明的
颜色，因为没有任何代码读过文字颜色。格式指南把 `0x002C JStyleTextChar +34` 列为候选，
等级 hypothesis，措辞是「带 `-1` 哨兵；形状符合文字颜色」。

实测把这句话推翻了一半、坐实了另一半：

```
 count  w/ hgt  value at +34
   367     355  0x00000000  #000000
     6       6  0x000000FF  #FF0000
     4       4  0x00404040  #404040
     2       2  0x006000FE  #FE0060
     2       2  0x00A0FE00  #00FEA0

sentinel (-1): 0/381          reads as a COLORREF: 381/381
```

**一个 `-1` 哨兵都没有**，而 **381 条全部读成合法 `COLORREF`**。已接线。

## 一、为什么这不是又一个漂亮的命中率

`CONTEXT.md` 的纪律要求 corpus 级结论不能直接接线（`GLine2d` 与 `JStyleOverride`
锚点两次撤回都栽在命中率上）。这一条的支撑是**结构性**的，不是统计性的：

1. **24 位约束。** 381 条记录的高字节**全为零**。一个不受约束的 `u32` 每条约有
   1/256 的机会高字节为零；381 条全中的概率在 `10^-920` 量级。这个字段在构造上就是
   24 位的——`COLORREF` 正是如此。
2. **跨族佐证。** `#FE0060` 不是随便一个值：**同一张图的线条也用它**
   （`OpenCADStudio` 的 `tests/pid_import.rs` 钉着 DWG-0201 的线条调色板含
   `" 35 #FE0060", 3`）。一个不相干的 `u32` 不会正好落在本图的非常规线色上。
3. **格式自洽。** 两个兄弟样式族用同样的方式存颜色：`JStyleSimpleLine +50`
   （native-reader）与 `JStyleSimpleFill +30`。第三个样式族携带同编码的 `COLORREF`
   是格式在自我一致。
4. **取值是调色板。** 367 黑 + 红 / 灰 / 品红 / 青绿，黑压倒性多数——正是 P&ID
   排字的样子。

## 二、指南那句「-1 哨兵」错了

全语料零个 `-1`。那句话大概来自把填充色的 `0xFFFFFFFE`「未设」哨兵套到了这里，
或者来自另一个版本的语料。本文以实测为准，指南 §8.2 已随之更新。

哨兵不存在这件事有个实际后果：**黑色是被声明的颜色，不是"没声明"**。367 条记录
明确写着 `#000000`。若把黑当成缺省而回退到图层色，等于把绝大多数标签又变回绿的。
`style_link` 因此只在高字节非零时才拒收。

## 三、屏幕上会看到什么

- 已解析索引里 **155 条**（走通两跳且字高可用的那些）：**153 黑 + 2 红**。
- 黑字在深色背景上由渲染器的 `adapt_to_bg` 翻成白色——和图纸自己的黑色线条待遇
  完全一致（DWG-0201 有 96 条线本来就是 `#000000`）。所以可见的变化是
  **标签不再是绿色**，加上少数图纸刻意着色的标签显出真色。
- 走字高兜底的记录同时也拿不到颜色，保留图层色。DWG-0201 上是 48 条里的 1 条——
  正是那条指向 0.254mm 被拒字高的记录。**颜色和字高同生共死，因为它们共用一次 join。**

## 四、原生读序：`style.dll!sub_10030A20`

第一轮从 DoIO 调用点反推没找到（vtable 虚函数无一直接调 DoIO）。**换成从接口
get/put 对入手就成了**——这正是当初定位填充色用的手法：`IJStyleTextCharImp` 的
vtable（`0x100a1c4c`）里那些 21–24 字节的小函数就是访问器，它们暴露出对象槽位
`+276`、`+316`、`+348`…，再回头找哪个 DoIO 调用者喂这些槽位，序列化器就浮出来了：
**`sub_10030A20`**。

读序（`jengine_1075(stream, size, ptr)` 即 DoIO）：

```text
  sub_10003814(...)         基类公共字段
  +26  u32
  +30  u16   语言 / 键盘布局   ← 读到 0 时 GetKeyboardLayout(0) 兜底
  +32  u16
  +34  u32   字符颜色
  +38  u8 x4
  +42  f64   字高，单位米
  +50  u16 / +52 u16 / +54 u32 / +58 u8 x6 / +64 u16 / +66 u8 x2
  +68  u16   字体名长度（UTF-16 码元数）
  +70  ...   字体名
```

**为什么这坐实了 `+34`**：`+30` 与 `+42` 是**此前就已记为 native-reader** 的两个偏移，
而它们之间的读取把每个字节都用掉了——`30 + 2 + 2 + 4 + 4 = 42`，**精确闭合、零余量**。
颜色只能在 `+34`。

## 四之二、「`-1` 哨兵」的真相：它永远写不到盘上

指南那句「带 `-1` 哨兵」不是凭空来的，原始代码里确实有，只是被读反了：

```c
if ( *(_DWORD *)(this + 356) == -1 && (*(_BYTE *)(a2 + 24) & 1) != 0 )
    *(_DWORD *)(this + 356) = 0;              // IO 之前
v3 = jengine_1075(a2, 4, this + 356);
if ( *(_DWORD *)(this + 356) == -1 && (*(_BYTE *)(a2 + 24) & 2) != 0 )
    *(_DWORD *)(this + 356) = 0;              // IO 之后
```

`-1` 是**内存里**的「未设」值，序列化器在两个方向上都把它归一化成 `0`。所以
**盘上永远看不到 `-1`**——这正是实测 381 条零个 `-1`、367 条为 `0` 的原因。

对本仓的实现有一个推论：把 `0` 当黑色读，与原生行为**完全一致**（原生也是把未设
归一化成 0 再按黑渲染）。那 367 条里混着「作者选了黑」与「未设归一化为黑」，
两者在渲染上不可区分，也无须区分。

## 四之三、顺带定位了字体名

读序走到底就是 `+68` 的 u16 计数与 `+70` 起的 UTF-16 正文，于是
`payload == 70 + 2*count`。`examples/probe_text_char_layout` 全语料验证：

- **381/381** 条 payload 精确等于 `70 + 2*count`（读序把每个字节都交代了）；
- `+70` 处读出的是真字体名，**零条不可读**：`Arial` 111、`Arial Narrow` 108、
  `宋体` 79、`仿宋` 26、`仿宋_GB2312` 25、`SimSun-ExtB` 15、`Braggadocio` 4、
  `Intergraph ANSI` 1。

指南里「字体名字段的确切偏移：用最长 UTF-16 串启发式读的，未定位」这条缺口就此关闭。
之前那个启发式扫出的 `"\u{d00}દ╆ɵ㽪"` 之流，是它在整个 payload 上乱扫的结果。

**一个已知边角**：8 条记录的名字读作 `ËÎÌå`——那是 `宋体` 的 GB2312 字节
（`CB CE CC E5`）被逐字节拓宽成 UTF-16 的结果，厂商写窄字符串进宽缓冲时没转码。
另有 4 条 `匪_GB2312` 同理。占 381 条里的 12 条，未处理。

## 五、改了什么

- `style_link`：新增 `TEXT_CHAR_COLOUR_OFFSET = 34` 与 `read_text_colour`（高字节非零
  即拒）；`StyleRecord` 多一个 `text_colour`；`ResolvedTextHeight` 多一个
  `colour: Option<u32>` 与 `rgb()`。**没有新建第二张索引表**——颜色与字高走的是同一
  条两跳链，同一次 join 取回。
- `OpenCADStudio`：新增 `apply_text_colour`，作用域与 `apply_text_height` 相同（只管
  `PID-TEXT`）。**没有放宽 `apply_symbology` 的图层门禁**——那个门禁是有意的，
  `PID-CONNECTIVITY` 的诊断色不能被图纸颜色覆盖。
- ratchet：`style_link_ratchet` 增 `text_reaches_the_colour_its_character_style_states`；
  OCS 增 `lettering_carries_the_colour_the_drawing_states`。

## 六、命名欠账

`ResolvedTextHeight` 现在同时携带颜色，名字窄了一号。改名会动 `OpenCADStudio` 的公开
调用点，**未获授权，留作建议**：`ResolvedTextStyle` 更贴切。
