# `remaining_header` 不是长度，是 PSM 信封的 `aux` —— 一条我们自己发明的校验

> 日期：2026-08-11
> 阶段：Phase 40 S5
> 来源：`radsrvitem.dll` 反编译（IDA 实例 `idalib-280240`）+ 全语料实测
> 上游：`docs/analysis/2026-08-10-the-silent-bucket-is-refusals-not-unknowns.md`（S1）、
> `docs/plans/2026-08-10-phase40-render-gap-recensus-cn.md`

## TL;DR

S1 量出 88 条 `igLine2d` 被拒，全部只栽在 `remaining_header != 12` 一道规则上。
S5 去原生序列化器求这个字段的语义，结论是：

**它根本不是字段布局的一部分，而是 PSM 通用信封 18 字节头里那 8 字节
`aux` 的高半段。写侧无条件写它，读侧读进一个再也不看的局部变量。
`== 12` 没有任何格式依据——是本 crate 自己发明的，并且在两个 phase 里
悄悄扔掉了 88 条真实的线，其中包含 A01 整张图的图框。**

没有「第二种帧装」。只有一种帧装，和一条写窄了的校验。

## 一、写侧：`PSMSerializeOut` (`0x56491E80`)

主路径按顺序写四段，然后才把流交给类自己的 `Save` 虚函数：

```c
// 1. type code (2 bytes)
(*write)(stream, &v40, 2, 0);
// 2. bytes_to_follow 占位 (4 bytes, magic 929325410)
v38 = 929325410;
(*write)(stream, &v38, 4, 0);
// 3. oid (4 bytes) —— v6[1]
(*write)(stream, v6 + 1, 4, 0);
// 4. aux (8 bytes) —— v35 与 v36 这一对
(*write)(stream, &v35, 8, 0);
// 5. 类的 Save 写 inner payload
v27 = (*(...)(*(_DWORD *)v37 + 20))(v37, ...);
```

### 第二条写路径把这个头逐字节拼了出来

当调用方装了 `*(a1 + 36)` 那个回调时，同一个函数改为在内存里拼头再交出去。
这段代码把 18 字节布局写死在了偏移上（`v19` 是 `_WORD *`）：

```c
*v31              = v40;      // +0   u16  type code
*(_DWORD*)(v19+1) = v33 + 12; // +2   u32  bytes_to_follow
*(_DWORD*)(v19+3) = v6[1];    // +6   u32  oid
*(_DWORD*)(v19+5) = v35;      // +10  u32  aux_lo
*(_DWORD*)(v19+7) = v36;      // +14  u32  aux_hi
```

**两条路径互为独立证据**：PSM 记录头是 `2 + 4 + 4 + 4 + 4 = 18` 字节，
其中最后 8 字节是一对 u32。类自己的 payload 从记录 `+18` 开始。

### `aux` 从哪来：对象记录的台账，不是几何

```c
v35 = 0;
v36 = 0;
if ( (*((_BYTE *)v6 + 14) & 0x40) != 0 ) {
    if ( *((_BYTE *)v6 + 25) == 0xFF ) { v17 = 1; v16 = *((_BYTE *)v6 + 28) == 1; }
    else                               { v17 = 0; v16 = *((_BYTE *)v6 + 26) == 1; }
    if ( v16 ) {
        if ( v17 ) { v35 = *(int *)((char *)v6 + 34); v36 = v6[10];               }
        else       { v35 = v6[8];                     v36 = *(int *)((char *)v6 + 38); }
    }
}
```

- **默认是 `(0, 0)`**。只有对象记录 `+14` 的 `0x40` 标志置位、且一个字节等于
  `1` 时，才从记录的 `+32/+38` 或 `+34/+40` 取两个 int 填进去。
- 取哪一对由 `+25 == 0xFF` 决定。**两种取法都存在**，这本身就说明 `aux`
  的两个槽在不同情形下装的是不同东西。
- 它来自**对象记录的台账字段**，与被序列化的几何类无关——`igLine2d`、
  `igTextBox`、`igLineString2d` 走的是同一段代码。

## 二、读侧：`PSMSerializeIn` (`0x564915E0`) 读完就扔

```c
v3 = sub_5647AFB0(v5, &v36, 2);    // type code
v3 = sub_5647AFB0(v38, &v40, 4);   // bytes_to_follow
v35 = sub_56491050(v38);           // 记住 payload 起点
v3 = sub_5647AFB0(v7, &v37, 4);    // oid

if ( v32[0] || *(this + 5) ) {
    v30[0] = 0;
    (*(...)(*(_DWORD *)*v9 + 12))(*v9, v30, 8, 0);   // 读 8 字节进 v30
}
// …… v30 在整个函数里再也没有出现过
```

读进来的 8 字节**没有任何一处被检查、比较或使用**。函数后面所有的校验是：

| 校验 | 对象 |
|---|---|
| `v37 != *(_DWORD *)(v46 + 4)` | oid 与对象记录内的 oid 一致 |
| `(WORD)v36 != ((*(_DWORD *)(v46+8) >> 6) & 0x3FFF)` | type code 与记录的类型一致（不一致时走 guidtab 链查） |
| `v40 != v20 - v35` | bytes_to_follow 与实际消耗一致 |

**没有一条碰 `aux`。** 一个读侧读完即弃的字段，不可能承担帧装判据。

> 顺带：那 8 字节的读是**条件性**的（`v32[0] || *(this+5)`）。这是流级模式而非
> 逐记录差异；本语料所有记录都是 18 字节头，模式是开的。若模式关闭，
> `bytes_to_follow` 一致性检查会立刻报 8 字节的差。

## 三、这条校验当年是怎么来的

`docs/analysis/2026-05-14-radsrvitem-psm-serialize-bytes.md` 的
「igLine2d 字节布局已揭示」一节写得很诚实：

```
8..11   u32   remaining_header = 0x0C = 12  (常量, 推测下面的 sub-header 长度)
```

括号里就是「推测」。它来自 **fixture 字节 dump**，不是反编译——那一节的标题
本身写着「无需 IDA 反编译」。**第一批看到的记录恰好都是 12，于是常量成了规则。**

同一份文档还留了一句现在看很刺眼的话：`A01: 0 (没有 0x0018 records)`。
A01 有 80 条，只是全被这条规则拒了，所以当年的探针一条也没看见。

## 四、为什么不能一删了事：那条规则在兼职当防伪命中门

`decode_iglines` 走的是 `PsmRecordDecoder::scan`——**逐字节滑窗**。而兄弟家族
`decode_primitive_lines`（`GLine2d`）自 Phase 39 的 `e5ef8fb` 起已经是
**按记录链**走的。对滑窗来说，`aux_hi == 12` 是这个家族唯一真正在挡东西的规则。

所以正确的动作不是「放宽」，是**换尺子**：把一条发明的字段规则，换成兄弟家族
已经在用、且 S1 用来证实那 141 条真实性的那个结构性不变量。

## 五、换尺子的代价与收益（实测）

`examples/probe_phase40_igline_chain_vs_rule`：

```

  其中落在记录链外                :   0
链门控 + 规则保留                 : 326      ← 一条不少，链门控零代价
链门控 + 规则去掉                 : 414      ← +88
```

| 流 | scan | 链外 | 链+规则 | 链−规则 |
|---|---:|---:|---:|---:|
| `DWG-0201/Sheet6` | 24 | 0 | 24 | 24 |

## 六、落地后三条独立读数印证「它们本来就是记录」

换尺子之后，三处**没有为此调整过**的既有断言各自给出了肯定：

1. **golden 快照纯新增**：`+5456` 行插入，**零删除**。只多收，没有任何既有记录
   被挤掉或改写。
2. **样式链接全部解析**：`tests/style_link_ratchet.rs` 断言「没有一条解析不出
   样式」。新进来的 4 条 `DWG-0202/Sheet6615` 记录，其 `index` 全部在本文档的
   `StyleCluster` 里解析成功（`direct` 74 → 78）。乱字节的 `index` 不会全中。
3. **调色板没长出第十项**：4 条全部落在既有的 `0.350mm #000000`（179 → 183）。
   0.35 mm 黑正是矩形轮廓该有的线重。

加上 S4 已经证过的那条：A01 那 80 条 `80/80 轴对齐`、四角逐位落在
`(0,0)–(594.0000, 420.0000) mm`。

## 七、这次没做，也不该顺手做

| 项 | 为什么 |
|---|---|
| 重命名 DTO 的 `parent_ref` → `aux_lo` | 本次只证明了 `aux_hi` 不是长度。`aux_lo` 取自对象记录的 `+32/+34`，「父引用」这个读法既没被证实也没被证伪，改名等于换一个同样没证据的名字。已在文档里注明它是信封字段而非几何字段 |
| 动 `igBoundary2d` 的同款 `aux_hi == 12` | 同一个概念错误，但 `0x0013` 家族**没有做过**这次的测量。原样保留，并在常量注释里写明它是待测量的语料规律而非格式要求 |
| 解释 `aux` 到底装的是什么 | 需要跟 `+32/+34/+38/+40` 那些对象记录字段，属于 PSM 台账而非几何。当前没有消费者 |
| 给 `aux_hi` 的三个取值编故事 | `8`/`12`/`6996` 的分布是观察，不是解释。测试把它钉成「只允许这三个值」，新值出现要重新看，而不是默默放行 |
