# `PSMspacemap` 是「谁引用我」的反向索引：181 不是 `parent_ref`，方向整个反了

> 日期：2026-08-27
> 范围：`pid-parse`
> 结论类型：**corpus（四图全部 space map 条目 × 全部记录链的 join，无抽样）**
> 前置：`2026-08-27-psmspacemap-is-the-object-reference-graph.md`（同日，方向被本文推翻）、
> `2026-08-27-the-spacemap-tag-is-not-a-type-code.md`（同日，角色被本文倒置）
> 含**两处推翻**：①「成员是出边、tag 是被指对象的类」——方向反了；
> ②「`sub_56495440` 重建路径把记录 payload+4/+8 写成自己的 181/182 成员」——
> 语料 0 命中，这四个文件不是那条路写的。
> probe：`examples/probe_psmspacemap_tag181_is_the_parent_ref.rs`

## 0. 要验的命题

上一轮 IDA 在 `radsrvitem.dll` 里读到一条重建路径：`sub_56495440` 走 cluster 的
记录链，对每条记录调 `sub_564794D0(map, oid, type_word, …, payload+4, payload+8)`，
而 `sub_56479290` 把最后两个参数写成成员、tag 写死 `181` / `182`。当时的读法是：

> 条目 = 记录自己，成员槽 0 = `(payload+4, 181)`，槽 1 = `(payload+8, 182)`；
> 所以 tag 181 就是本仓各记录家族里的 `parent_ref` 字段，182 是 `+8` 那个字。

这个读法跟语料有一处已知的顶撞（该路径成对写 181/182，语料里却是 84 比 519），
所以先验语料再动文档。验法是把两边 join 起来：条目的持久 id 是
`(segment << 13) | index`，记录的 payload+0 是 oid——同一个存储里按同一个数对上。

## 1. 判决：0/84，0/519

| 命题 | 结果 |
|---|---|
| tag 181 成员的 value == 本条目记录的 payload+4 | **0 / 84** |
| tag 182 成员的 value == 本条目记录的 payload+8 | **0 / 519** |

而且不是「差一点」：持有 181/182 成员的那些条目，自己记录里的 `+4`/`+8` 恰恰
**全是 0**。槽位次序也对不上——那条路写 slot0=181、slot1=182，语料里 181 从不在
slot 0（分布在 1..12），slot 0 的 425/519 是 182。

**所以这四个文件的 space map 不是 `sub_56495440` 那条路写的**，它读出来的规则对
这批文件没有效力。（该反汇编本身没读错字节；错的是把它当成了这些文件的写入者。
下一轮 IDA 的复核点见 §7。）

## 2. join 的前提自己先成了一条结论：持久 id 就是 oid

四图 11 个存储、**1948/1948** 条条目，在**自己存储**的记录链里都有同 oid 的记录，
零缺席。记录来源分布（条目侧）：

- `PSMcluster0` / `Sheet*` / `Unclustered Dynamic Attributes` 供给全部条目；
- `StyleCluster`（737 条记录）和 `Dynamic Attributes Metadata` 的记录**从不**带条目；
- `DWG-0202` 的 `Sheet6615`（5 条）也不带。

## 3. 方向：把「谁在 payload 里写着谁」逐字节扫出来

两个方向各扫一遍，问同一个问题——引用到底存在谁的记录里：

- **正向**（旧读法要求的）：member.value 出现在**条目自己**记录的 payload 里吗？
  几乎全空。84 个 181 成员 0 命中；190（1446 个）、249（731）、185（279）、
  188（46）、201（72）、205（8）全部 0 命中；183 也只有零星巧合。
- **反向**：**条目的 id** 出现在 **value 的记录**的 payload 里吗？多数 tag 上是
  100%，而且偏移按记录家族固定：

| tag | value 的记录家族 | 条目 id 在其 payload 的哪里 | 命中 |
|---|---|---|---|
| 190 | `0x0089`（动态属性行）| `+12` | **1446/1446** |
| 249 | `0x00FA` DependencyObject | `+16` / `+22`（6 步长，依赖的两端）| **730/730** |
| 183 | `0x0042` | `+12..+44`（4 步长表）| **357/357** |
| 201 | `0x0013` igBoundary2d | trailer 引用区 `+148..` | **72/72** |
| 185 | `0x0019`/`0x0006`/`0x0085`/`0x0082`/`0x0015`/`0x000F`/`0x006A`/`0x0077` | `+18` / `+22`（八个家族共形）| **279/279** |
| 205 | `0x0079` | `+12` | **8/8** |
| 181 | `0x00CE` igSymbol2d / `0x003D` igSmartFrame2d | `+29` / `+156` | **84/84** |
| 188 | `0x0115` | `+49..+280` 多处 | 42/46 |
| 184 | `0x0057` / `0x0060`（ViewFilterSet）| 多数**无 payload 对应** | 60/366 |
| 182 | 多家族（`0x0067` 列表居多）+ 191 个无记录的 value | 部分有 | 192/519 |
| 261 / 225 | `0x004F` | 少数在 `+14` | 4/45、3/7 |
| 239 | `0x0058` | 少数在 `+14..+34` | 14/29 |

**每个成员是一条入边**：条目是被指对象，value 是引用者，引用本体存在引用者的
payload 里（能存的那部分）。184 这类找不到 payload 对应的，是**只活在这张表里的
应用层登记边**（视图过滤集的成员关系不需要写进谁的记录）。

三件顺手就位的：`0x0089` 动态属性行在 `+12` 指宿主对象（DA 挂接从此有了字节级
锚点）；`0x00FA` 依赖的两端引用坐在 `+16`/`+22`；**igSymbol2d 的 `+29` 是 site
引用**（挨着 `+25` 的样式引用），igSmartFrame2d 的在 `+156`。

## 4. tag 是引用者的类

两个判据合在一起：

1. **表内**（上一篇测的，数字不变）：2415 个作为 value 出现的对象，每个只带一种
   tag，含出现在多条条目上的 675 个，零分歧。
2. **join**：tag 几乎一一对应引用者的记录家族（§3 的表）。一个 tag 盖多个家族的
   只有 185（八个共形家族，同一对偏移）和 181（symbol 与 frame，功能同类）、182
   （列表/容器类）。

上一篇「tag 是被指对象的类」错在方向不在测量——value 换了角色，「跟着 value 走的
tag」就从目标的类变成了引用者的类。`PSMroots` 认出的名字全部保留、角色倒置：
184 = 被 `TopVFSet`/ViewFilterSet 引用，182 = 被 `_SupportOnlyList`/`JSitesList`
这类列表引用，261/225 = 被指向 Server/Imagineer 文档的 `0x004F` 对象引用。

顺带：249 的引用者家族 `0x00FA` = 250，正是之前当巧合毙掉的那个「差 1」。13 对里
只有这一对差 1（181↔206、190↔137 都不沾边），所以仍按巧合记，不当规律用。

## 5. 181↔182 是一对互指，`JSitesList` 顺带破了

- **84/84**：每个持有 `(Y, 181)` 的条目 X，Y 的条目都反过来持有 `(X, 182)`。这是
  语料里唯一成对的 tag（另有 11 个 182 自环）。含义：igSymbol/igSmartFrame 在
  `+29`/`+156` 指它的 **site**，site 以 182 指回。
- **`/JSitesList` 流**：`'OLEM'` magic + `u32 数量` + `u32 id 表`。D06 那份是
  `[23, 204, 300, 336, 1835, 2605, 3644, 145, 151]`——**恰好是全部持有 181 成员的
  条目**加两个 Document site；DWG-0201 那份 20 个 id 与顶层 `JSiteN` 存储名一一对应。
- **四图恒定的引用者 id 2 就是这个列表对象**：它没有 PSM 记录（所以 join 查无此
  oid），它的引用直接存在 `/JSitesList` 流里；`JSite` 条目上的 `(2, 182)` 就是它的
  入边。182 那 191 个「无记录的 value」应多为此类流对象。
- 所以 `JSite` 的一般义是 **OLE 站点**：符号/框架挂在站点上（181/182 互指），
  Server/Imagineer 文档是站点里的两种大号特例。

## 6. 这张表不是全量引用图

- **1401 条记录的 payload+4（本仓叫 `parent_ref`）非零，却一条都不进表**（547 条
  为零）。`0x0003` 等家族的 parent 链完全不被索引——表只登记 §3 那十几种引用。
- 那条唯一的悬空边（`DWG-0201` 顶层 `0x00006000` entry 2 → 369，tag 249）现在能
  讲通了：369 曾是一条 `0x00FA` 依赖记录，**依赖删了、被指对象身上的反指没清**。

## 7. IDA 复核：entry 键就是 oid，写侧那条路只写两个成员

回 `radsrvitem.dll`（`idalib-4200`）把 §0 那条重建路的三个函数逐个反编译，四条都硬：

**（1）entry 键 = 记录自己的 oid。** `sub_564794D0(this, a2, …)` 里 `a2` 就是 oid：

```c
v9  = a2 >> 13;        // 段
v12 = a2 & 0x1FFF;     // 段内 index
… sub_56479290(segment, v12, …)   // 条目建在 index = v12 处
```

所以条目按记录自己的持久 id 建键——**「persist id == oid」不是语料巧合，是读器自己
的算法**。上一轮这个键读对了；错的只是把成员当成了出边。

**（2）这条路只写两个成员，且成对。** `sub_56479290` 写的是个 24/44 字节的**内存
节点**，扩展形式里恰好两个成员：`(payload+4, tag 181)`、`(payload+8, tag 182)`，写死、
成对、永远只有这俩。语料条目最多 27 个成员、13 种 tag——**结构上就不可能**由这条路
生成。

**（3）`sub_56495440` 是重建/压缩例程，不是平常的写入者。** 它 `malloc(0x2400)` 开滑
窗，把一个 cluster 的**整条记录链**流进来逐条重新登记，末尾若作废超过 10%
（`v34 > v30[0]*0.1`）就给文档置脏位。`xrefs` 查无直接调用方——**vtable 间接调用**
（导入 / 修复 / GC 才走）。正常保存的四个文件自然不带它的签名，这正是语料 0/84、
0/519 的由来。

**（4）11 个语料 tag 全部不是硬编码。** 扫全 `.text`：除重建路的 181/182
（`0B5h`/`0B6h`），**没有任何一个其余 tag（183..261）作为成员 tag 立即数写出**（命中
的都是 `[ebp-0B8h]` 这类栈偏移假阳性；两处 `mov edi,105h` 一个是 Win API 的
`nSize`、一个不喂成员写）。即正常写入者把**引用者的类当参数**传进去（从引用对象身上
读），从不烤进代码——正是「tag = 引用者的类」的预期。

**净结果**：§1–§6 的语料方向被反汇编独立坐实。两条写入路径并存——重建路硬编码
181/182（出边、成对），正常路把引用者的类当参数写入边（复用了 181/182 等值）——
所以 181 共 84、182 共 519 本就不该相等。
