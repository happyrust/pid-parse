# 出图驱动把字体变换写成 256 分之几：标题栏的 0.797 和旋转 Arial 的 1.012 是同一条规则

日期：2026-11-11　`main`：`e03c225` 之上

## 结论

验收门禁剩下的 47 条超限标签里，44 条是标题栏里压窄的宋体。它们两边的 `Tf`、字距都相同，只有文字矩阵
`Tm` 的横向缩放不同：参考图写 `0.797`，我方写 `0.8`。

这个数不是 GDI 的，也不是出图程序的，是 PDF 驱动把字体变换写进 `Tm` 时自己的定点算术。规则找到了：

```text
L = trunc(across × 1 250 000)      across：字体垂直于基线方向上，一个设计单位是多少设备单位
Q = L div 256                      整数除法
n = trunc(e × 1 250 000 / Q)       e 取 across 与 along（along = across × 压窄比）
Tm 里写 n / 256，三位小数
```

它复现 11 张参考图上全部 14 个不是 `1 0 0 1` 的文字矩阵——九档压窄的宋体、旋转的宋体、压窄的 Arial `M`、
旋转的 Arial 与 Arial Narrow——没有一个例外。常数 1 250 000 就是手头 5.0.1.9 版驱动同一段代码里的常数。

写出器照这条规则写 `Tm`（`pid-plot/src/write/text_matrix.rs`）之后，超限标签 47 → 3，剩下的 3 条都不是
排字的问题；我方 11 张验收图上每一个非平凡的文字矩阵都与参考图同一档的相同。

## 参考图上的现象

参考图里不是 `1 0 0 1` 的文字矩阵一共 14 种（`tools/pdf_text_objects.py matrices`）。乘 256 都是整数：

|---|---:|---|---:|---:|

| 宋体 | 12.48 | `0.77 0 0 1`、`0 0.77 -1 0` | 197 | 256 |
| 宋体 | 13.44 | `0.785 0 0 1` | 201 | 256 |
| 宋体 | 14.4 | `0.797 0 0 1` | 204 | 256 |
| 宋体 | 14.88 | `0.773 0 0 1` | 198 | 256 |
| 宋体 | 16.8 | `0.742 0 0 1` | 190 | 256 |
| 宋体 | 17.76 | `0 0.754 -1 0` | 193 | 256 |
| 宋体 | 18.72 | `0.77 0 0 1` | 197 | 256 |

| Arial（旋转） | 12.45 | `0 1.012 -1.012 0` | 259 | 259 |

正排、不压窄的文字一律是 `1 0 0 1`，不论字型。

九档宋体的压窄比是 `2W/em`（`W` 是样式请求的平均字宽，`em` 是字身，都是整数个设备单位）。把它乘 256：
213.33、196.92、201.14、204.80、198.19、190.17、193.73、196.92、198.69，参考图写的是 213、197、201、204、
198、190、193、197、198——196.92 进成 197，204.80 却舍成 204。所以它既不是四舍五入，也不是截断。

## 被否定的解释

**「GDI 建字体时把宽度取整了」。** 在本机 GDI 上用这九组 `(em, W)` 建宋体，取字形的未 hint 轮廓放大 32 倍量
（精度约 1e-5）：横向压窄比九档都正好是 `2W/em`（0.833333、0.769231、0.785714、0.800000、……），纵向
1.000000；`tmAveCharWidth` 正好是 `W`。GDI 没有取整。

**「请求字宽与该字高下的自然平均字宽都是整数，写出的是两者之比」。** 设备是 150 dpi（一个设备单位是
0.48 pt，标签起点落在这个网格上）。字身 39、宽 15 那一档：宋体在 39 个单位上的自然平均字宽是 19.5，取整只能是
19 或 20，15/20 = 192/256，15/19 = 202/256，参考图是 197。换更细的分辨率，两个数都成了精确的倍数，比值回到
`2W/em`，又是上一节的矛盾：字身为偶数的两档 (26, 10) 与 (30, 12)，比值都是精确的有理数，一个要进、一个要舍，
任何「精确比值取整一次」都做不到。

## 规则从哪里来

出参考图的是 4.5.2.9 版驱动，这个版本的 `acfpdfu.dll` 不在这台机器上。手头有 5.0.1.9
（`D:\work\cad\bin\acfpdfu.dll`），它写文字矩阵的那段代码（反编译，`sub_1000E860`）是：

```text
XFORMOBJ_iGetXform(pxo, &xform)                     notional → device 的字体变换
eM22 == eM11 且两个斜项为 0 →  写 "1 0 0 1"          正排、不压窄：特判
纯 90° 旋转                   →  写 "0 1 -1 0"         （4.5.2.9 印的是 0 1.012 -1.012 0，当时还没有这一条）
其余：
    len   = hypot(eM21 × 1250000, eM22 × 1250000)
    a     = len × (1/256)
    scale = 1250000 / a
    四项各乘 scale，按 %g 印「值 / 256」
```

全程浮点，所以 5.x 会印 `0.8`、`0.769231`。把 `len × (1/256)` 换成整数除法、把每一项截断成整数再印，就是
上面的规则——4.5.2.9 的写法。它不是从 4.5.2.9 的二进制里读出来的，是搜出来的；支撑它的是见证有多少、
把它钉得有多死。

## 搜索：试过的规则族

`tools/driver_text_matrix.py` 是最后一族的检验；前四族是手算与一次性的脚本。

| 规则族 | 结果 |
|---|---|
| 精确比值 `2W/em` 取整一次（四舍五入、截断、进一） | 否定：(26, 10) → 197 要进，(30, 12) → 204 要舍 |
| 两个整数之比（请求字宽 / 自然平均字宽），各种分辨率 | 否定：见上一节 |
| 加或乘一个常数再取整：`floor(v + c)`，`round(v × f)` | 九档能凑出来（`c` ∈ [0.077, 0.2)，`f` ∈ [0.99785, 0.99854)），但常数没有来历，也给不出 Arial 的 1.012 |
| 换成缇（1/1440 in）再取整：分子四舍五入、分母截断、商截断 | 九档全中，但 Arial `M` 的 207 用整数缇凑不出来（130/161 → 206，131/161 → 208） |
| 5.0.1.9 那段代码，两步换成整数运算 | **14 / 14** |

最后一族钉得有多死：

- **常数。** 把 1 250 000 换成 1000 到 20 000 000 之间的每一个整数，能 14 个全中的只有 345 个：
  1 249 941～1 250 225 与 1 250 714～1 250 773。125 000 只中 4 个，1 000 000 中 10 个，65 536 中 8 个。
- **整数步。** 除以 256 必须是整数除法、各项必须截断：两者任何一个换成四舍五入、进一，或者除法不取整，至少
  错 3 个。`L` 本身截断、取整、进一都一样（紧跟着就被整除掉了）。`scale` 必须是浮点，换成整数除法只中 12 个。
- **最贴边的见证。** Arial Narrow 的 37 单位字格：截断前是 259.012。它是 259 而不是 258，只因为这个字型的
  字格是 2319 个设计单位（`usWinAscent + usWinDescent` = 1888 + 431）；2320 就会是 258。这个数是从字体文件
  读的，不是凑的。

## 写出器的改法

- `write/text_matrix.rs`：`written(across, 压窄比, 是否正排)` 给出 `Tm` 的两个缩放，以及驱动留作字距换算用的
  「沿基线的 256 分之几」。正排且不压窄的照旧 `1 0 0 1`。
- `write.rs` 的 `show_text`：`Tm` 写这两个缩放。出图程序的那一套——字格、压窄比、每个字的整像素步进——
  不变，照旧按压窄比本身算。
- **字距。** 驱动把「设备上要的字距」除以沿基线的 256 分之几，写成 `Tc`。于是一个文字对象里的字不再正好
  落在步进上，而是每个字偏「字宽 ×（写出的缩放 − 压窄比）」，在对象内部累计。参考图就是这样：
  `设计证书号` 每个字少走 0.09 个单位。这正是那 44 条标签宽出、窄出 0.05～0.43 mm 的来源。
- 偏离在文字对象结束处归零，所以要先按文字种类切对象（上一篇，
  `2026-11-11-a-string-is-one-text-object-for-each-script-run.md`）。不切的话，A2 图的证书行（宋体 24 单位、
  宽 10，46 个字一串）会累计窄 0.16 mm；切开之后与参考图差 0.0003 mm。
- 旋转的字照旧逐个落在整像素步进上，`TJ` 里的调整量按新的缩放折算。
- 没有照搬的一处：参考图的 `Tc` 截断到三位小数，我方不截断。一条 21 个字的标签因此差不到 0.005 mm。

## 没有见证的，以及局限

- 256 与 2048 以外的设计网格（每 em 的设计单位数）。
- 不是直角的旋转：驱动对四项各自截断，并从两个截断过的分量求向量长度；这里只把两个缩放乘上正弦、余弦。
- **一条标签里换了字型或字号的那一段**（借来的字、记录里点名别的字型的段）与所在标签共用一个 `Tm`，矩阵按
  标签点名的字型算。驱动会给它自己的矩阵。参考图上没有哪条旋转或压窄的标签带这样的段，所以没有样本；
  夹具 `工艺管道及仪表流程-1` 里有 33 个这样的文字对象。
- 截断前正好是整数的项（驱动的单精度浮点决定进退），以及 `n/256` 正好落在两个三位小数中间的项
  （`n` = 16、48、80、…；这里四舍五入进一）。
- 出参考图的 4.5.2.9 版二进制仍然没有读到。拿到它可以把这条规则从「14 个见证」变成「读出来的」。
