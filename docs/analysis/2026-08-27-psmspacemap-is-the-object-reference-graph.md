# `PSMspacemap` 存的是对象引用图：`span` 是在用槽数，`tag` 是被指对象的类

> 日期：2026-08-27
> 范围：`pid-parse`
> 结论类型：**corpus（四图 38 个 member 流穷尽，无例外）**
> 前置：`docs/pid-format-guide.md` §3.1（2026-08-26，帧本身，native-reader）
> 含**一处推翻**：`span` 不是「和成员数对不上的 317 条」，是我们拿错了比较对象。
> probe：`examples/probe_psmspacemap_tag_and_span.rs`

## 0. 上一轮留下的两个问题

8-26 那一轮用 `radsrvitem.dll` 的 `Segment::Load` / `Segment::Save` 把帧坐实了，
四张图 38 个流全部走到最后一个字节。但条目里有两个字段只是被搬了出来，没人说它们
是什么：

```text
u32  head    —— 低半是 index
u16  ???     —— 本仓当时叫 stated_span
u16  count
count × { u32 value ; u16 tag }
```

当时的记录是：「1948 条里 1631 条的 `span` 恰好等于自己的成员数，**但有 317 条不
等**」，以及「tag 分布 14 个值，`190` 最多（1446 个），**各自什么意思还没坐实**」。

这一轮不再问反汇编，改问语料。三个没人认领的字段（那个 `u16`、`value`、`tag`）全部
有了答案，而且**顺带发现这张表根本不是一张号码表**。

## 1. 一句话

**每条条目是一个对象的出边表**：`u16` 说有几条边在用，成员槽两两成对地说
「指向哪个对象（持久 id）」和「那个对象是什么类」。

## 2. 第一个 `u16` 是在用槽数，第二个是槽容量

三个测量放在一起就够了：

| 测的东西 | 结果 |
|---|---|
| `tag == 0` 与 `value == 0` 是否同真同假 | **4446 / 4446** 个成员槽 |
| 在用槽数 == 非空槽数 | **1948 / 1948** 条条目，零反例 |
| 已用槽前面有空槽（打洞）的条目 | **0 / 1948** |
| 在用槽数 == 成员槽总数 | 1631 / 1948 |

所以成员数组是「按位置寻址、尾部留空」的定长数组：第二个 `u16` 是**容量**，
第一个是**填了多少**。这和头 12 字节里那对 `条目数 / 简单槽容量` 是同一种写法，
读器在同一个结构里用了两遍。

**上一轮那「317 条不等」不是数据不齐，是比错了。** 拿在用槽数去比容量，当然对不上；
比非空槽数就一条都不差。差值分布也只往一个方向偏，正是「尾部有空槽」的样子：

```text
head_hi 2: span - count  {-2: 3, -1: 36, 0: 508}
head_hi 3: span - count  {-12: 1, -10: 3, -7: 1, -6: 6, -5: 4, -4: 4, -3: 8, -2: 19, -1: 232, 0: 1123}
```

> 反汇编里那条「head 高半为 3 时给 span 加 2」属于**另一个**条目读器
> （`sub_5647AB70`），本语料没有一个流走它的帧，所以那两个成员在字节里根本不存在，
> 加不加与这里的读数无关。上面 `head_hi 3` 的直方图也没有 `+2` 这一档。

## 3. `value` 是同一 id 空间里一个活对象的持久 id

判据是**自由表**，而且它足够狠：这些段一共发出过 40893 个索引，其中 **11998 个
（29%）在自由表上**。如果 `value` 不是对象引用，随便什么数都该有三成砸进死索引。

实测 3989 个非空成员：

| 落点 | 个数 |
|---|---|
| 活索引（`< m_iNext` 且不在自由表） | **3988** |
| 自由表上的死索引 | 1 |
| 越过 `m_iNext` | 0 |

按 tag 分开看也一样：13 个 tag 里 12 个全中，剩下那个（`249`，731 个成员）差一条。

那一条例外值得单独记一笔：`DWG-0201GP06-01.pid` 顶层 `PSMspacemap\0x00006000`
的 entry 2 指向 `369`（tag 249），而 `369` 已经被回收进第 0 段的自由表——**一条悬空
边**，不是我们读错。

自由表本身也先验过一遍：16 个流里，**没有一个索引既在自由表上又带条目**，也没有一个
自由表项落在 `m_iNext` 之上。它确实是一张死索引表，上面那个 29% 才有意义。

### 3.1 id 空间按存储分，不按文件分

顶层 `/PSMspacemap` 和每个 `JSiteN/PSMspacemap` **各自独立编号**。这不是推测——
上一版 probe 就是栽在这里：它用「去掉 `PSMspacemap` 之后的路径」当 key，四张图的顶层
map 于是并成了同一个 `/`，A 图的 id 在 B 图的集合里能命中，测出来一批假阳性。按
`(文件, 存储)` 二元组重切之后，命中率反而上去了——真信号一直在，是 key 把它搅混了。

## 4. `tag` 是被指对象的类

### 4.1 判据

只用表内信息就能把「tag 属于目标」和「tag 属于这条边」分开：

> 把每个被指到的对象拿出来，看指向它的那些成员是否**在 tag 上达成一致**。
> 一致 → tag 说的是这个对象**是什么**；不一致 → tag 说的是这次引用**干什么用**。

语料里被指到的对象 **2415** 个，其中被指了不止一次的 **675** 个。
**每个对象身上的 tag 都只有一种，零分歧。**

如果 tag 是边的角色，675 个多入度对象里出现分歧的应该是多数——一个对象既被当作
「父」又被当作「样式」是再正常不过的事。一条都没有。

### 4.2 三条旁证

- **跨文档常量。** 四张互不相干的图，顶层 map 里 `2 → 182`、`7 → 183`、`19 → 184`
  全部一致。文件级分配的东西不会这样。
- **tag 几乎钉死目标条目的形状。** 在有自己条目的目标里：`183`/`184`/`190` 只落在
  head 高半 2，`181`/`188`/`249` 只落在 3。唯一混用的是 `182`（128 比 12）。
- **取值集合是读器的，不是文件的。** 四张图的 tag 全部取自同一个 14 值集合
  `{0, 181, 182, 183, 184, 185, 188, 190, 201, 205, 225, 239, 249, 261}`，没有一张冒
  出集合外的值；各图只用到其中一部分（D06 没有 `201`，0202 没有 `188`/`225`/`239`）。

这也把反汇编那条线接上了：`sub_5647AB70` 给自己合成的两个成员写死 `181` / `182`，
一个读器能把类编译进代码里，正说明这些值是它先验知道的固定集合。

### 4.3 哪个 tag 是哪个类：还不知道

**不要拿 §4 的 PSM type code 表去套。** 对不上。`205` 差 `JSymbol`(206) 一个数、
`249` 差 `Dependency Object`(250) 一个数，但 `181`/`183`/`190` 这些一个都对不上，
所以那两处是巧合，不是偏移量。

现在只有一个锚点，而且它给出的是**否定**信息：

`JSiteN` 的 `N` 就是顶层 id 空间里的一个持久 id。判据是四张图七个 `JSite` 的数字后缀
**全部**在顶层 map 里找得到自己的条目（7/7），而且七条形状一模一样——随手起的编号不会
有这个性质：

```text
D06.pid          JSite145 : head_hi 2, 在用 2, [(2, tag 182), (146, tag 261)]
D06.pid          JSite151 : head_hi 2, 在用 2, [(2, tag 182), (138, tag 225)]
DWG-0201GP06-01  JSite329 : head_hi 2, 在用 2, [(2, tag 182), (397, tag 261)]
DWG-0201GP06-01  JSite396 : head_hi 2, 在用 2, [(2, tag 182), (224, tag 225)]
DWG-0202GP06-01  JSite793 : head_hi 2, 在用 2, [(2, tag 182), (794, tag 261)]
工艺管道及仪表流程-1  JSite6963: head_hi 2, 在用 2, [(2, tag 182), (6962, tag 225)]
工艺管道及仪表流程-1  JSite7559: head_hi 2, 在用 2, [(2, tag 182), (7560, tag 261)]
```

但**顶层 map 里没有任何一条引用指向 `JSite`**（顶层每个段都搜过，零命中）。所以
`JSite` 在这张引用图上是源点——进得去它们的路在这张表之外，`PSMroots` 是最自然的那条，
但本轮没验。锚点因此只能给否定信息：它证不了 tag `182` 是什么类，只说明每个 `JSite`
都指着同一个文档级单例 `2`。

一条**未证实的观察**，留给下一轮：`183` 和 `184` 常常是相邻的一对 id
（`14`/`15`、`74`/`75`、`96`/`97`、`243`/`244`、`27865`/`27866`），看着像成对分配，
但不是每次都相邻（D06 的 `JSite145` 里是 `25`/`27`）。

## 5. 有出边的对象才有条目

条目数远小于活 id 数。工艺图顶层第 0 段：`m_iNext` 7669、自由表 6219，活 id 约 1450，
而这一段只有 **337** 条条目。被指到的对象也大多没有条目——同一个 id 空间里 630 个被指
对象，只有 193 个有。

所以这张表是**出边表**，不能当「文档有哪些对象」的答案用。没有出边的对象（大概率就是
叶子：几何、文字这些）在这里是隐形的，只在别人的成员槽里露一次面。

## 6. 已落地

- `PsmSpaceMapEntry::stated_span` → **`live_member_count`**，附
  `live_members()` 取前缀（clamp 过，坏计数不会越界）。三处调用点，无外部影响。
- `PsmSpaceMapMember` 的两个字段改写文档：`value` 是目标的持久 id，`tag` 是目标的类。
- `parse_psm_space_map_with_trace` 的帧注释按新读法重写；解析器内部
  `count` → `capacity`。
- `docs/pid-format-guide.md` 新增 §3.2，删去两段「还没坐实」；`CHANGELOG.md` 记一条。
- `tests/parse_real_files.rs` 增两条回归：
  `psm_space_map_states_how_many_member_slots_are_in_use`（含 1948 / 4446 / 457 棘轮）、
  `psm_space_map_tag_belongs_to_the_object_it_points_at`（含 2415 / 675 棘轮）。

**没有改解码行为**：字节怎么读还是怎么读，改的是这些数叫什么、以及我们敢拿它做什么。
