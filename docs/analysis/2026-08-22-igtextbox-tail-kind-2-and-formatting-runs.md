# `igTextBox` 的字节账目闭合了：kind 2 是另一种放置记录，形状 3 的 A/B 是字符样式 run

> 日期：2026-08-22
> 阶段：文字保真取证（**只取证，本轮未改解码器**）
> 证据等级：**native-reader**（`radsrvitem.dll` 的 Load / GetSize / Save 三者互证）
> 产物：`examples/probe_igtextbox_tail_and_runs`、`tools/idalib_igtextbox_style_apply.py`

## TL;DR

2026-08-13 留下两个未解释的结构，本轮一趟带出来，并且**字节账目闭合**：

```text
bytes_to_follow = 22            公共头
                + body_len      按形状
                + tail_len      按尾块 kind

body_len   形状 1 :  2 + 2*count
           形状 2 : 10 + 2*count
           形状 3 :  6 + 2*count + 8*(A + B)

tail_len   kind 1 : 36
           kind 2 : 68 + 8 * popcount(flags & 0x3F80_0000)
```

全语料 **260/260 精确相等，零余量**——没有「剩下这些不知道是什么」。

- **kind 2 多出来的 32／40 字节**不是挂件，是**同一个放置类的长格式**：
  `IGDSFactoryTextPointRectShape` 的 kind 1 写 36 字节（插入点 + 方向 + 一个 dword），
  kind 2 写 68 字节固定部分，再按 `tail+36` 的标志位每置一位多写 8 字节。
  `68 - 36 = 32`，`76 - 36 = 40`——正是此前记的那两个数。
- **形状 3 的 A／B 条目是带字符样式的富文本 run**：每条 8 字节
  `(u16 长度, u16 选择子, u32 样式 id)`。选择子 1 指向 `0x002C JStyleTextChar`
  （320 条里 313 条命中），选择子 2 指向 `0x002D JStyleTextPara`
  （13/13，且**每一条都等于记录自己的 `+14`**）。
- **顺带**：形状判别位不是独立字段，是**从 run 数量推出来的**；形状 2 的
  `count | 0x10000` 从来不是标记，那是**一条 run 条目**，`0x10000` 是它高半字里的
  选择子 `1`。
- **顺带（要紧的）**：形状 2 那条 run 指的字符样式，与解码器当前走两跳
  （`+14` → `JStyleTextPara +38` → `JStyleTextChar`）拿到的**不是同一条**：
  215 条里 **153 条不一致**，而不一致的那些**字高／字体确实不同**。详见 §6。

## 一、怎么找到的

沿用上两轮验证过的手法（接口 get/put 访问器 → 对象槽位 → 喂这些槽位的 DoIO
调用者），这次从 Load 往下走了三层：

```text
IGDSFactoryText                       operator new(0x5C)，工厂 sub_56497EE0
  ??_7IGDSFactoryText@@6B@   @0x566666fc   +60 Load  +64 GetSize  +68 Save
  ??_7IGDSFactoryText@@6B@_0 @0x56666748   this+20 的文本 sink，22 个槽
      +56 SetText(count, ptr)          sub_564986E0
      +68 追加 run，选择子写死 1        sub_564978B0
      +72 追加 run，选择子写死 2        sub_56497930
      +76 复位                          sub_56498020
      +84 取／建放置对象 → this+88      sub_56497E40
  this+88  IGDSFactoryTextPointRectShape（operator new(0xA0)）
      +24 Load(0, kind, tail_ptr)       sub_56498780   ← 尾块读序
      +28 GetSize                       sub_56497AE0   ← 尾块字节账目
      +32 Save                          sub_56497BF0
      +36 判定自己是 kind 1 还是 2       sub_56497A10
```

**账目是读、写、算尺寸三处互证的**，不是单看 Load 推的：

- `IGDSFactoryText::GetSize`（`sub_56498AB0`）算 `head+body`，再加上
  `this+88` 自己报的尺寸；
- `IGDSFactoryText::Save`（`sub_56498940`）把 `总长 - 6` 写进记录字节 2..5，
  也就是 `bytes_to_follow`——**这就是上面那条等式，由写入方给出**；
- Save 结尾把尾块 Save 的返回值写进记录字节 26（= payload `+20`），
  所以 `+20` 不是一个独立声明的字段，而是**放置对象自报的格式**。

## 二、公共头与三种形状，统一成一句话

Load 一开始 `memcpy(this+32, Src, 0x1C)` ——记录前 28 字节（= payload `+0..+21`）
整块吞下，所以 body 从 payload `+22` 起算，与解码器一致。

三种形状其实是**同一套字段的三种紧凑写法**，`GetSize` 里的这段是决定性的：

```c
if ( A || B ) {  if ( A != 1 || B )  shape = 3;  else shape = 2;  }
else            shape = 1;
```

即：

| 形状 | 何时用 | body 布局（payload 相对） |
|---:|---|---|
| 1 | 一条 run 都没有 | `+22 u16 count`；`+24` 文本 |
| 2 | 恰好一条选择子 1 的 run | `+22` **run 条目 8 字节**；`+30 u16 count`；`+32` 文本 |
| 3 | 其余 | `+22 u16 A`；`+24 u16 B`；`+26 u16 count`；`+28` 文本；其后 A 条 run 再 B 条 run |

形状 2 的 `+22 dword == count | 0x10000` 因此有了解释：那 4 字节是 run 条目的
`(u16 长度, u16 选择子)`，长度等于 count、选择子等于 1。`+26` 的 u32 是这条 run 的
样式 id。**解码器现在把这 4 字节当冗余校验用，是对的，但它其实是数据。**

## 三、run 的语义

Load 按 8 字节步长走 `A + B` 条，读每条的选择子派给两个槽；两个槽的实现自己把
选择子写回去（`sub_564978B0` 写 `1`，`sub_56497930` 写 `2`），所以磁盘上的
选择子与位置必然一致——Save 也是先写 A 条再写 B 条。

`GetSize` 还给了一条硬不变式：**选择子 1 的所有长度加起来必须等于字符数**，
否则整条记录被拒（`return E_FAIL`）。这坐实了「选择子 1 的 run 覆盖文本区间」。

实测（全语料 260 条）：

```text
(A, B) 分布        A=0 B=0 : 32     A=1 B=0 : 215    A=3 B=1 : 2    A=9 B=1 : 11
形状由 (A,B) 复现  260/260
选择子取值         {1: 320, 2: 13}
选择子与位置一致    260/260
选择子 1 长度求和 == 字符数   228/228   （形状 1 无 run，不参与）
多于一条 run 的记录 13
```

选择子 1 的 320 条 run 里 **313 条的值是 `0x002C JStyleTextChar` 的 id**，
1 条落在 `0x002D`，6 条落在 `0x002E`。选择子 2 的 13 条**全部**是
`0x002D JStyleTextPara`，且**全部等于记录自己的 `+14`**——也就是说选择子 2 那条
run 是把段落样式重述了一遍，不是新信息。

多 run 的标签长这样（探针实测打印）：

```text
"250-LNG-57602- - "  (17 chars)
   len 3 sel 1 → 0x42     "250"
   len 1 sel 1 → 0x46     "-"
   len 3 sel 1 → 0x42     "LNG"
   len 1 sel 1 → 0x46     "-"
   len 5 sel 1 → 0x42     "57602"
   ...
   len 1 sel 2 → 0x24     （段落样式，= 本记录的 +14）

"27.0 m^3  3.0 m*3.0 m*3.0 m"  (27 chars)
   len 15 sel 1 → 0x69
   len  1 sel 1 → 0x84     ← 单个字符换样式：上标的 "3"
   len 11 sel 1 → 0x69
```

管道号里**分隔符 `-` 与号段用的是两条不同的字符样式**（`0x42` / `0x46`
交替），`m^3` 里那个 `3` 单独一条 run。这就是富文本，不是几何数据。

## 四、kind 2 的尾块

`IGDSFactoryTextPointRectShape::Load` 的读序（偏移相对尾块起点，
即 payload `+22 + body_len`）：

```text
  +0   f64   插入点 x        ⎫ kind 1 与 kind 2 完全相同
  +8   f64   插入点 y        ⎪ ——所以 2026-08-13「当前无误读」的判断成立
  +16  f64   方向 cos        ⎪
  +24  f64   方向 sin        ⎪
  +32  u32   （两种 kind 都有；此前记作「尾块最后 4 字节」）⎭
  --- 以下仅 kind 2 ---
  +36  u32   标志位          ← 决定后面有几个可选字段
  +40  f64   ⎫ 两个长度量，原生拿它们与一个全局容差比长短
  +48  f64   ⎭
  +56  u32   ⎫
  +60  u32   ⎬ 三个 dword
  +64  u32   ⎭
  +68  f64   可选，位 0x0080_0000
       f64   可选，位 0x1000_0000
       f64   可选，位 0x2000_0000
       f64   可选，位 0x0100_0000
       f64   可选，位 0x0200_0000
       f64   可选，位 0x0400_0000
       f64   可选，位 0x0800_0000
```

七个可选位合起来正是 `0x3F80_0000`，而 `sub_56497A10`（「我是 kind 1 还是 2」）
用的判据是：

```c
kind = 2  当且仅当  |+40| 或 |+48| 超过容差
                 或 +56 / +60 / +64 任一非零
                 或 flags & 0x3F800000 非零
```

**同一个掩码**同时出现在「有没有可选字段」和「要不要写长格式」两处——这是本轮
最强的一处自洽：kind 2 的定义就是「这条记录带了默认之外的东西」。

实测（全语料）：

```text
尾块长度        36 : 236     68 : 15     76 : 9
比 36 多出       +0 : 236    +32 : 15   +40 : 9
标志位取值      0x00000000 : 4    0x60000000 : 7    0x60000004 : 2
                0xc0000000 : 3    0xc0000008 : 8
每条的可选字段数   0 : 15      1 : 9
+40（米）  {0.005080, 0.005184, 0.006350, 0.012654, 0.029144, 0.040640,
            0.042000 x8, 0.042009, 0.044399, 0.044460, 0.090604}
+48（米）  {0.003865, 0.005080, 0.006098 x5, 0.006350, 0.008309 x9,
            0.010160, 0.010849, 0.011616, 0.020037}
```

`+40` 落在 5–91 mm、`+48` 落在 3.9–20 mm，而本语料的字高是 1.5–6.35 mm：
形状上像**文本框的宽与高**（类名 `PointRectShape` 也这么说）。但**原生代码只
证明了它们是与长度容差比较的 double，没有给出命名**——这条按推断记，不按
native-reader 记。

标志位高 2 位（`0x4000_0000` / `0x8000_0000`）在读序与尺寸里都没被用到，取值
却有变化（`0x6...` / `0xc...`）；低位 `0x4` / `0x8` 同理。它们**不影响字节账目**，
语义未解。

## 五、`+32` 那个 dword

两种 kind 都读它，是原先说的「尾块最后 4 字节」。全语料分布：

```text
0x00000000 : 11   0x01000000 : 79   0x05000000 : 9    0x08000000 : 2
0x15000000 : 94   0x26000000 : 2    0x31000000 : 3    0x38000000 : 23
0x40000000 : 7    0x42000000 : 10   0x48000000 : 20
```

**低 24 位恒为零，全部信息在最高字节**（11 个取值）。原生只是原样搬进对象，
没有在本轮读到的任何函数里再解释它。语义未解，但它已被账目覆盖——不是缺口。

## 六、这一趟捎出来的一个疑似缺陷（下一轮的输入）

形状 2 的那条 run 直接指着一条 `JStyleTextChar`。解码器现在**不读它**，而是走
`+14` → `JStyleTextPara +38` → `JStyleTextChar` 两跳。两者对比（215 条形状 2）：

```text
run 的 id 与两跳结果   一致 61   不一致 153   解析不出 1
```

进一步比对两条样式**实际产出的字形**（字高 / 颜色 / 字体名，用 08-13 定下的偏移）。
这一项的数字**只测到 201 条语料**（`DWG-0201GP06-01.pid` 当时被锁，见 §8），
在那 122 条不一致里：**字形相同 0 条、不同 116 条、解析不出 6 条**。也就是说
不一致几乎必然带来可见差异——例如

```text
run "Arial Narrow" 2.4694mm #000000   vs   para "Arial Narrow" 2.5000mm #000000
run "Arial"        2.2931mm #000000   vs   para "Arial"        3.1750mm #000000
run "Arial Narrow" 2.4694mm #000000   vs   para "Arial"        3.1750mm #000000
```

run 侧的字高是 2.4694 / 2.2931 这类**非整数**，para 侧是 2.5 / 3.175（1/8″）
这类**标称值**——像是「段落默认」与「这段字实际用的」的关系。

原生把 run 交给 `AddCharStyleRun(长度, 样式 id)`，那是**真正给字上格式**的调用；
段落的 `+38` 是段落级默认。因此**很可能 run 优先**，也就是说我们现在有一批标签
的字高／字体取自段落默认而不是实际样式。

**但这一条本轮不下结论**：读序只证明「run 被逐区间应用」，没有直接读到渲染端
的取舍规则。要么找到消费 `+68` 槽的渲染路径，要么用一张能对照的图核对。
**这是下一轮的第一件事，优先级高于把 run 接线**——先确认谁赢，再谈改。

## 七、仍然不知道的（登记，不猜）

- `+32` dword 最高字节的 11 个取值；
- kind 2 标志位里 `0x4000_0000` / `0x8000_0000` / `0x4` / `0x8` 的含义；
- `+40` / `+48` 是不是宽高（形状吻合，命名未证）；
- `+56` / `+60` / `+64` 三个 dword（取值成组出现：`(0x0e,0x0d,0x0d)` 8 条、
  `(0x1b,0x1a,0x1a)` 4 条、`(0x35,0x0d,0x0d)` 3 条、`(0x36,0x1a,0x1a)` 8 条、
  `(0x1a,0x0d,0x0d)` 1 条——后两位总是相等，像一对 id）；
- 选择子 1 里落在 `0x002E`／`0x002D` 的 7 条 run（313/320 命中 `0x002C`）；
- 七个可选字段各自是什么（只证明了「每个 8 字节」，没证明是什么）。

以上都**不影响字节账目**：它们是已定位、已计入长度、语义未解的字段，不是
「还有一段不知道是什么的字节」。

## 八、Coverage Gap：本轮的验证是分两次拼起来的

取证期间有一个 `OpenCADStudio` 进程一直开着仓里的 fixture，对文件加**字节范围锁**
（`os error 33`），并在旁边留下 `test-file/.<name>.pid.ocs.lock`。它先锁
`DWG-0201GP06-01.pid`（PID 71272 → 退出后 17284 又起来接着锁），后来换成锁
`DWG-0202GP06-01.pid`——像是有人在逐张翻图。后果：

- 语料从 260 条掉到 201 条，而**旧探针的写法会把这件事吞掉**：
  `sheet_streams` 打不开文件就返回空 vec，下游读成「这个 fixture 没有记录」。
  第一次跑出来的 201 看上去和 260 一样体面。新探针因此改成**打不开就报错、
  整轮标记为 PARTIAL**——本文 §一至 §五、§七的数字都取自没有 UNREAD 行的那次
  完整运行（260/260）；§六的字形对比只测到 201 条，已就地标注。
- **`cargo test --all-features` 没能拿到绿灯**：失败的 target 每一个都只报
  `os error 33`，随当时被锁的那张图在 `geometry_golden_snapshot` /
  `render_gap_census` / `style_link_ratchet` / `parse_real_files` /
  `sheet_family_wiring` / `unit_parsers` / `writer_real_files` 之间移动。
  本轮**只新增两个文件、未改任何已有文件**，所以这不是回归；但它**是一次没能
  拿到的绿灯**，如实登记，不当成通过。`cargo clippy --all-targets --all-features`
  与 `cargo fmt -- --check` 都是干净的（不读 fixture）。
  共重试 20 次、跨约 10 分钟，其间只抢到过两个短窗口。

教训与 08-13 那条同源：**在报一个数之前，先确认自己确实看到了要看的东西。**
上次是偏移看错了位置，这次是文件根本没打开。两次都是「阴性/短缺的结果长得
和正常结果一模一样」。

## 九、复现

```powershell
cargo run --example probe_igtextbox_tail_and_runs     # 语料侧，账目 + 分布
python tools/idalib_igtextbox_style_apply.py          # 原生侧，读序
```

`tools/idalib_igtextbox_style_apply.py` 里有一处环境绕行值得留意：
`dlls/radsrvitem.dll.i64` 旁边留着一份**未打包的数据库**
（`.id0/.id1/.id2/.nam/.til`，来自一次没正常关闭的 IDA 会话）。headless IDA 会
自动选「恢复打包库」，要删那些文件，而 `.id0` 删不掉（permission denied），
`open_database` 直接返回 4。脚本把打包库复制到临时目录再打开，绕开这件事，
**不动仓里的任何文件**。
