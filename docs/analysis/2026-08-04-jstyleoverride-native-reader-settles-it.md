## 2. Phase 16 的 schema 是对的

Phase 16 记录的是：

> `4 × u32 + 4 × f64 + 3 × u32 + 2 × u16`

version 3 逐项对上：`+26/+30/+34/+38` 四个 u32，`+42/+50/+58/+66` 四个 f64，
`+74/+78/+82` 三个 u32，`+86/+88` 两个 u16。**16 + 32 + 12 + 4 = 64 字节**，
加基类块 26 = 90。

Phase 16 所说的「payload `+0..15`」是**基类块之后**的偏移，也就是本文的 `+26..+41`。

## 3. 推翻一：anchor 解读不成立

Phase 16 Slice F 的注释写：

> IDA Version-3 schema 把 payload `+0..15` 读作 **4 × u32**；
> 而 probe v5 的跨 fixture 证据显示把前 8 字节与 `+8..15` 各读作一个 `f64`
> 会得到稳定落在 `[0, 1]` 的归一化坐标，所以作为 **inferred anchor** 发出。

**原生读取序给出裁决：那 16 字节是四次独立的 4 字节读取**
（`this+88` / `this+96` / `this+100` / `this+152`），**不是两个 f64**。

所以 `JStyleOverrideEmitter` 把它们投影成 `PidGraphicKind::Annotation` 的锚点
**是误读**。「值落在 0..1」只是四个 u32 恰好拼出了合法的小 double 位模式。

**影响**：OCS 的 `PID-ANNOTATION` 图层画的方向短线没有事实依据。该图层默认隐藏，
所以没有可见损害，但 `Annotation` 这个 kind 的产出应当撤回或降级。
真正的 f64 在 `+42 / +50 / +58 / +66` 四个位置。

## 4. 推翻二：我自己那个 `+50` 几何指针发现

`2026-08-04-jstyleoverride-points-at-geometry.md` §2 报告：`+50` 在两张图上都稳定
命中已知几何 OID（17/20、32/47），并据此说「这是几何指针」。

**站不住**：

1. **`+50` 在 version 3 里是一个 f64 的起点**，不是 u32 字段边界。
2. 我那次用滑窗 `scan_records(data, 0x0030, 40, 400)` 抓 Sheet 流里的记录，得到的
   payload 长度是 **128 / 129 / 145 / 224 / 225**。而原生布局是 **90（v3）或 98（v2）**。
   **两个都对不上** → 滑窗把记录边界切错了，后续所有偏移都是错位的。

一个把 u32 当边界、又建立在错误分帧上的「命中」，即使跨两张图一致，也只说明**同一个
分帧错误在两张图上一致地重现**。跨 fixture 一致性挡得住取值巧合，**挡不住系统性的
方法错误**——这是今天第二次栽在这上面（第一次是循环论证验证 CLSID 表）。

**因此「几何 → 样式」的链路仍然一个候选都没有**，四个全部排除。
