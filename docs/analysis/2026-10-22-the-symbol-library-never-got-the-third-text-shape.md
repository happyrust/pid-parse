# 库侧的文字读不出来，是第三种形状 + 一条过严的尾巴算术（606 条记录、83 个符号，已修）

> 日期：2026-10-22
> 阶段：改解码器，有行为变化
> 证据等级：**structure**（字节 + 语料逐条，与 `2026-08-13-igtextbox-has-three-shapes.md`
> 的 native-reader 公式对照）
> 产物：`examples/probe_sym_text_shape_gap`
> 前篇：`2026-10-22-the-normal-view-that-drew-nothing.md` §7（那 14 条读数）

## TL;DR

上一节把 203 条「空表」拆开时，剩下 14 条读数是「表里只有一条计数对不上的 `0x004D`」。
问的是：那批记录**用的是不是第三种头宽度**。答案是**是，但不止**：

| 库侧 `Sheet*` 流上的 `0x004D` | 条数 | 改前 `decode_text` 读得出来 |
|---|---:|---:|
| 形状 1（`+18 = 1`） | 566 | 471 |
| 形状 2（`+18 = 2`） | 2098 | 1789 |
| 形状 3（`+18 = 3`） | 202 | **0** |
| 合计 | 2866 | 2260 |

拒收 **606** 条，两个彼此独立的毛病：

1. **形状 3 的布局从来没实现。** 它的长度在 `+26`、文本在 `+28`，body 是
   `6 + 2*count + 8*(A+B)`；`decode_text` 只试 `+30` 和 `+22`，于是全族 202 条一条也
   读不出来。其中 **61 条**的 payload 长度其实完全对得上，只是长度字段不在它试的两个
   位置——再多试一个偏移也没用，`8*(A+B)` 那一项同样差着。
2. **「尾巴必须正好 36 字节且落在 payload 末尾」这条算术过严。** 另外 **404 条**
   （形状 1 的 95、形状 2 的 309）长度就在它试的偏移上，文本也读得通，只是记录在
   36 字节尾块之后还挂着 **32 / 40 / 48 / 56** 字节的可选字段（8 的整数倍，即更多的
   `f64`），于是「正好等于」永远不成立。绘图侧的解码器为这件事专门写着「留出余量而不是
   正好贴合」——库侧没有。

判定这 606 条是**真字**、不是被字节凑出来的：**606/606** 在形状给出的
`22 + body_len` 处读出米级图纸坐标，而且坐标跨文件复现（`(0.0, -2.7) mm` 110 次、
`(0.0, 2.7) mm` 110 次、`(84.2, 129.2) mm` 19 次）；同一批记录把 `text_end` 当插入点
念，得到的是 `2.75e-313` 这种次正规数。读出来的字符串 **606/606 都可读**，没有一条是
二进制被念成字：`"TBD"`、`"NULL"`、`"1\"x1\""`、`"CSC NULL"`、`"设计条件\r"`，以及整段
`<?xml version="1.0"?><body><intstgxml stream="Revision" …/></body>` 字段引用。

**代价**（改前）：332 个符号至少有一条字读不出来，其中 **83 个符号的整份文字全被拒** ——
这 83 个本体一个字母都不写（`Text with Leader.sym`、`Fail Action.sym`、`Nozzle NPD.sym`、
`Utility Connector.sym`、`Sum Funct TR.sym` …）。

**已修**（§四）：两个毛病都在 `symbol_library::decode_text` 里，改成向
`igtextbox_body_shape` 这张形状表问路，尾块从 `22 + body_len` 起算、判据改成「留得下
36 字节」。读得出的记录 2260 → **2864**（只剩 2 条自称空文本的），库侧文字图元
2023 → **2404** 条，整份文字被拒的符号 **83 → 0**；「一张干净视图集管着空表」的读数
203 → **108**。选表与出图读数逐位未动。

## 一、那 14 条读数具体是什么

`probe_empty_sheet_view_sets --detail 20` 列出的 14 条，去重后是 7 个文件（两个库根各
读一遍），每份都是 `Sheet6` 上一条 `0x004D`。逐条看形状：

| 符号 | payload | 形状 | 读出的字 | 尾巴位置 |
|---|---:|---:|---|---|
| `Nozzle NPD.sym` | 92 | 3 | `1"` | 正好贴末尾 |
| `Fail Action.sym` | 152 | 3 | `CSC NULL` | 正好贴末尾 |
| `Red Nominal Diameter.sym` | 122 | 3 | `1"x1"` | 正好贴末尾 |
| `Option.sym` | 192 | 3 | `0.25" thck  ` | 贴末尾 |
| `Piping Materials Class.sym` | 112 | 3 | `NULL` | 贴末尾 |
| **`Nozzle Rating.sym`** | 122 | **2** | `TBD` | 之后还有 48 字节 |

6 条是形状 3，**1 条不是**——`Nozzle Rating` 是形状 2、长度就在 `+30` 上，它读不出来
纯粹因为尾块后面还有 48 字节。这就是为什么「第三种头宽度」是对的、却不完整：14 条读数
里有 1 条跟形状无关。

## 二、为什么库侧没跟着修

`2026-08-13-igtextbox-has-three-shapes.md` 把三种形状的公式（`radsrvitem.dll` 的
`igTextBox` Load）落进了 `parsers::sheet_records::igtextbox_body_shape`，绘图侧 260 条
`0x004D` 就此零拒收。`symbol_library::decode_text` 是**另一条线**：它不是按形状查表，
而是「试 `+30`、试 `+22`，哪个算得出正好 36 字节尾巴就信哪个」。那条规则是
`examples/probe_sym_textbox` 时代从语料里反推出来的，当时确实解释了 908 + 248 条，
但它描述的是形状 1/2 的**最小**形态——形状 3 与「尾块之后还有字段」这两类它无从表达。
同一个二进制格式，两条读法，一条有形状表、一条没有。

## 三、形状 3 的读数，以及 `A`／`B` 到底是什么

`+18` 判别位在库里的分布是 566 / 2098 / 202，与绘图侧同族。
`Fail Action.sym` 的记录尾块读 `(0.10795, 0.1397) m`，与 `Red Nominal Diameter.sym`
独立记录的同一对数字相同——这正是图纸上默认标签位置的定义值，不是巧合。

**那 `8*(A+B)` 字节不是 double，是格式化 run** —— 每条 8 字节
`(u16 len, u16 selector, u32 style_id)`，先 `A` 条 selector 1（字符样式），再 `B` 条
selector 2（把记录自己的段落样式重述一遍）。这一条早已定案，库侧只是从未量过：
`2026-08-13-text-para-layout-and-justification.md` §五（原生按 8 字节步长遍历、按
选择子派给两个槽）、`2026-08-22-igtextbox-tail-kind-2-and-formatting-runs.md`
（`GetSize` 的 `if (A||B) { if (A != 1 || B) shape = 3; else shape = 2 }`，形状由 run
数推出）、`docs/pid-format-guide.md` 均已写成 run。**本文早先写的「counters 的
doubles」是错的**，也已改正。

库侧 2866 条记录逐条量（新探针 `examples/probe_sym_text_runs`）：

| 量 | 结果 |
|---|---|
| 格式化 run 总数 / 选择子 | 3113 / `{1: 2911, 2: 202}` |
| 形状 3 的 `A` | `{2:47, 3:7, 4:134, 5:2, 8:2, 12:2, 14:8}` |
| 形状 3 的 `B` | **全部为 1**（202/202） |
| 「先 A 条 selector 1、再 B 条 selector 2」 | 0 条破例 |
| selector 1 的长度和 == 字符数 | 0 条破例（18163 字符） |
| selector 2 == 记录自己的 `+14` | **176/202** |
| selector 1 的样式 id 落在符号自己的 `StyleCluster` 上 | 2866 `JStyleTextChar` / 1 `JStyleTextPara` / 3 其他 / **41 未定义** |
| 零长 run | 35 条，35 条记录各一条（`Air Compressor.sym` 的 `5x1#0 0x1#35 2x2#36` 那种占位） |

与绘图侧唯一的差异：绘图侧 13/13 的 selector 2 都与 `+14` 相等，库侧只有 176/202。
差的那 **26 条**大多指向 `+14` 附近（`17→22`、`12→20`、`13→22`、`19→24`、`10→16`、
`23→28`、`26→31`、`33→38`），且**解析出的字高与 `+14` 完全相同**（0 条不同），所以
它们只是同一段落族的另一个 id，不影响今天画出来的字号。

**真正还没闭上的是另一件事**：库侧从来不平 run——`lettering_of` 只用 `+14` 那一跳
的段落样式。把 run 的字符样式拿来对照，**2266 条可比的记录里有 1350 条（59.6 %）
run 说的字高与段落默认不同**，830 条字体不同、279 条颜色不同。这与绘图侧
`2026-08-22-run-beats-paragraph-default.md` 的结论一致（run 覆盖全文，段落样式是
默认值），只是库侧一直没接。

## 四、改了什么

一处，`symbol_library`：

- `decode_text` 不再试偏移，改读 `+18` 的形状判别位，把
  `count / text_start / body_len` 交给 `igtextbox_body_shape` —— 这张表原本是
  `parsers::sheet_records` 的私货（Phase 40 从 `radsrvitem.dll` 读出来的），现在
  `pub(crate)`，两侧共用一份，不再各写一套；
- 尾块从 `22 + body_len` 起算，判据从「正好贴合 payload」放松到「留得下 36 字节」；
- 插入点读 `tail_start`，不再读 `text_end`（形状 1/2 两者相同，形状 3 不同 ——
  这正是它以前读出 `2.75e-313` 的原因）；
- `lettering_of` 的方向对与锚点字节也跟着从 `tail_start` 读，不再假定尾巴是
  `payload_len - 36`：带 32–56 字节可选字段的记录，最后 36 字节并不是尾块；
- 仍拒：形状表不认识的判别位、payload 放不下尾块、空文本（2 条）、非坐标的插入点。
  （原文这里还列了「计数跑出 body（`text_end > tail_start`）」，那条永不触发，见 §六；
  审查后补上的方向对与尾型两道检查见 §七。）

| 读数 | 改前 | 改后 |
|---|---:|---:|
| `0x004D` 读得出的记录 | 2260 / 2866 | **2864** / 2866 |
| 形状 3 | 0 / 202 | **202** / 202 |
| 库侧 `Text` 图元（跨表去重后） | 2023 | **2404** |
| 整份文字全被拒的符号 | 83 | **0** |
| 「干净视图集管着空表」 | 203 | **108** |

最后一行是这条改动的连锁反应：那 203 条里 **14 条「整张表全是拒收记录」直接清零**，
**114 条「表里本体被孪生表认领」降到 33** —— 81 个符号的那个「空表」其实挂着自己的
标签，只是标签以前读不出来。剩下的 108 条是 71 条 8 字节空链 + 33 条真重复 + 4 条
边界被认领。

**输出侧未动**：

- 选表：`probe_normal_view_too_wide` 全部 11 条规则读数逐位不变（shipped 仍 159/172），
  `probe_library_vs_cached_bodies` 的 190 对仍是 pair 190 / same 146 / mismatched 39 /
  1518 笔画 / 464 被滤 —— 字没有把哪张表顶成「最肥」；
- 出图：`plot_compare`（五张参考图）、`export_every_fixture`、`export_plant_backup`
  （53 张，93.9 s）全过；
- `symbol_library` 单测 34 条（新增形状 3、带可选字段的记录、空文本、未知形状、
  计数越过 body 五类），全工作区 344 个测试二进制全 ok。

## 六、审查之后的三项测量（2026-10-22，计划 `2026-10-22-library-text-review-follow-ups.md` S1）

审查发现两件事。§四「仍拒」里的「计数跑出 body」永不触发：三种形状的 body 长度都由计数
算出，形状 1 / 2 的 `tail_start` 正好等于 `text_end`，形状 3 多 `8*(A+B)`。尾巴放宽成「留得
下」以后，库侧也没有了绘图侧那道防计数多读的方向对检查。动手之前先量了三件事。

**M1 方向对与尾型**（`examples/probe_sym_text_shape_gap` 新增「the tail of every record a shape
reads」一节）：

| 量 | 结果 |
|---|---|
| 方向对是单位向量 | 2812 |
| 方向对按字高缩放（0.5–250 mm） | 52 |
| 两样都不是 | **0** |
| kind 1（`+20 = 1`）尾后字节 | 0 B × **2321**，无一例外 |
| kind 2（`+20 = 2`）尾后字节 | 32 B × 410、40 B × 19、48 B × 64、56 B × 50，共 **543** |
| kind 2 文本框宽高可用 | 543 / 543 |

「尾后 32 / 40 / 48 / 56 字节」就是绘图侧早已认识的 kind-2 尾：36 字节定位尾 + 4 字节标志字 +
文本框宽高 + 三个计数 = 68 字节（`IGTEXTBOX_TAIL_KIND2_LEN`），再多的 8 / 16 / 24 字节是标志字
控制的可选 `f64`。标志字的 16 种取值逐一对上：位 24、25、27、29 每置一位多 8 字节，位 2、
20、21、30、31 不加字节，543 / 543 无例外；位 26、28 语料里从未出现。

**M2 选表**（新探针 `examples/probe_sym_pick_with_and_without_text`）：探针按
`displayed_primitives` 的规则自己选一遍表，1262 / 1262 与库函数逐个图元相同；再把「至少
画出一样东西 / 画得最多」改成只数几何（全无几何时退回原选法）。两种选法在 9 个符号上不
同（两个库根各一份，共 17 个文件）：

| 符号 | 现行选表 | 只数几何 | 说明 |
|---|---|---|---|
| 电磁阀 `2-way Valve` / `3-way Valve` / `4-way Double Valve` / `4-way Single Valve` | `{6}`，**0 条本体** + `S` | `{46}` / `{45}` / `{129}` / `{48}`，9 / 12 / 18 / 13 条 | 干净表 `Sheet6` 只剩显示层上的 `S`，本体在跨表去重时留给了字面序在前的孪生表 |
| 坡度标签 `Slope Dnwrd / Upward (Angle / Rise & Run)` × 4 | `{6, 37}`，11 条 + `SLOPE` | `{37}`，11 条 | 两张都是干净表；只数几何会把 `Sheet6` 上的 `SLOPE` 丢掉 |
| `MOV-Electrically Operated Valve with Flange2`（仅 `symbols-full`） | `{6}`，6 条 + `M` | `{166}`，7 条 | 无正常视图；`Sheet6` 6 笔 + `M` 与 `Sheet166` 7 笔打平，按表号取 6 |

所以「只数几何」不是答案：它修好电磁阀，却弄坏坡度标签。电磁阀的病根在跨表去重的顺序
（计划 S3）。这些差异不是文字修复带来的：库普查「干净集画不出东西」的 431 在修复前后
不变，说明 `S` / `SLOPE` / `M` 修复前就读得出来。

`bounds()`（所有图元，含隐藏层文字）比显示范围大一倍以上的符号 94 个，其中 49 个多出来的部分
全是文字，多为 `Labels - Equipment\Descriptions` 下的说明标签：模板文字落在一百多毫米外
（`Air Cooler Description.sym` 全部图元 130 × 178 mm，显示 16 × 10 mm）。

**库普查**（`probe_normal_view_too_wide --library-census`）：1262 个符号读出，1120 个有视图集，
868 个有干净集；干净集画不出东西 **431**（不变），管着一张没有图元的表 **163 → 94**；422 张
全开表有笔画，其中 41 张在隐藏名层上有东西、3 张有几何。

## 七、收紧：方向对把关计数，尾型校验长度（计划 S2）

M1 量出两条规则在语料上都不拒任何一条真记录，于是都落进 `symbol_library`：

- **方向对**：`sheet_records` 新增 `igtextbox_letter_height`，单位向量返回 0、字高带内返回字高、
  其余 `None`。绘图侧拒收本来就靠它，现在 `decode_text` 读字之前也问它。计数多读时尾块整体
  后移，「方向对」读到的是尾块之后的字节，不是方向。
- **尾型**：尾后字节按 `+20` 的尾型核对 —— kind 1 必须正好结束，kind 2 必须是 32 字节
  文本框尾再加整数个 8 字节字段，没见过的尾型仍只要求放得下。标志字到字节数的对应量得出
  （§六），但没有做成硬校验：位 26 / 28 从未出现，硬校验会把没见过的组合拒掉。
- `text_end > tail_start` 删掉。库侧读数不变：2864 / 2866，`Text` 图元 2404。

两条规则各管一半：尾型只看尾后还剩多少字节，多读 8 个字（尾块后移 16 字节）的 kind-2
记录仍然「合法」（48 → 32），要靠方向对拒；反过来，尾后只多几个零字节的记录方向对读得
通，要靠尾型拒。单测把这两类都钉了。

## 八、选表：共享笔画留在正常视图那张表上（计划 S3）

M2 的两种候选都不对：现行选表让电磁阀只画一个 `S`，「只数几何」让坡度标签丢掉 `SLOPE`。
病根在 `read_symbol_geometry` 的跨表去重：按流名字面序读表，两张表共有的笔画留给先读到
的那张。`Sheet46` 排在 `Sheet6` 前面，于是电磁阀的整份本体都算到了没有视图集的孪生表
上，干净的 `Sheet6` 只剩显示层上的 `S`。

改法：先读视图集干净（不显示隐藏名层）的表，再读其余，各自内部仍按流名顺序。选表规则
一条没动。

| 读数 | 改前 | 改后 |
|---|---:|---:|
| 电磁阀 × 4 画出的本体 | 0 笔 + `S` | 9 / 12 / 18 / 13 笔 + `S` |
| 坡度标签 × 4 | 11 笔 + `SLOPE` | 11 笔 + `SLOPE` |
| M2「画出的几何不同」的符号 | 9 | 1（`MOV … Flange2.sym` 打平，未动） |
| 53 张备份 1828 对：一致 / 不一致 | 1411 / 367 | **1439 / 339** |
| 被显示规则丢掉的笔画 | 4441 | 4207 |
| 过半被滤的本体 | 343 | 253 |
| `bounds()` 超过显示范围一倍以上 | 94 | 85 |

53 张图逐张比，一致数只升不降：20 张各多 1–3 对，其余不变。`probe_normal_view_too_wide`
的放置打分在同一批输入（53 张备份 + 5 张参考图 + 7 个 fixture）上是 shipped
1554 / 1662 → 1612 / 1629，分母变了：「哪张表能复现缓存」取决于笔画归哪张表，归属一变，可
判的放置也跟着变，所以这里以上表 1828 对的口径为准。

## 八、run 接线：库侧文字按覆盖字符最多的 run 取样式（2026-10-23）

§三 量到的那个洞（1350 条记录的字高停在段落默认）这一轮补上了，用的是绘图侧已经定谳的
规则，而不是另立一条。

### 一条规则，两处共用

`style_link::resolve_text_style` 原本只吃一条 `DecodedIgTextBoxRecord`，而它真正读的只有
三样东西：`+14` 的索引、字符数、runs。把入参收成这三样以后，库侧（手里只有 payload 字节）
和绘图侧（手里是解码记录）调的是同一个函数，包括三处取舍：

- 字高／颜色／字体取**覆盖字符最多的那条 selector-1 run**，并列取标签起始那条；
- 对齐与行距取段落 —— 它们是段落属性，`resolve_run_style` 那条路上恒为 `None`；
- 无 run（形状 1）、run 解析不出（21 条 id 在符号自己的 `StyleCluster` 里没有）、或
  selector-1 长度和不等于字符数时，退回段落默认 —— 那正是厂商模型里
  `TextStyle.CharStyle` 该生效的地方。

库侧也不再自己走一遍 run：`symbol_library::text_runs` 调
`parsers::sheet_records::igtextbox_runs`（提为 `pub(crate)`）。形状 2 的那条在 `+22`
（`count | 0x10000` 就是它的 `(长度, 选择子) `）、形状 3 的那 `A + B` 条在文本之后，都由
同一个读者给出。§二 那个「同一个格式、两个读者」的病根在 run 这一层没有再犯一次。

`SymbolLettering` 多一个字段 `run_style_id`：**这次是哪个字符样式赢的**，`None` 表示
段落默认在答。图内缓存本体的 `SymbolLettering::from_decoded` 走同一条规则 —— 它读的正是
「同一份二进制、另一个表」，两条路径各读一份的话，§二 的病史会原地复发。

## 九、多 run 分区：一条标签逐段上纸（2026-10-23）

§五第一条那个洞（「一条文字只有一个样式槽」）这一轮补到了最后一段：分段不再只记在数据里，
而是**逐段画到纸上**。

### 数据链

| 层 | 承载 | 位置 |
|---|---|---|
| 库 | `SymbolLettering::spans`（`start` / `len` / `style_id` / 字高 / 字体 / 颜色） | `src/symbol_library.rs` |
| 绘图侧共用 | `ResolvedTextStyle::spans`（按 `char` 偏移的分区） | `src/style_link.rs::resolve_text_style` |
| 布局 | `PaperTextSpan`，字高已折成纸张毫米（`height_m * scale * MM_PER_METRE`） | `pid-plot/src/model.rs` |
| 写 PDF | `text_segments` 按 `(字号, 字体)` 切段，每段自己的 `Tf` + `Tj` | `pid-plot/src/write.rs::show_text` |

两条来源（`.sym` 自己的 payload、图纸里缓存的符号本体）在库侧就汇到同一个
`guarded_spans`，所以「同一个格式两个读者」的老病不会再从分区这一层长出来。

### 两条规则

- **切在字号或字体变化处**：只换字体（`Wastewater Pit.sym` 的 `*`）也切，虽然那一段的字高
  与正文相同 —— 切点是 `(字号, 字体)` 两样中的任意一样
  （`a_span_in_another_face_is_cut_at_the_same_size`）；
- **只切真的不一样的地方**：相邻 run 解出同一字号、同一字体时合回一段
  （`spans_that_change_nothing_are_written_as_one_run`）。这既让「样式变了」和「记录
  自己重复了一遍」在纸上不可区分——它们本来就该不可区分——也不给比较器的文字配对多塞几条 run。
- **续行不用自己算偏移**：`Tj` 本身推进文本位置，推进量按**当前字号的字形宽度**算，
  所以第二段正好接在第一段末尾（`a_span_at_its_own_size_continues_where_the_previous_one_ended`：
  首字符画成两倍 body，`second.origin - (first.origin + first.advance) < 0.05 mm`）。
- **非 BMP 时整段撤回**：run 长度数的是 UTF-16 单位，span 偏移数的是 `char`，一条含星形面
  字符的标签会把第二段切在半个字符上。`guarded_spans` 在这种情况下不给分区
  （`a_label_with_a_non_bmp_character_keeps_its_spans_off`），标签照旧按压平后的单一样式排字。

### 为什么明知 0 也接

- 这是「一条文字只有一个样式槽」的最后一层：分区一旦有标签用得上，writer 就会切段，
  不需要再改模型、再改一遍走向；
- 0 是**图纸**上的 0，不是**库**里的 0：分区在库里有 165 条，其中 3 条真的改字样，
  只是它们所在的符号还没被这 58 张图放下；
- 分段对单一样式的标签是恒等变换（切点为空 → 一段），所以「0」与「回归」在这条路上
  不是同一件事：字节数逐位相同正是这一点的证据。
