# 字高找到了：`0x002C` payload `+42`

> 日期：2026-08-04
> 范围：`pid-parse`
> 结论类型：**字段已定位**（值域自证 + 两图交叉 + id 空间对上）；
> 尚未做 native-reader 复核与 promotion。
> 前置：`2026-08-04-stylecluster-record-chain.md`
> 工具：`examples/probe_jsl_text_char_style`

## 1. 布局

`0x002C`（**JSL Text Character Style**，style.dll）payload 里两个已定位字段：

| 偏移 | 类型 | 含义 |
|---|---|---|
| `+14` | `u32` | **样式 id**，每条记录唯一 |
| `+42` | `f64` | **字高，单位米** |

payload 长度有 74 / 80 / 88 / 92 / 94 五种，随内嵌字体名长度变化，
但 **`+42` 在五种长度上都是字高**——字段位置不随 payload 长度变动。

（一处自我更正：初版判定「80 字节档布局不同」，那是判据写错造成的。当时要求
「一桶内全部命中」才报告，而 80 字节档 11 条里有 2 条落在 1mm 以下。改成逐字节扫描
并允许少数例外后，`+42` 在该档是 **9/11 命中**，取值 1.524 / 2.293 / 2.500 / 2.822 /
3.175 mm，同样是标准字高。**没有第二种布局。**）

字体名以 UTF-16 存在较长的 payload 里，实测读出 `"Arial Narrow"`、`"仿宋_GB2312"`。

## 2. 为什么确定 `+42` 就是字高

值域自己证明自己。两张图所有合规档位读出的全部取值（毫米）：

```
1.500  1.588  2.000  2.293  2.464  2.469  2.500  2.540
2.646  2.822  3.175  3.500  3.528  3.704  4.233  6.350
```

逐个对上制图惯例：

| mm | 是什么 |
|---|---|
| **2.500** | **ISO 3098 正文字高**——正是 importer 现在的回退值 |
| 1.588 / 3.175 / 6.350 | 1/16″ / 1/8″ / 1/4″ |
| 2.540 | 0.1″ |
| 2.469 / 2.646 / 2.822 / 3.528 / 4.233 | 7 / 7.5 / 8 / 10 / 12 磅（×0.3528） |
| 1.500 / 2.000 / 3.500 | 整毫米 |

**英制分数 + 磅值 + 整毫米三套体系同时出现**，这是字高才有的取值分布；没有别的
样式字段会长这样。而且 2.500 出现在两张图上，与 ISO 3098 完全一致。

## 3. 与 Phase 35-D 的 join

Phase 35-D 从 **DWG-0201** 的 `igTextBox` trailer 解出稳定样式 id：
`56` → 中文、`64` → 管道号、`21` → 常规标注。

实测 DWG-0201 根 `/StyleCluster` 的 `0x002C` 记录：**48 条，id 取值 4..128 全不重复，
且 `21`、`56`、`64` 三个全部在内。**

| 流 | `0x002C` 条数 | id 范围 | 35-D 的 id |
|---|---:|---|---|
| DWG-0201 `/StyleCluster` | 48 | 4..128 | **21, 56, 64 全在** |
| DWG-0201 `/JSite329` | 35 | 4..106 | 只有 56 |
| 工艺 `/StyleCluster` | 21 | 4..71 | 无 |

DWG-0201 根流全中，这就是 35-D 那三个 id 的归属地。JSite 子文档只带自己用到的样式，
少几个是正常的。工艺那张图没有这三个 id——35-D 的 id 是从 DWG-0201 解出来的，
换一张图有自己的 id 集合，**不能据此说 id 跨图纸稳定**（35-D 原文那句需要复核）。

## 4. 亚毫米的那几条

`+42` 在少数记录上读出 1mm 以下的值：DWG-0201 根流 80 字节档 11 条里有 2 条，
分别是 **0.254mm（= 0.01″）** 与 **0.176mm（≈ 0.5 磅）**。

两者仍是「像单位换算出来的整数」而不是随机字节，所以更可能是**未被引用的模板样式**
或某种缩放基准，而不是读错了字段。**但这一点没有证据，只是观察**；要么按 id 反查
有没有 igTextBox 引用它们，要么等 native-reader 复核时一并回答。

## 5. 还没做的

1. **端到端 join 未验证。** 目前证到「id 空间对得上」，还没证「某条 igTextBox 的
   id=56 → 取到该样式的字高 → 画出来是对的」。要按 refno 逐条对。
2. **字体名字段的偏移与编码规则未定**，只是用「最长 UTF-16 串」启发式读出来的。
3. **native-reader 复核未做。** `style.dll` 在本机，类已定名，与 pid-parse 已解码的
   `JStyleOverride` 是 CLSID 连号兄弟——按 Phase 16 的方法复核一遍，证据等级才够 promotion。
4. 第 4 节那两条亚毫米记录未解释。

**在第 1、3 项做完之前不要 promotion**，也不要把 `+42` 直接接进 OCS 渲染。
