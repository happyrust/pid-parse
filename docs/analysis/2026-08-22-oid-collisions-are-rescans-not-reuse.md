# `(stream, oid)` 碰撞普查：167 条里 166 条是同一条记录被扫了两遍，不换键

> 日期：2026-08-22
> 阶段：索引键健壮性 —— **登记阴性结论 + 加守卫断言**（见 §5）
> 证据等级：**全语料实测**，产物 `examples/probe_oid_collision_census`
> 起点：`2026-08-22-four-labels-have-a-second-line.md` §6 顺带查到的那一例

## TL;DR

三张索引（`LineStyleIndex` / `FillIndex` / `TextHeightIndex`）都以
`(stream path, graphic oid)` 为键，`OpenCADStudio` 也按这一对做 join。上轮偶然
撞到一例两条记录共用一个键，于是本轮把它量全。

原始数字看着吓人，**但拆开之后不是一回事**：

| | line | fill | text | 合计 |
|---|---|---|---|---|
| 记录数 | 673 | 20 | 235 | 928 |
| 键数 | 568 | 15 | 178 | 761 |
| 被两条以上记录占用的键 | 105 | 5 | 57 | **167** |

167 里：

- **166 条的两个字节区间是重叠的** —— 那不是两条记录共用一个 oid，而是
  **同一条记录被扫描器读了两遍**。`PsmRecordDecoder::scan` 逐候选偏移试解，
  一条记录的字节若在前后几字节处也能通过校验，就会再出来一次。这是解码器的事，
  跟 oid 唯不唯一没关系。
- **只有 1 条是真的两条记录**，就是上轮那例。

而那唯一一条真碰撞，**两条记录声明的是同一个 style id（36）**。所以：

**本语料没有任何一次塌陷改变了画出来的东西。不换键。**

## 一、判据为什么用「style id 是否相同」，而不是「解析结果是否相等」

这是本轮唯一一个方法上的选择，值得写清楚。

问「今天这两条解析出来的样式一样吗」是能答的，但那个答案**明天可能就不作数**：
同时有人在定「run 优先还是 para 优先」，215 条里 153 条两者不是同一条样式。口径
一改，「解析结果相等」这个关系本身就得重量。

问「这两条记录**存的是不是同一个 style id**」则不受影响。style id 是几何记录自己
写在 `+14` 的东西；**两条记录指向同一个 id，无论解析器怎么走——一跳还是两跳、
走段落还是走 run——都不可能解出不同的符号学。** 所以本文的结论和 §5 的守卫断言
都按这个口径写，一个具体样式值都不依赖。

今天口径下的「解析结果相等」也一并打印了，作为旁证，两者一致。

## 二、重叠 vs 不重叠：怎么分的，以及为什么这条线要划

一个键被两个**重叠**字节区间占着，例如：

```
DWG-0202GP06-01.pid  /Sheet6  oid 70  [line]  style ids {1}
         igLine2d  bytes     252..308
         igLine2d  bytes     260..316
```

`igLine2d` 是 6 字节头 + 50 字节 payload = 56 字节，两个区间都恰好 56 字节、相隔
8 字节。这只能是**同一条记录在偏移 252 和 260 上各通过了一次校验**，不是图上有
两条线。

这条线划得对不对，是可以被证伪的：**如果它们真是同一条记录，两次读出的 style id
必须一致。** 实测 166 条重叠键里**读法不一致的有 0 条**。若有一条不一致，就说明
「同一条记录」这个解释是错的，得回头重看。

## 三、唯一那条真碰撞，以及它告诉我们 oid 是什么

```
工艺管道及仪表流程-1.pid  /Sheet6  oid 6345  [text]  style ids {36}
  igTextBox  bytes    1615..1799   text "250-LNG-57602- - "     at (0.1705, 0.2215) rot 0
  igTextBox  bytes   46104..46294  text "250-LNG-57602-6D02-C"  at (0.1705, 0.2215) rot 0
```

两条记录**位置完全相同、样式相同、文本不同**——一个是带空位的管线号模板
`250-LNG-57602- - `，一个是填好的 `250-LNG-57602-6D02-C`。

这回答了「oid 到底是什么语义」这个问题，而且回答得比预期干净：

- **oid 是对象身份，不是每族的计数器。** 全语料 761 个键里，**被一个以上索引认领
  的 oid 有 0 个**——一条线和一条标签从不共用 oid。若 oid 是各族各自从 1 开始数，
  跨族撞车会大量出现。
- **这一例不是「两个不同对象撞了同一个 id」，而是「同一个对象在文件里存了两份」**
  ——同一身份、同一位置、内容一新一旧，看起来是被取代的旧版留在了文件里。

所以 oid 的唯一性假设**基本成立**；破例的这一条也不是 id 分配出了问题。这正是
「不该换键」的实质理由：换键是在修一个不存在的病。

## 四、但这一对确实有别的毛病，只是不归本轮

塌陷不改画面，说的是**样式**。至于这两条会不会都被画出来，是另一个问题，答案是
会：

```
工艺管道及仪表流程-1.pid /Sheet6 oid 6345: 2 normalized entit(ies)
  "250-LNG-57602- - "     at (0.1705, 0.2215)  confidence Decoded
  "250-LNG-57602-6D02-C"  at (0.1705, 0.2215)  confidence Decoded
```

**同一点上叠印着两版管线号。** 这是真缺陷，但它的成因是「文件里留着被取代的旧
记录，而解码器两条都收」，**不是键的问题，换键也治不了**——换了键之后照样是两个
实体叠在一起，只是各自拿到自己的样式而已。

登记在此，归属：记录取舍策略（该不该识别并拒收被取代的记录），不在本轮点名文件内。

**同理，那 166 条重扫也登记在此**：它让三张索引的构建多走了 105 + 5 + 57 条记录，
`line` 一族 673 条记录只落成 568 个键。它不改画面（同一条记录读两遍，值一样、键
一样），但它说明 `scan` 的候选偏移偏松。归属：`src/parsers/sheet_records.rs`
的扫描逻辑，本轮按边界不碰。

## 五、结论与落地

**不换键。** 换键要动三张索引加消费侧的 join，而实测：真碰撞 1 条、危险碰撞 0 条、
跨族复用 0 条，换了买不到任何东西。

改为在 `tests/style_link_ratchet.rs` 加一条守卫
`no_key_is_shared_by_records_that_ask_for_different_styles`，钉两件事：

1. **没有任何键被声明了不同 style id 的记录共用**（`conflicting.is_empty()`）
   —— 这条是真正的守卫，它变红就意味着有记录正在被按别人的样式画；
2. **真碰撞（非重扫）不超过 1 条** —— 用 `<=` 而不是 `==`，因为将来若有人收紧
   扫描或识别出被取代的记录，这个数只会往下走，不该因为变好而变红。

断言里**一个具体样式值都没有**，所以 run/para 那一轮定下来之后它不需要重量。

## 六、本轮登记不做

- **不换键**（本文结论）。
- **166 条重扫**：属 `scan` 候选偏移，本轮边界外。
- **叠印的那对管线号**：属记录取舍策略，本轮边界外。
- **未重钉任何既有分布断言**（字高 / 颜色 / 对齐 / 字体 / 行距）——按用户拍板，
  它们可能在 run 优先定下来后整体重量。
