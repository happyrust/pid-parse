> 日期：2026-08-04
> 范围：`pid-parse`
> 结论类型：**native-reader 级证据**——语料侧的字段定位与原生序列化逐字节吻合。
> 前置：`2026-08-04-jsl-text-char-style-height.md`（语料侧）、

## 1. 找到读取序的路径

```text
DllGetClassObject_0 (0x1000F2D0)
  └─ CLSID 47FCC333 @0x1009DDB4 → ClassFactory<JStyleTextChar>
       └─ JStyleTextChar vtable @0x100A1D1C
            ├─ slot 32 (+128)  共享持久化入口 → sub_1007A680
            │    └─ 由 IJPersistImp@JStyleBase vtable @0x100A667C 的 Load/Save 转入
            └─ slot 17 (+68)   类专属序列化 → sub_100323A0
                 ├─ jengine_1076(stream, &CLSID_JStyleTextChar, …)  取版本号
                 ├─ version 2 → sub_10002CFC + sub_10002CC0
                 └─ version 3 → sub_10030A20   ← 本文分析的就是它
```

`sub_100323A0` 里直接引用 `xmmword_1009DDB4`，就是已逐字节核对过的
JStyleTextChar CLSID——**身份没有推测成分**。

## 3. 逐字节对上语料侧的结论

基类部分长度记为 `B`，其后按上表累加：

```text
+B+0   4  (this+396)
+B+4   2  (this+348)
+B+6   2  (this+350)
+B+8   4  (this+356)
+B+12  1  (this+352)
+B+13  1  (this+364)
+B+14  1  (this+365)
+B+15  1  (this+360)
+B+16  8  (this+368)   <-- 唯一的 f64
```

语料侧实测 f64 在 **payload `+42`**，因此 **`B = 26`**。这个值自洽：语料侧的
**样式 id 在 `+14`**，落在 26 字节的基类区内，与「基类持有 id」相符。

**逐项核对：**

| 语料侧观察 | native reader | 结论 |
|---|---|---|
| `+42` 是 f64，值域是 ISO/英制/磅值字高 | 整条记录**唯一**的 8 字节字段 | **确认** |
| 74 字节档变化列含 `42..48` | f64 占 `+42..49`（末字节常量） | **确认** |
| 记录尾部有 UTF-16 字体名 | 长度前缀 + `2×len` 字节 UTF-16 | **确认** |
| `+14` 是每条唯一的 id | 落在 26 字节基类区内 | 相符 |
| 74 字节档变化列含 `30, 31` | `+30` 是 2 字节键盘布局/语言 | **解释了** |
| 74 字节档变化列含 `26, 27` | `+26` 是 4 字节字段的低半 | **解释了** |

**字高的证据等级从 corpus-statistical 提升到 native-reader。**

## 4. 顺带得到的两个新字段

- **`+30`（u16）= 语言 / 键盘布局**。读到 0 时原生代码用 `GetKeyboardLayout(0)` 兜底。
  这解释了中文样式与西文样式为何在这一列上分组——之前列分析看到 `30, 31` 在变，
  但不知道是什么。
- **`+34`（u32）带 `-1` 哨兵**。`-1` 在 IGDS 里是「继承 / ByLevel」的惯用值，
  位置和形状都符合**文字颜色**。⚠ 这是推断，不是结论：原生代码只显示它有
  `-1` 语义和条件归零，没有显示它被当颜色用。

## 5. 仍未做的

1. **version 2 路径**（`sub_10002CFC` + `sub_10002CC0`）没读。语料里是否存在
   version 2 的记录未知——`jengine_1076` 返回的版本号需要在真实流上取一次。
2. **基类 `sub_10003814`（vtable slot 33）没读**，所以 26 字节基类区的内部布局
   仍是推断（id 在 `+14` 是语料侧观察，不是原生佐证）。
3. `0x002E` **JStyleSimpleLine 的读取序没读**——线宽 `+34` 与颜色 `+50` 仍是
   corpus-statistical。路径完全相同（CLSID `47FCC335` @`0x1009DE18` → vtable
   `0x100A18F8` → slot 17 = `0x10002DE9`），下次照做即可。
4. `0x0030` **JStyleOverride 的读取序没读**（slot 17 → `sub_10029DE0`），
   所以「它到底是样式覆盖还是标注锚点」这个质疑仍然开着。

## 6. 复现

IDA 开 `dlls/style.dll.i64`，反编译 `0x10030A20`。
