# 虚线线型解开：`0x002F` 记录布局 + `0x002E +54` 的 join

> 日期：2026-08-07
> 范围：`pid-parse`（Phase 38 S5，缺口 B）

> 两者是两种帧装，分别坐实不同的事，见 §6。
> 前置：`2026-08-04-jstylesimpleline-native-reader-confirmed.md`（同一套 style.dll 路径）、
> `2026-08-04-style-dll-class-chain.md`（族身份四证）、

## 0. 一句话

`0x002F` 是最后一个没解的样式族。它一直没被列分析破出来，因为它**不是定宽行**：
每条记录是「一个计数 + 那么多个 `f64`」，长度随图案而变。native reader 先告诉我该找
这个形状，拿它去语料对字节，一次就中——20 条记录**条条恰好 `50 + 8N` 字节**。

## 1. 路径（native reader）

与 `JStyleSimpleLine` / `JStyleTextChar` 完全同构，走的是 §class-chain 那份已打通的
`style.dll` 类链：

```text
CLSID 47FCC336 @0x1009DE90  →  ClassFactory<JStyleSimpleDashType>
  └─ JStyleBase::IJPersistImp 适配层（全是 thunk，转发到外层类 vtable 固定偏移）
       └─ 外层 +128  共享帧架  →  派给 +68 逐类 worker（Dash = sub_1001BB50）
            └─ 版本分发后逐字段调 jengine_1075(stream, size, ptr) 读写同体
```

CLSID 的 16 字节已逐字节核对：`{47FCC336-2D0F-11D0-A1FF-080036A1CF02}`，正是
type code → CLSID 表预测的 `47FCC336`；对照组 `0x002E` 在 `@0x1009DE18` 读出
`47FCC335`，也对。**族身份此前已四证（CLSID 表 / jutil / RTTI / 类工厂），这里再加一条
序列化器自证。**

## 2. version-2 的字段序列（native reader）

`JStyleSimpleDashType` 的 `+68` worker，版本 2 在基类块之后写：

```text
jengine_1075(stream, 4, …)          （未命名）
jengine_1075(stream, 4, N)          虚线段数
  N × jengine_1075(stream, 8, …)    虚线图案本体   ← N==0 时整段不写
jengine_1075(stream, 4, …)          标志
jengine_1075(stream, 8, …)          （比例 / 总长）
jengine_1075(stream, 4, …)          标志 bit4 的副本
```

版本 3 = 版本 2 再加一个 `u32`；版本 4 全交基类。

**「一个计数紧跟 N 个 double」本身就是虚线图案该有的形状**，也解释了为什么列分析
（假定定宽）从来对不齐它：它是变长记录。

## 3. 记录布局（corpus）

把上面的形状按 `.pid` 的帧装落到字节上，语料里全部 20 条 `0x002F` **条条吻合**：

```text
+0 .. +47   固定头（样式 id 在 +14，与 0x002C / 0x002E 同偏移、同语义）
+48   u16   N，虚线段数
+50   f64[N]  虚线图案
```

即每条记录**恰好 `50 + 8N` 字节**。这是个很硬的判据：读错一个字段、或计数错一位，
就会在某条记录上留下余数。66 / 82 / 98 三种长度分别对应 N=2 / 4 / 6，一条不差。

与 DLL 自己的流唯一的差别在编码宽度：DLL 里计数是 `u32`，`.pid` 里是 `u16`，且图案
之后直接截止（没有 §2 里那几个尾字段）——这正是 §6 说的「两种帧装」。

### 3.1 解出来的图案

| 图案（mm） | 出现在 | 判读 |
|---|---|---|
| `-3.5000, -1.7500` | 六个流，最常见 | 公制虚线，3.5mm 划 / 1.75mm 空 |
| `-1.9050, -1.2700` | 四个根流 | 0.075″ / 0.05″ —— **英制**虚线 |
| `-7.0000, +1.7500, +0.3500, +1.7500` | DWG-0202 | 点划线（链线） |
| `-14.0000, +1.7500, +0.3500, +1.7500, +0.3500, +1.7500` | DWG-0202 | 双点划线 |
| `0.0000, +1.5875, -3.1750, +1.5875` | DWG-0202 | 首元素长 0 = 一个点；1/16″ 与 1/8″ |

**能从同一个偏移里同时掩出整数毫米档与整分数英制档，不是噪声能凑出来的。**
符号（正负交替）是格式自带的，本模块原样保留、不解释——`style.dll` 里还没有哪处
说清哪个符号画、哪个跳，只需要重复周期的渲染器可以用绝对值。

## 4. join：哪根线用哪个图案（native reader 定存在，corpus 定偏移）

native reader 说：`JStyleSimpleLine` 把虚线类型当一个**惰性解析的 id** 持有——对象里
`+104` / `+120` 两个 u32 是 id，各自旁边 `+100` / `+116` 缓存解析后的对象指针，getter
首次访问时解析、setter 在 id 变化时丢弃缓存。解析 `+104` 那个用的接口 IID 是
`EA1ACBD2`，它的全部使用点都落在 `JStyleSimpleDashType` 的实现地址段内——所以 `+104`
就是虚线引用。**id 一定被写进线样式记录里，所以语料里必有一列是它。**

corpus 把这一列钉死在 `0x002E` payload 的 **`+54`**：

- 对每个流，统计「`+54` 落在本流虚线 id 集合里」的线样式记录数，**恰好等于该流定义的
  虚线样式数**——最富的流 4 配 4，另外六个流 1 配 1。跨 10 个流是干净双射。
- 其余任何 u16/u32 偏移都够不上：唯一的杂音是某流 `+27` 上 8 中 1，字节重叠的巧合。
- 只有 58 字节那档 `0x002E` 有空间容下 `+54` 的 u32——所以**画虚线的线样式必然是长档**，
  短档（54 字节）本身就没有这个字段，读出来就是「实线」，与「不画虚线」同义。

**判据不是命中率**（§8.1 的教训）：是「计数列的势恰好等于虚线样式的势」这个双射，
以及 `50 + 8N` 的逐条零余数。两条都可证伪。

## 5. 端到端：渲染器现在真的拿到虚线

`style_link` 现在解析链尾多返回一个 `dash: Option<DashPattern>`。跑 `probe` 的
end-to-end 段（`line_styles_for_file` → `resolve_line_style`），真图上：

| fixture | 带虚线 / 画出记录 | 解出的图案 |
|---|---|---|
| DWG-0201 | **15 / 138** | 14× `-3.5/-1.75mm`、1× `-1.905/-1.27mm` |
| DWG-0202 | **9 / 101** | 8× `-3.5/-1.75mm`、1× 英制 |
| D06 | **1 / 16** | 1× 英制 |
| 工艺管道-1 | 0 / 303 | 该图线样式全解析为实线 |
| A01 | 0 / 6 | 同上 |

这不是「知道图案值在哪」，是「哪根线画成哪种虚线」——缺口 B 从自证推到了画面。

## 6. 为什么写「两种帧装」

`0x002E` 的线宽/颜色，native reader 里的字段间距（id 后紧跟宽、宽后紧跟色）与语料里的
偏移（`+14 → +34 → +50`）**对不上**，但字段的存在与先后一致。虚线这里同理：DLL 流里
计数是 u32 且尾部还有标志字段，`.pid` 里是 u16 且截止在图案末尾。

结论不变、也不削弱：**native reader 给的是字段清单与读写顺序**（该找什么形状、有没有
这个引用），**语料给的是这份帧装在 `.pid` 里的字节偏移**（`+48` 的 N、`+50` 的图案、
`+54` 的 join）。两者各自可证伪，合起来把 `0x002F` 钉死。

## 7. 仍未做 / 边界

1. **符号语义**（正=划还是正=空）未从 `style.dll` 定论，见 §3.1；渲染只需周期时无碍。
2. 两张图（工艺管道-1、A01）读出 0 条虚线。解码经 20/20 语料自证、join 经双射自证，
   所以这是「该图本就没有虚线样式被引用」，不是漏读；但没有第三方语义可他证这两张
   「确实全实线」，留作观察。
3. `0x002A` / `0x002B` 填充仍未取证（缺口 E，Phase 39）。
