## 1. 问题

08-27 把空间图翻成入边索引之后，tag 188 那一行是「引用者 `0x0115`，条目 id 在 payload 多处，42/46」。
09-14 从 JDim 这一侧读出五个引用槽并起了名。若 `+92` 真是被量的几何，那么每一条 tag-188 成员、
只要条目是 `Line` / `Point`，就**必须**落在 `+92`（或它的第二块同形 `+202`）而不在别处；反过来
任何 `JDimGroup` 都不该落在那里。若偏移与条目的类无关，§5 的命名就被否掉了。

## 2. 方法：逐条 join，不抽样

1. 走四主图每个 `PSMspacemap` 段，取所有 tag 为 188 的活成员（46 条；D06 17 / 0201 13 / 工艺 16；
   0202 与 08-27 一致为 0）。
2. 每条成员的 `value` 在**同一存储**的记录里解出来，核实确是 `0x0115`——46/46 是。
3. 在那条 JDim payload 里按每个偏移扫条目 id 的 `u32`，每个命中连同其后四字节处的 `u16`（§5 说的标记字）
   一起报出。
4. 条目 id 也解到它自己的记录，于是每行都写着尺寸指向的是什么类。

定义沿用 §5：**引用槽 = `u32` 命中同存储某对象、且其后跟一个非零标记字。** 标记字为零的命中不算槽。

## 3. 整账：46 = 40 落槽 + 2 假命中 + 4 不在 payload

| 偏移 | 命中 | 角色 |
|---|---:|---|
| `+92` | **29** | 被量的几何 |
| `+202` | **10** | 被量的几何，第二块 |
| `+280` | **4** | 被量的几何，主区末尾（§8） |
| `+49` / `+65` / `+161` / `+177` / `+193` | 4 / 6 / 4 / 2 / 2 | **不是槽**：标记字全 0（§4） |

46 条成员里 **42 条的条目 id 出现在 payload 某处**——这就是 08-27 的 42。但其中 **40 条落在一个具名槽里，
2 条只落在非槽字节上**；再加 4 条 id 根本不在 payload 里，**无槽成员共 6 条**（§5）。

**槽预言类，零反例**：

| 槽 | 标记字 | 指向 |
|---|---|---|
| `+92` | `0x00CB` ×27、`0x00F0` ×2 | `Line Object` ×27、`Point Object` ×2 |
| `+202` | `0x00CB` ×4、`0x00F0` ×6 | `Line` ×4、`Point` ×6 |
| `+280` | `0x0044` ×1、`0x0045` ×3（见 §8） | `Line` ×4 |

标记字对类：`0x00CB → Line` **31/31**，`0x00F0 → Point` **8/8**。每个几何槽都指向 `Line` / `Point`，
没有一条指向 `JDimGroup` / 约束 / 属性集。**§5 对 `+92` / `+202` 的命名成立，且 08-27 那行「多处」
其实就是这三个偏移。**

槽与成员的算术也对得上：一个 `+92` / `+202` 槽在目标条目上产生**两条**成员，一个 `+280` 引用产生
**一条**——26 对（JDim，目标）里 20 对严格相符，6 对多出一条成员，正是 §5 那 6 条。

## 4. 两条假命中：`0x3F` 是 f64 的指数字节

D06 里 oid 63（`Point Object`）被 JDim 18 / 21 各「命中」四处（`+49` / `+65` / `+161` / `+177`），
标记字全 0。看字节就明白：`3F 00 00 00`——`0x3F` 是紧挨着它前面那个 f64 的最高字节（指数），
后面跟三个零字节。`+49` 结束的是 `+42` 的尺寸值 0.03556，`+65` 结束的是 `+58` 的 4.88e-4，
`+161` / `+177` / `+193` 结束的是块区里的 0.13589 / 1.0 / 0.127。**这两条根本不是引用**，08-27 的 42 应读作 40。
只有 id 恰好等于 63 = `0x3F` 的对象才会撞上这一点，别的图没有同类现象。

## 5. 六条无槽成员，6/6 是组里另一条尺寸量的几何

| 图 / 存储 | 条目 | 成员挂在 | 实际量它的是 | 两条尺寸同属的组 |
|---|---|---|---|---|
| D06 `/JSite145/` | 57 `Line` | JDim 24 | JDim 19，`+202` | 28 |
| D06 `/JSite145/` | 63 `Point` | JDim 18 | JDim 24，`+92` | 28 |
| D06 `/JSite145/` | 63 `Point` | JDim 21 | JDim 20，`+202` | 29 |
| 0201 `/JSite329/` | 72 `Line` | JDim 40 | JDim 38，`+202` | 48 |
| 工艺 `/JSite7559/` | 90 `Point` | JDim 94 | JDim 109，`+202` | 69 |
| 工艺 `/JSite7559/` | 90 `Point` | JDim 108 | JDim 67，`+202` | 68 |

每一条：成员挂着的那条 JDim 自己没有槽指向该条目，但**同一 `JDimGroup` 里的另一条 JDim** 在 `+92` / `+202`
量着它。组共享的几何，空间图把入边记到了兄弟尺寸头上。**08-27 的「4 条未命中」由此有解释**（连同 §4 的
两条，6 条全部落在这一条规律上，0 条例外）。组记录本身的 payload 里**没有**这些几何的 id。

## 6. 尾字 = 所属 `JDimGroup` 的 oid，组回指 6/6

09-14 §2 从 `radsrvitem.dll!sub_564BB990` 坐实了尾字**在哪**（`+34+main_len`，仅当 `+26` 含 `0x0100`），
但没说它**是什么**。语料 18 条里 13 条带尾字（D06 5、0201 2、工艺 4、A01 2），**13/13 解到同存储的
`0x0058 JDimGroup Object`**，且每个存储里取值不同（28 / 29、48、68 / 69、88）。

从组那一侧回验：`JDimGroup` 记录 34 / 38 字节，`+24` u16 是成员数，`+26` 起每 4 字节一个 u16 oid
（读法是语料的，只为了闭环）。**六个组，成员表与「尾字指向我」的尺寸集合逐个相等**：

| 存储 | 组 | 尾字指向它的 JDim | 组列出的成员 |
|---|---|---|---|
| D06 | 28 | {18, 19, 24} | {18, 19, 24} |
| D06 | 29 | {20, 21} | {20, 21} |
| 0201 | 48 | {38, 40} | {38, 40} |
| 工艺 | 68 | {67, 108} | {67, 108} |
| 工艺 | 69 | {94, 109} | {94, 109} |
| A01 | 88 | {97, 98} | {97, 98} |

不带尾字的 5 条（`0x0041` / `0x0051`）不指向任何组，六个被指向的组的成员表里也没有它们。**尾字从「未坐实」
升到「语料互证」**：它是这条尺寸所属组的 oid。

## 7. `+140` 不是引用

§5 把 `+140` 读成「归属的组 / 约束 / 属性集」，依据是 14/18 解到了某条记录。并排之后它过不了引用该过的两关：

- **取值不随存储变。** 四个独立索引空间（D06 / 0201 / 工艺 / A01）里 `+140` / `+250` 共 24 个值，
  **只有 48（×20）与 16（×4）两个**。真 oid 从各存储自己的索引空间里取，不会四个文件都是 48。
- **解到的类各不相同。** 48 在 D06 是 `Vertical Constraint`、在 0201 是 `JDimGroup`、在工艺是 `JSheet`、
  在 A01 **解不到任何记录**；16 在 D06 是 `FreeFormAttrSet`、在工艺解不到。这是「小整数碰巧撞上某个 oid」
  的形状，不是引用的形状。
- 09-14 已经记下它的标记字 `0x0067` / `0x008C` **不跟类走**——而几何槽的标记字与类一一对应。

空间图对它零成员（任何 tag 下都不记 JDim → 那个对象的边）。但**同样的检查尾字也不过**：JDim → 组这条边
空间图也不记（13/13 组条目上没有以 JDim 为 value 的成员），所以空间图不能作为「是不是引用」的判据；
`+140` 的否定靠的是前两条。**它是什么**没有答案——48 / 16 = `0x30` / `0x10`，像一个标志或长度，留 raw。

## 8. `+280`：主区末尾一个裸引用，后面那个「标记字」是尾字

工艺两条 288 字节记录（JDim 67 / 109）在 `+280` 指向 `Line 93`（JDim 109 的 `+92` 也是 93——同一条线量了两次），
其后的 u16 是 `0x0044` / `0x0045` = **68 / 69 = 这两条尺寸各自的组 oid**。也就是主区在 `+284` 结束、
尾字紧随，`+280` 是**不带标记字**的最后一个 u32 引用；09-14 §5 记的「与尾字重叠」说的正是这一点。
没有新的标记字族。

## 9. A01 交叉核对：格式的性质，不是这四个文件的

导出件 `A01.pid`（`/JSite39/`，4 条 JDim，11 条 tag-188 成员，不在 08-27 的 46 里）：10 条落槽
（`+92` ×8、`+202` ×2，全 `0x00CB → Line`），1 条无槽成员（136 ← JDim 97）是组 88 里 JDim 98 在 `+202`
量的线；组 88 回指 {97, 98} 相符；`+140` 五个值全是 48、全解不到记录。四条规律一条不差。

## 10. 对 J2 DTO 的结论（更新 09-14 §7 的两栏）

| 字段 | 09-14 | 现在 | 等级 |
|---|---|---|---|
| `+92` 被量的几何 + 标记字 | 坐实 | **坐实**，空间图 40/40 背书、槽预言类零反例 | corpus，双向 |
| `+202` 第二块同形 | 坐实 | 坐实，同上 | corpus，双向 |
| 尾字 `+34+main_len` | 位置坐实、含义未坐实 | **所属 `JDimGroup` 的 oid**，组回指 6/6 | corpus，互证 |
| `+140` / `+250`「归属」 | 坐实 | **不是引用，出 DTO**（字节仍在 `raw_tail`） | — |
| `+280` | 与尾字重叠 | 288 形的末尾裸引用，留 raw（块内文法未解） | corpus |

按 D3：`+140` 以 `owner` 之名进了 `15aa915` 的 DTO，应当撤下；尾字改名为组引用；`+92` 不动。
