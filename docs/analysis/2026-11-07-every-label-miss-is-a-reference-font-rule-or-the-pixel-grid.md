# 逐条文字残差普查：偏差出自 72 单位参考字体的落点规则，余下的是参考图的像素网格（2026-11-07）

## 结论

11 张原厂参考图整页比对（不加图框掩膜，只排除缺失符号框），比对器配上 4307 对文字（参考侧 4331 条 run 中配上 4318 条，A2 未配的 13 条另有源侧记录）。按「锚点位置偏差 > 0.15 mm 或整串宽差 > 0.05 mm」筛出 **2399 对**：位置超限 456 对，宽度超限 2046 对，两者都超 103 对。读数基于 `main` `f7ea986`（参考图按裁剪读墨迹之后）；裁剪前的 `1dfa33e` 上是 2391 对，差的 8 对都是 `line-metrics` 的临界条。

逐条归类后，2397 对有明确原因，1 对是两条各自放置的标签合成一串时带了两次像素取整，1 对没有解释（1 px）。原因归结成一件事：**RAD `render.dll` 的文字落点全部量在 72 单位参考字体上**，而我们有几处用了嵌入字体自己的度量、或者把规则只实现了一半：

- 水平方向：框宽是存储值（含尾随空格）在参考字体上的连续宽度 `size72.cx × a8`，由锚点码挂在插入点上；行是去掉尾随空格、保留前导空格的字符串，按段落对齐放进框里；串内每个字的前进是整像素的 `lpDx`，PDF 里写成每串一个 `Tc`。
- 竖直方向：基线下落是参考字体的 `tmAscent`、`tmDescent`、`ADMXZ` 大写高（`asc72`/`desc72`/`cap72`）乘 `a8`；大写字高样式的中线是 `0.5·(asc72 − desc72)`，不是半个大写高；升部字高样式（符号里的阀门 `M`、电磁阀 `S`、电机 `M`）的中线反过来是半个大写高 `0.5·cap72`。竖直码 8（`igVerticalShapeCenter`）挂在一行框的中线上，框高是段落的一个行距，行距方式取段落样式的 `+28`：按升部排行（10 pt 设备位号）时中线在半升部 `0.5·asc72`，按整个字格排行（其余段落）时是格中线。
- 起点按 150 dpi 取整：参考图 4331 条有墨 run 的起点全部是 0.48 pt 的整数倍（从页面左下角量）。设备把纸宽铺成 `floor(W·150/25.4)` 个整像素，两轴同一比例，起点在这个网格上只取整一次（见「像素网格」）。

用这套模型重建参考图（探针里的 `model_*` 列），起点 4295 对中 4291 对残差 ≤ 0.12 mm，各类残差均值在 ±0.05 mm 内、标准差 0.019–0.058 mm，正是 1/150 in 网格均匀取整的理论值 0.049 mm；基线 4227/4295（不吻合的 59 对是下面的 10 pt 设备位号，模型没读段落的行距方式，见第 7 项；其余是 `℃` 借字）；串内字距：横排两字串 1101/1101、三字以上 2608/2626 与 `lpDx` 模型相差 ≤ 0.005 pt；三字以上的旋转串逐字落在各自的 `lpDx` 位置，176/180 在 0.5 px 内（另 4 条是两条标签被读成一串）。

第 1–6 项、像素网格（第 8 项）和升部字高中线修完后超限 124 对（见「修复清单」）。十张标准幅面图上配上的 4059 条 run 里，除 57 条 10 pt 位号中线（第 7 项）和 11 个借字 `℃` 外，3991 条起点与参考逐像素相同。第 7 项（段落行距方式）修完后超限 68 对，59 条 10 pt 位号的竖直残差从 −0.542 mm 降到均值 +0.008 mm（−0.047 至 +0.021 mm），在网格取整范围内。第 9 项（字距在设备纸面上取整）修完后超限 64 对，`AC-01031A/B/C` 与 HxCD `25-CI-1450-B5-` 的字距与参考逐像素相同，全语料只有这 4 条 run 的 `Tc` 变了。

本主题在 `b23b04c` 收口：剩下 64 对逐类为什么不修或待复核，以及 docs 门禁那 11 条旧错误不是回归的对照方法，见「收口记录」。

## 普查方法

探针 `pid-plot/examples/probe_why_paired_labels_miss_the_reference.rs`：

```text
cargo run -p pid-plot --example probe_why_paired_labels_miss_the_reference -- <out-dir>
CAUSE=leading-pad cargo run -p pid-plot --example probe_why_paired_labels_miss_the_reference -- <out-dir>
```

它按验收测试的流程排出 11 张图（`PID_ACCEPTANCE_CORPUS`，默认 `验收数据`），整页比对，逐条读取 `compare.rs` 新公开的配对明细 `CompareReport::text_pairs`（`TextPair`：两侧 run 下标、类别、来源、along/down/advance），再从两侧 PDF 逐字形读回字体名、字号（体高）、横向缩放和每个字后的字距，写出 `pairs.tsv`（全部配对）和 `flagged.tsv`（超限的），并打印按图、按原因的计数和模型检验。`TextPair` 只是把 `match_text` 原本就做的配对暴露出来，类别均值仍由同一串配对按同一顺序求和，`text_offsets` 逐位不变。

- 位置偏差取锚点对应点：左锚是基线起点，居中是起点加半个串宽，右锚是终点；整串宽度是从首串原点到末串终点。
- 来源按「锚点会把这串挂在哪」重新找：比对器自己的来源窗口是 20 mm、量的是串起点，长串和方框字段会落空（整页 96 对是 `unknown`，重新找回 84 对，类别写作 `unknown~锚点/线`），相邻两个同名标签也会互换插入点。
- 段落对齐和原始锚点码从 `.pid` 重新解析（`style_link::text_styles_for_document`）。

## 各类的依据

### 两字串的字距（`two-glyph-spacing`，1276 对）

`I` 井场 `HS`（`/Sheet6` 291281..291359，Arial Narrow 7 pt）：参考 `Tc −0.260`，`lpDx` 模型 `−0.2608`，我方 `0`，串宽多 0.090 mm。同类有 `LT`、`XL`、`PG`、格网号 `B2`/`E5` 等，全语料横排两字串 1101 条参考 `Tc` 与模型相差都在 0.005 pt 内（标准差 0.0005 pt）。

`render.dll` `sub_1007EF20` 在 `0x1007f153..0x1007f1a4` 决定是否传 `lpDx`：只有 `lfCharSet ≠ SYMBOL`（NT 下）、`n < 3`、`(a7 & 0x7F000000) == 0` 同时成立才传空指针，此时用 GDI 设备字体自己的前进。两条路给出的都是**整像素**前进：本机 GDI 量 Arial Narrow `lfHeight = 24`（7 pt 的单元格）时 `H S L T X P G N C 1` 的前进是 `12 11 9 10 11 11 13 12 12 9`，与 `round(72 px 前进 × a8)` 逐个相同。我方 `n < 3` 时用嵌入字体的小数前进（`W × em`），`Tc = 0`，这是要改的规则：横排一两个字的串也按整像素前进排，`Tc` 的算法与长串相同。

### 前导空格（`leading-pad`，673 对）

`I` 井场 ` 1001501B`（`/Sheet6` 288853..288945，存储值带一个前导空格，居中）：参考 run 的第一个字形就是空格，9 个字形，`Tc −0.210`；把空格算进 `lpDx` 模型给 `−0.2098`，我方裁掉空格后是 8 个字形、`−0.2512`。居中也按含空格的整串算，所以参考的可见墨迹比我方偏右半个空格：ink along −0.27…−0.35 mm，宽度少 0.10 mm。

`write.rs` 现在的注释说参考图「不为填充空格画 run」，这对尾随空格成立（全语料参考 run 没有一条以空格结尾），对前导空格不成立。改法：前导空格作为字形保留在串里（参与 `lpDx`、`Tc` 和对齐宽度），只去掉尾随空格。

### 尾随空格与段落对齐（`trailing-pad-paragraph`，153 对）

`I` 井场 `L=200mm `（`/Sheet6` 150528..150618）：锚点码 `0x01`（左/升部），段落对齐居中，存储值有一个尾随空格。参考起点在插入点右边 0.419 mm，模型 0.393 mm（半个空格的连续宽度 `14 × a8 / 2`），我方在插入点上。同一字符串右锚的那条（`0x21`）参考终点在插入点左边半个空格。分组看得很清楚：

| 锚点码 / 段落 | 尾随空格 | 条数 | 参考相对我方 |
|---|---|---:|---|
| `0x01` / 居中 | 有 | 132 | 右移 0.388 mm |
| `0x21` / 居中 | 有 | 9 | 左移 0.366 mm |
| `0x01` / 左 | 有 | 105 | 0.007 mm |
| `0x01` / 右 | 有 | 2 | 0.038 mm（`right_pad` 已处理） |

规则：框 = 存储值（含尾随空格）的连续宽度，按锚点码挂在插入点；行 = 去尾随空格的字符串，按段落对齐放进框，行起点 = −f锚·W框 + f段·(W框 − W行)。`right_pad` 是其中「左锚 + 右段落」那一种。`H=120℃ ` 这类带借字的同样属于这一类。

### 居中/右对齐的退量（`aligned-extent`，首要 22 对，涉及 2081 对）

`render.dll` `sub_1000bcd0`（经 ILT `0x100023f6`）居中退 `0.5 × size72.cx × a8`，右对齐退 `size72.cx × a8`，`size72` 是 `GetTextExtentExPointA` 在 72 单位字体上量的宽度（`0x1007f28d`）。这个宽度是连续值，不等于实际排出的宽度。我方用自己排出的宽度（前 n−1 字 `lpDx` 加末字自然宽）：Arial Narrow 的末字自然宽普遍比 `lpDx` 大约 5%，居中标签因此平均偏左约 0.05 mm；模板 SimSun w800 的 3.2 mm 字每个汉字自然宽 22 px、连续宽 21.51 px，居中字偏左约 0.09 mm，右对齐的 `设计证书号`、`勘察证书号` 偏左 0.23 mm（上表 ours−m）。参考相对模型在这些类里都只剩像素取整。单独超限的 22 对是这 0.05–0.1 mm 碰上取整方向（`PIA`、`MOV`、`FIQ` 这些标签在符号里位置固定，取整方向每次一样）。

### 竖直线位（`line-metrics`，首要 120 对，涉及 290 对）

`sub_1000bcd0` 的竖直码（`a7` 的 `(a7>>24)&0xF`，由记录的锚点字节直接打包，`0x10049030`）：0 基线，1/7 升部 `asc72`，2 大写顶 `cap72`，3/8 半升部 `0.5·asc72`，4 半大写 `0.5·cap72`，5 格中线 `0.5·(asc72 − desc72)`，6/9 降部 `desc72`。三个量都来自 `sub_1000C880` 建的 72 单位字体（`tmAscent`、`tmDescent`、`ADMXZ` 的 `gmptGlyphOrigin.y` 均值并钳到 `tmAscent − tmInternalLeading`），再乘 `a8`。

| 线位 | 模型 / 样式字高 | 参考实测 | 我方现在 |
|---|---|---|---|
| Arial Narrow 升部 | 58/44 = 1.318 | 1.317 | 1.288（字体表 `ascent/H 顶`） |
| Arial 升部 | 58/46 = 1.261 | 1.259 | 1.264 |
| SimSun 中线 | (62−10)/2/49.2 = 0.528 | 0.521–0.537 | 0.500 |
| 仿宋 中线 | (62−10)/2/48.2 = 0.539 | 0.535–0.538 | 0.500 |
| Arial Narrow 中线 | (58−14)/2/44 = 0.500 | 0.497 | 0.500 |
| 符号字 Arial（升部字高）中线 | 半个大写高 23/58 = 0.397（第 5 项之后的例外，见下） | 0.37–0.40 | 0.396 |
| 符号字 Arial（大写字高 5.08 mm）中线 | 22/46 = 0.478 | 0.479 | 0.500 |

代表样例：模板 `审  定`（SimSun 3.2 mm 居中/中线）参考基线在插入点下 1.743 mm，模型 1.691，我方 1.600，我方偏高 0.14 mm；`L=200mm` 升部线我方偏高 0.04–0.08 mm。改法：`FaceHeights::drop` 改为 72 单位字体的度量（`REFERENCE_CAP_PX` 的 `cap72`/`asc72`，`desc72 = 72 − asc72`）。

### 10 pt 设备位号的中线（`tag-middle`，59 对）

`V-10019`、`P-10015B`、`IE-10019`、`AC-01031A` 这批 Arial Narrow 10 pt 位号（锚点码 `0x48`），参考基线在插入点下 0.656 个样式字高（`V-10019`：2.330 mm），半升部 `29 × a8` 给 2.325 mm；同样 `0x48` 的 7 pt 位号（`MOV`、`1001101D`、`LV`）是 0.498，格中线。两批记录的 `igTextBox` 字节结构完全相同，区别只在引用的样式：10 pt 引段落样式 61 / 字符样式 62，7 pt 引 16 / 17。两条 `JStyleTextPara`（96 字节）只在载荷 `+28`（`0x0011` 对 `0x0012`）、`+30`（`0x0601` 对 `0x07E1`）和 `+38`（59 对 12）不同。`render.dll` 的版式引擎（`0x1004da00` / `0x1004e110`）对竖直码 8 先把框上移半个框高再下落一行，框高取自段落的行距方式；框高为 `asc + desc` 时得格中线，为 `asc` 时得半升部。这三个字段里哪一个是行距方式还没在 `style.dll` 里对上，所以本类列为「我方、字段待解码」，CT-6 只在字段确认后修。

**已解（第 7 项，`ce9959a`）**：行距方式是 `+28`。`style.dll` 读 `JStyleTextPara` 的 `sub_100337A0` 把 `+26` 处的 `u32` 只留高半字，即 `+28`，存进对象的 `0x15C` 槽；`IJStyleTextParaImp` 虚表第 24 项 `GetLineLeading`（`sub_10033580`）把它和 `+66` 的行距倍数一起返回，第 10 项 `SetLineLeading`（`sub_10033EF0`）把两者一起写入。取值是 `Interop.RAD2D.dll` 的 `LeadingTypeConstants`：16 `igLinespacingFractionCap`、17 `igLinespacingFractionAscender`、18 `igLinespacingFractionTile`；`render.dll` 排行时在 `0x1004277B` 按 1、2、17、18 分支。11 张图的全部文字框里，`+28` 为 17 的只有这 59 条 10 pt 位号的段落，其余段落都是 18；`+30` 的 `0x0601` 也出现在落在格中线的仿宋、宋体段落上，不是区分字段。竖直码 8 是 `TextVerticalJustificationConstants` 的 `igVerticalShapeCenter`，一行框高一个行距：按升部排行时中线在半升部，按整个字格排行时在格中线，与两批实测相符。修法：`style_link::LineLeading` 读 `+28`（只认这三个 `Fraction` 值，其余拒读），随段落样式进 `ResolvedTextHeight` / `ResolvedTextStyle`；`pid-plot` 的 `TextLine::from_paragraph` 对竖直码 8、按升部排行的段落取 `TextLine::HalfAscender`（`FaceHeights::drop` 里的 `0.5·asc72`）。修后 59 条的竖直残差从 −0.542 mm 降到均值 +0.008 mm（−0.047 至 +0.021 mm）。

### 旋转串逐字落位（`rotated-glyphs`，首要 40 对，涉及 232 对）

参考把旋转 90° 的串拆成单字，每个字一个 `Tm`（带约 1.008/1.012 的等比缩放，#15 已登记），位置就是 `lpDx` 累计值：`I` 井场 `40-WO-1001405-B5-EH40` 的 21 个字落在 `0 15 30 38 64 84 93 108 123 137 152 167 181 196 205 222 237 245 263 282 296` px，与模型逐个相同；全语料三字以上的旋转串 176/180 在 0.5 px 内，另 4 条是两条标签被读成一串。我方整串一个 `Tj`，`Tc` 按精确 em 算而 `Tf` 落在 0.03 pt 网格，逐字累积约 0.04 mm，再加末字缩放差，串宽少 0.06–0.07 mm。两字旋转串里 185 条 Arial Narrow（`NC`、`1"`）的第二个字比 `lpDx` 远整 1 px，等于设备字体未提示宽度取整（`N`：12.54 → 13 px），即 `lpDx = NULL` 那条路（版式引擎发出的行锚点字节为 0）；另 40 条 SimSun 模板两字串两种算法结果相同。改法：旋转串逐字定位到 `lpDx` 位置（两字串用取整的自然前进）。

## 像素网格

参考图的文字起点是设备像素。设备把整张纸宽铺成 `floor(W·150/25.4)` 个 1/150 in 像素（A0 的 7021.65 个画成 7021，A1 的 4966.54 个画成 4966），两轴按同一比例 `k = floor(Wpx)/Wpx` 从页面左下角缩放，每条 run 的起点在缩放后只取整一次到整像素，Amyuni 按 0.48 pt 写出。用这条规则预测，十张标准幅面参考图上配上的 4059 条 run 中 3991 条起点与参考逐像素相同（两轴都在 0.02 mm 内）：模板字正排 154/154、旋转 84/84，图纸字旋转 290/290，符号字正排 116/116、旋转 27/27，来源待定的旋转串 12/12，图纸字正排 3308/3319。不中的 68 条是 57 条 10 pt 位号中线（第 7 项）和 11 个借字 `℃`（横向恒差 +0.65 px，竖直为 0）。

另外两种取整都对不上：插入点和对齐偏移各自取整到像素只命中 57%，在我方 1:1 的页面坐标上取整只命中 12%（那一版普查超限 953 对）。`render.dll` 在 `0x1007ef6b`、`0x1007ef93` 和 `0x1007f3a5..0x1007f3d4` 的两次 `+1.5·2^52` 就近取整因此不在设备像素上，单位应当更细（推测是 1/2400 in 的逻辑单位，未在代码里确认）。比对器整页拟合出的尺度约 1.0001，就是 `1/k` 混了模板线条的结果。

我方实现（`write.rs::device_scale`、`on_the_device_grid`）：页面是标准幅面（`STANDARD_SHEETS_MM`，横放或竖放）时，`show_text` 把 run 起点乘 `k` 取整到像素，再除以 `k` 放回 1:1 的页面；线条几何不动，比对的拟合把 `k` 连同整页一起拿掉。A2 的页面是 594.33 × 420.57 mm，参考画在 594 × 420 的纸上（拟合尺度 0.9999872，x 居中、y 贴底），不是这条映射，所以 A2 不取整，留给 A2 复核。

同一个比例也作用在字距上（第 9 项）。`render.dll` 在设备自己的像素上给每个字的 `lpDx` 取整，误差扩散「累计差过 1 px 就补一格」也在那里判，所以 `a8` 看到的是乘过 `k` 的样式字高。差别只有万分之一，只在累计差正好落在 1 px 边上的串上翻转：三张空冷图的 `AC-01031A/B/C`（Arial Narrow 10 pt，前 8 字 226 单位）按本页比例累计 107.008 px，差 1.008，补成 107 px；按设备比例累计 106.996 px，差 0.996，不补，106 px 与参考相同（`Tc` −0.2913，参考 −0.2910）。HxCD `25-CI-1450-B5-`（Arial 9 pt，前 13 字 422 单位）方向相反：末字的差按本页比例是 −0.989，不补（173 px），按设备比例是 −1.008，补一格（172 px），`Tc` 从 0.1011 变成 0.0642，参考 0.064。`CT-10017A`（224 单位）两种比例都补成 106 px，与参考相同。全语料只有这 4 条 run 的 `Tc` 变了。框宽、竖直线位是连续量，仍按本页比例；A2 不是标准幅面，`k` 取 1。

同一批参考图里还有一处只影响字形大小的差别：旋转的 Arial Narrow 写成 `0 1.008 −1.008 0 Tm`，旋转的 Arial 写成 `0 1.012 −1.012 0`，压窄 w800 的 Arial 写成 `0.809 0 0 1.012`（都是三位小数），`Tf` 与我方相同，所以只是字形大约 1%，起点不受影响（#15，源侧，不复现）；旋转的 SimSun 没有这个系数。
